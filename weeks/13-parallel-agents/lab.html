Week 13 Lab and Assignment ​

Lab — Three agents, one integrator (75 min) ​

Three agents can write three changes in the time one would take. Someone still has to read all three, check each against its issue, and make them work together, and today that someone is you. You'll plan a parallel run on three of roomly's issues, start three agents at once in three worktrees (one of them may be a background agent), then review and integrate their branches one at a time with a timer running, until CI is green on the combined result. The numbers you log are the start of this week's retrospective.

You'll use the roomly kit in a fresh copy. The issues in ISSUES.md are written against the code as shipped; your copy from weeks 5–10 has your own refactor and fixes in it, which would mix with the agents' diffs and make the review time meaningless.

Get a fresh copy:

  • Use the template: open the eswa-roomly template repository (link on Canvas), choose Use this template → Create a new repository, name it roomly-parallel, make it public (free CI), and open it in a Codespace.
  • Or copy its files: git clone --depth 1 https://github.com/Boyu-Zhang-UOI/eswa-roomly.git ~/roomly-parallel && rm -rf ~/roomly-parallel/.git, then git init, commit, and push it to a new repository of your own.

NOTE

🟢 AI on for the issues themselves: that's the point of the Lab. 🔴 AI off for your reviews: you read every diff yourself, so the time you log measures your review, not a reviewer bot's. Approvals stay on in every agent (rule 2), and all three run in your sandbox.

Before the Lab (about 20 minutes, at home; the Lab has no time for setup):

  1. Create the copy and open it in a Codespace. npm test should report 29 passing tests; no npm install is needed.

  2. Add CI. Create .github/workflows/test.yml:

    yaml
    name: Tests
on:
  push:
    branches: [main]
  pull_request:
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 22
      - run: npm test

    Commit it to main, push, and check that the run is green.

  3. Check that two CLI agents start in the Codespace and answer, each with a provider that works for you (the week 13 row of Tool Handout: Tools by week; two agents on one free key share its rate limit, so consider putting one on the lab machine).

  4. Optional, a background agent: if its allowance permits (TOOLS.md), connect Jules (or the Copilot cloud agent, if your plan has it) to this repository only, with the narrowest access the tool offers. Without one, you'll run a third CLI agent instead.

Setup check (5 min) — Core ​

bash
git switch main && git pull
npm test                         # 29 pass
git status                       # clean
gh run list --limit 1            # the CI run on main: success

✅ Checkpoint: tests pass, CI is green on main, and two agents start.

Part A — Plan the parallel run (10 min) — Core, 🔴 AI off ​

Plan before any agent starts, because the plan is what you'll compare the results with.

  1. Read ISSUES.md and, for each issue you're considering, find the code it will change: the route in src/server.js or src/routes.js, the function in a service module, the script. Use grep -n and open the files. Write down the files and functions for each, tagged observed.

  2. Pick three issues such that, by your reading, at least two of them change the same file. You're scheduling a conflict on purpose, to practice resolving it at a point you chose.

  3. Name the merge points: for each pair of issues, where you expect their branches to meet (a file, a function, the route table, the README's API table), and your integration order.

  4. Assign the agents and write a Specify · Delegate · Verify line for each issue in AI_LOG.md. Specify is the issue's acceptance criteria; Delegate is the agent, its permissions and its directory; Verify is the tests you expect and one check you'll run yourself.

  5. Start your review log in REVIEW_LOG.md:

    BranchAgentAgent startAgent doneReview startReview endReview minFindings (located)Sent back or fixed?Conflict filesConflict minTests after merge

✅ Checkpoint: three issues, their files, the predicted merge points and order, and three Specify · Delegate · Verify lines, all written before any agent starts.

Part B — Launch three agents (10 min) — Core ​

Create one worktree and branch per issue, from main:

bash
git worktree add ../roomly-issue-[a] -b issue-[a]
git worktree add ../roomly-issue-[b] -b issue-[b]
git worktree add ../roomly-issue-[c] -b issue-[c]    # skip if issue [c] goes to a background agent
git worktree list

Open a terminal in each worktree, check pwd, and start a CLI agent there with approvals on. Give each the same frame, with its own issue pasted in:

text
You are working on roomly, a Node.js JSON API with no framework, in this directory only.
Task: resolve issue #[n] from ISSUES.md:
[paste the issue's text and acceptance criteria]

Rules:
- Change only what this issue needs. If you notice other problems, list them at the end; don't fix them.
- First write tests that fail without the change, with node --test in tests/, using tests/helpers.js
  (freshData() gives a temporary data folder and a frozen clock). Never write to data/.
- Never weaken, skip or delete an existing test. Run npm test before you finish: everything must pass.
- Update README.md only if the API changed.
- Commit on this branch with a clear message. Don't push, merge or touch any other branch.
Start with a short plan and wait for my approval.

For a background agent, put the same frame and issue text in a GitHub issue in your repository, with one change: it pushes its own branch, so the last rule becomes "Push only your own branch; never push to main or merge". Then hand that issue to the agent as its documentation describes:

bash
gh issue create --title "[issue title]" --body-file [file with the frame and the issue text]

It works on a branch of its own and comes back with a branch or a draft PR. Record when you started each agent.

While they run, you're the supervisor: approve or refuse each plan and command, and count the approval prompts you answered. Three agents asking at once is where approvals get rubber-stamped; note any you approved without reading. If a manual check needs a server, give each worktree its own port (PORT=3001 npm start): each worktree has its own data/ folder.

✅ Checkpoint: three agents working, three start times logged.

Part C — Review and integrate, one at a time (25 min) — Core, 🔴 AI off for the review ​

Integrate on a branch, in the order you planned, as each agent finishes. In your main worktree:

bash
git switch -c integrate main

For each branch:

  1. Start the timer: write the clock time in REVIEW_LOG.md.

  2. Read the whole diff against the point where it left main:

    bash
    git diff main...issue-[a]                    # three dots: only what the branch changed
git fetch origin && git diff main...origin/[background-agent-branch]

  3. Check every acceptance criterion: name the test that covers it, or check it yourself (freeze the clock with ROOMLY_NOW=2026-11-09T16:00:00Z as the issues assume, start the server on its own port, and curl the case).

  4. Check the scope: nothing outside the issue, no existing test weakened, no writes to data/, no "while I was there" fixes. Run npm test in that worktree.

  5. Stop the timer. Log each finding with its file and line. If something is wrong, send the located finding back to the same agent session, or fix it yourself; either way it's a follow-up fix, logged, and the timer runs again for the re-review.

  6. Merge it into integrate and run the tests:

    bash
    git merge --no-ff issue-[a]                  # or origin/[background-agent-branch]
npm test

    On a conflict, time it separately. git status lists the files; resolve each one by reading both sides against both issues' acceptance criteria, not by keeping "ours" or "theirs" wholesale. Then git add the resolved files, run npm test, and git commit.

After the last merge, look for the conflicts git can't see: run the full suite, start the server once, and run one acceptance check from each issue against the integrated code. Then push and open a PR from integrate to main, with a description you write yourself (what's in it, how you verified it, the conflicts and how you resolved them):

bash
git push -u origin integrate
gh pr create --base main --head integrate --title "Integrate issues #[a], #[b] and #[c]" --body-file [your description]
gh pr checks --watch

If the background agent opened a draft PR of its own, close it with a link to yours once it's integrated.

✅ Checkpoint (checkoff): the integrate PR contains all three branches, CI is green on it, and REVIEW_LOG.md has your times and findings.

If time ​

  • Merge and clean up: merge the PR, then remove the worktrees (git worktree remove ../roomly-issue-[a], then git worktree prune). Never let an agent run git worktree remove --force or git reset --hard for you (troubleshooting).
  • A fourth reader: ask a fresh agent session to review each diff against its issue's criteria, with located findings only. Score its findings against yours: which were real, which invented, which it missed, and how long it took.
  • Your parallelism number: add up the agents' wall time and your review and integration time. Would two agents have finished sooner than three, given that your review is serial? What about one?

Checkoff ​

Staff confirm, at the end of the Lab:

  1. Three branches integrated: git log --oneline --graph integrate shows all three merges, and CI is green on the PR.
  2. The review log: for each branch, the agent's time, your review minutes, located findings, and any conflict with its minutes.
  3. Predictions against reality: the merge points you named in Part A, and where the branches actually met.
  4. A question, for example: "Show me one finding you sent back or fixed: what did the agent miss?" or "Which conflict did git not report, and how would you have caught it?"

Troubleshooting ​

  • fatal: '[branch]' is already checked out: a branch lives in one worktree at a time; make a new branch (troubleshooting).
  • An agent edited files in the wrong directory: it was started outside its worktree. Stop it, git status in each worktree, and restore what it touched. Check pwd before starting an agent.
  • A test passes alone and fails after the merge: two branches made changes that clash in behavior (a route both claim, a shared helper changed two ways). That's a semantic conflict: read both diffs together.
  • Tests depend on today's date: the agent didn't use freshData() or a frozen clock. Send it back.
  • The background agent can't see the repository: its GitHub app isn't installed on it, or its access was limited to another repository. Fix the installation, or run a third CLI agent and log the switch.
  • No CI run on integrate: the workflow runs on pushes to main and on pull requests; open the PR.
  • Rate limits with three agents on one key: move one agent to the lab machine or another provider, and log it.

Assignment — A process retrospective with data ​

Your team has run a semester of agent-assisted work through PRs, reviews and CI. Now measure it. The retrospective is team-written, with one individual section per member, in your team fork as course/RETROSPECTIVE.md; its numbers go into the final report's process section and are checked in the week 14 Lab (final report).

NOTE

Privacy. The fork is public. Report numbers by PR and by category of PR, never as a ranking of people. No grades and no judgments about teammates here: those belong in peer evaluation on Canvas (privacy of your work).

Deliverables ​

Team sections (written together):

  1. Scope and definitions, fixed before you compute anything: the period (for example from the m0 tag to the m2 tag); what makes a PR agent-authored, agent-assisted or human (from course/AI_LOG.md and Assisted-by: trailers, not from guesses); review time (what starts and stops the clock); time to merge; a follow-up fix (for example, a later PR within 7 days that changes lines a merged PR added, or says it fixes one); a CI failure and its causes.

  2. The data, reproducible: the raw exports committed under course/data/, and one script that computes every number in the retrospective from them:

    bash
    gh pr list --state all --limit 200 --json number,title,author,createdAt,closedAt,mergedAt,reviews,commits,additions,deletions > course/data/prs.json
gh run list --limit 500 --json databaseId,workflowName,event,headBranch,conclusion,createdAt > course/data/runs.json
node course/data/analyze.mjs      # or a Python script: one command, every number

  3. A results table by category of PR: count, merged, median (and maximum) review time, median time to merge, review rounds, follow-up fixes (count and share of merged PRs), CI failures before merge by cause (tests, lint, CodeQL or Semgrep, flaky, configuration).

  4. What course/AI_LOG.md shows: how many PRs have an entry; for how many verification caught something before merge, with two located examples; what the agents couldn't do.

  5. Findings, each tagged observed or inferred, with n, and at least one compared with a published number (for example Watanabe et al.'s 45.1% of merged agent PRs needing further changes), saying why your setting differs.

  6. What we'd delegate differently: at least three concrete changes (to course/TASKS.md, AGENTS.md, CI or the review process), each with the data behind it and what you'll measure to know whether it worked.

Individual section (one per member, headed by your GitHub username, written by you, 🔴 AI off):

  1. Your parallel run: your REVIEW_LOG.md summarized: the agents' wall time against your review and integration time; what your review caught; where the branches met against where you predicted; and how many agents you would run at once next time, and why.
  2. One of your M2 PRs as a case: what was delegated, what your verification caught (located), and the follow-up it needed, if any.
  3. One change in how you delegate, with the evidence from items 7–8.

Steps ​

  1. Agree the definitions as a team first, and write them down before anyone runs the script. A definition chosen after you see the numbers is a choice of result.
  2. Export the data and write the analysis script (🟢 an agent can write it; Specify the definitions, and Verify by computing two PRs' numbers by hand and checking that the script agrees). Commit the data, the script and its output.
  3. Fill in the team sections together; each member writes their own section.
  4. Check every number against the script's output, tag every claim, and list who wrote which section at the top.

How it's graded ​

The 15-point assignment rubric (Rubrics: Assignment (15 points)), scored for each member. The team sections count for every member who contributed to them (the list at the top says who); your individual section counts for you:

  • Deliverables work (5): the retrospective complete, with the data and script in course/data/; your individual section; your Lab integration with CI green (finish it if the Lab ended early).
  • Verification (4): definitions written before computing; one command reproduces every number from committed data; counts and medians with n; the script checked by hand on two PRs; claims tagged observed or inferred.
  • Process record (3): your AI_LOG.md entries for the parallel run (three Specify · Delegate · Verify lines and the review log), and Assisted-by: trailers on AI-assisted commits.
  • Write-up (3): your individual section: located claims; a delegation change backed by your own data; honest limits (small samples, self-timed review, which PRs were left out and why).

Due before next week's Seminar (default 11:59 pm the night before). Next week's Seminar opens with a 7-minute quiz on this assignment, the last quiz of the term.

NOTE

Minimum to keep up: your three branches integrated with REVIEW_LOG.md filled in; the team's PR and CI data exported with a script that reproduces a table of review time, follow-up fixes and CI failures; and your individual section. The final report's process section is built from these.
