Week 1 — Lab and Assignment ​

In the Lab you run a real, minimal coding agent and read every part of it: the loop, the tools, the approval gate and the trace. In the assignment you extend it, then use what you learned to take apart a session with a production CLI agent.

AI-use key: 🟢 AI on: use any assistant or agent, following the Safe Loop · 🔴 AI off: no assistant, no completions, no chat; your own reading and writing. Close the AI panels and turn completions off for 🔴 parts.

Rules for agents this week (safety contract): work in a Codespace; approvals stay on (no --yes, no autopilot or "yolo" modes); your key lives in a Codespaces secret, never in a file you commit; commit before and after every agent task.

Before the Lab (15 min) ​

  1. Create your repository from the kit. Open the eswa-mini-agent template (link on Canvas) → Use this template → Create a new repository, public, in your own account, named eswa-mini-agent. Or copy its files into a new repository of your own:

    bash
    git clone --depth 1 https://github.com/Boyu-Zhang-UOI/eswa-mini-agent.git eswa-mini-agent
cd eswa-mini-agent && rm -rf .git && git init -b main && git add . && git commit -m "Start from the mini-agent kit"

    Then publish it to GitHub (VS Code's Publish to GitHub, or gh repo create).

  2. Add your key as a Codespaces secret. github.com → Settings → Codespaces → New secret: name LLM_API_KEY, value your free-tier key (which provider), repository access only eswa-mini-agent (why a secret, not a file).

  3. Create a codespace on the repository (Code → Codespaces → Create codespace on main).

The lab machine's local models aren't reachable from a Codespace. In this Lab, use the free API. The lab machine is for laptops in a dev container on the campus network or VPN (local models).

Setup check (5 min) ​

In the codespace's terminal:

bash
node --version
test -n "$LLM_API_KEY" && echo "LLM_API_KEY is set"

You need Node 20.12 or later (22 recommended) and the line LLM_API_KEY is set. If the key isn't set, you added the secret after creating the codespace: reload it when VS Code offers, or rebuild it.

Part 1 — Configure and test the kit (10 min) ​

Core · 🟢 AI on

  1. Create .env and confirm git ignores it:

    bash
    cp .env.example .env
git check-ignore -v .env

    The second command must print the .gitignore line. If it prints nothing, stop and fix .gitignore.

  2. Edit .env: set LLM_BASE_URL and LLM_MODEL to the primary provider's values in Tool Handout: LLM APIs for the kits, and delete the LLM_API_KEY line: the secret provides it, and each variable lives in one place only.

  3. Run the offline tests, then a task that changes nothing:

    bash
    npm test
node agent.mjs "List the files in the workspace and tell me how many there are."

    npm test must end with # fail 0. The agent prints the workspace path and its trace file, calls list_files (read-only, so no approval prompt), and answers.

✅ Checkpoint: # fail 0, and one answer from the model. On a 401, 404 or 429, see troubleshooting.

Part 2 — Read the loop (15 min) ​

Core · 🔴 AI off. Reading this code yourself is the point: in the oral exams you'll explain a trace without help.

Open agent.mjs, lib/tools.js and lib/approval.js side by side. Create NOTES.md in the repository root and answer each question in one or two sentences, with the file and line you read. Each answer is an observed claim because you read the line, so cite it.

  1. runAgent: which two conditions end the loop, and what status does each return?
  2. executeToolCall: list the checks, in order, that a tool call passes before its handler runs. Where does the workspace guard (resolveInside) run relative to the approval gate?
  3. Which tools need approval, and where is that decided?
  4. What exactly does the model receive after you deny a command? Quote the string.
  5. lib/approval.js: name two cases in which a command that starts with an allowlisted prefix still prompts you. When is --yes refused?
  6. The kit's README says, under "Safety rules", that the file tools can't read or write outside the workspace. Find the code that runs run_command. Does the same guard apply to it? What would stop cat ~/.bashrc?
  7. lib/model.js: which failures are retried, and which are not? Why the difference?
  8. Look at what executeToolCall writes to the trace. Which trace line holds the output of a tool? (Look carefully. Part 4 checks your answer.)

✅ Checkpoint: eight answers in NOTES.md, each citing a line. Commit it:

bash
git add NOTES.md && git commit -m "Lab 1: notes on the mini-agent loop"

Part 3 — First run, every change approved (15 min) ​

Core · 🟢 AI on

For this run there's no allowlist and no --yes, so every write and every command stops at the gate. Check that no allowlist exists, then start the task:

bash
ls .agent-allowlist 2>/dev/null || echo "no allowlist: every command will ask"
node agent.mjs "In the workspace, create slugify.mjs exporting a function slugify(title) that lowercases, trims, replaces each run of characters other than a-z and 0-9 with a single hyphen, and strips leading and trailing hyphens. Create slugify.test.mjs using node:test with at least three cases, including the empty string. Run the tests with node --test and fix any failure. Then summarize what you did, marking each claim observed or inferred."

At each prompt, read before you answer. For edit_file: is the path inside the workspace, and a file the task needs? For run_command: does the whole command do only what the task needs, and would you run it yourself? Answer y only then. If you answer n, watch what the agent does next, and rerun the task until one run finishes with every change approved: that's your checkoff run.

When it finishes, check the result yourself rather than trusting the summary:

bash
cd workspace && node --test && cd ..

Save the trace as evidence, check it holds no key, and commit it. (traces/ is git-ignored, so copy the file out.)

bash
mkdir -p evidence
cp "$(ls -t traces/*.jsonl | head -1)" evidence/week1-checkoff.jsonl
grep -qF "$LLM_API_KEY" evidence/week1-checkoff.jsonl && echo "KEY FOUND: do not commit" || echo "no key in the trace"
git add evidence/week1-checkoff.jsonl && git commit -m "Lab 1: trace of the checkoff run"

✅ Checkpoint: node --test in workspace/ ends with fail 0, the trace is committed, and the agent's summary tags its claims. Check whether its "observed" claims really are: did it run what it says it ran?

Part 4 — Read the trace (10 min) ​

Core · 🟢 AI on (but answer the questions yourself)

A trace is one JSON object per line: model_request, model_response, approval, tool_call and, if the step limit hit, stopped (trace). Print a one-line summary of each:

bash
node -e '
const fs = require("fs");
for (const line of fs.readFileSync(process.argv[1], "utf8").trim().split("\n")) {
  const e = JSON.parse(line);
  const calls = e.message?.tool_calls?.map((c) => c.function.name).join(", ");
  const what = e.type === "model_request" ? "" : (e.name ?? calls ?? "(text reply)");
  const size = e.type === "model_request" ? `${JSON.stringify(e.messages).length} chars sent` : "";
  console.log(e.type.padEnd(15), String(e.step ?? "").padEnd(3), what, e.decision?.reason ?? "", size);
}' evidence/week1-checkoff.jsonl

Add answers to NOTES.md, under a heading "Trace":

  1. How many model turns did the run take, and how many approvals did you give?
  2. How many characters did the first request send, and the last? Why does it grow, and roughly how fast? (Hint: what does each request contain?)
  3. Find the output of your first run_command. Which line is it on? Was your answer to Part 2 question 8 right?
  4. Name three things a model received or used that aren't in this trace. Hint: look at what callModel sends and what the provider returns.

✅ Checkpoint: four answers under "Trace", committed.

Part 5 — Deny, and test a claim (If time) ​

If time · 🟢 AI on

Part 2 question 6 was answered by reading code. Make it an observed claim by experiment, in your codespace, where nothing in your home directory matters:

bash
node agent.mjs "Run the command: ls ~ and tell me what it printed."

Approve it once: the output lists the codespace's home directory, outside the workspace. Run it again and deny it, then find the denial in the new trace: what did the model see, and do next? Record both in NOTES.md, tagged observed. The guard protects the file tools; for a shell command your "no", and behind it the sandbox, is all there is. Week 2 looks at why production harnesses add an operating-system sandbox.

Part 6 — Same task, three runs (If time) ​

If time · 🟢 AI on

Delete the workspace files (rm -f workspace/slugify*) and run the Part 3 task twice more. For each run, record the turns, the sequence of tool names and whether the tests passed. Which differences matter for correctness? With a fallback key, switch provider by configuration (how), run it once more, and log the switch in AI_LOG.md: a different model gives a different result.

Checkoff (15 min) ​

Show a staff member, in your codespace:

  1. npm test ending with # fail 0.
  2. evidence/week1-checkoff.jsonl, committed: the task finished, and an approval line with reason approved at terminal comes before every edit_file and run_command tool call (no --yes, nothing allowlisted).
  3. node --test passing in workspace/.
  4. NOTES.md with the Part 2 and Part 4 answers, pushed. Staff ask you to explain one, usually "where is a tool's output in the trace?" or "what stops cat ~/.bashrc?"

Scored with the Lab checkoff rubric. Blocked by a tool? Show the exact error and what you tried: a precise blocker earns partial credit.

Next steps (5 min) ​

  • Push everything (git push) and stop the codespace when you leave.
  • Read the assignment below, and install your CLI agent for Part C now, so a sign-up problem surfaces this week, not the night before.
  • If you haven't yet: sign the safety contract and fill in the team-formation survey on Canvas.

Assignment — Extend the agent and dissect a real one ​

About 4.5 hours. Everything goes in your eswa-mini-agent repository. Submit the repository URL and the commit to grade on Canvas (how to submit).

Deliverables ​

DeliverableWhereAI use

B. One extension (approval policy, compaction or bash-only), with testsYour choice of files, plus tests🟢 AI on
EXTENSION.md: what you built, how you verified it, its limitsRepository root🟢 AI on
C. A trace dissection of a session with a real CLI agentTRACE_DISSECTION.md, plus the raw session in evidence/Session 🟢 AI on · annotations 🔴 AI off

All the kit's original tests must stay green, and every new test must run offline (a scripted model or a stubbed fetch, as in tests/).

A. A new tool (about 1 hour) ​

Pick one, or propose your own of similar size:

  • search_files(query, path?): grep across the workspace. Read-only.
  • read_file_range(path, start_line, end_line): read part of a file, so the model can stay inside a small context.
  • delete_file(path): changes the world, so it needs approval and a clear describe() line.

Requirements:

  1. A JSON schema in TOOL_DEFINITIONS with a short, literal description and correct required fields. The description is a prompt the model reads, so write it as carefully as code.
  2. A handler in createTools. Every path goes through workspace.resolveInside, and the output is capped, as the other tools do.
  3. A decision about approval (NEEDS_APPROVAL), justified in one sentence in EXTENSION.md.
  4. Check first: write the tests before the handler, run npm test, and paste the failing output once into EXTENSION.md. At minimum: one test for normal use, one for misuse (a path escape or a bad argument rejected with a ToolError), and one loop test in which a scripted model calls your tool and receives its result (copy scriptedModel from tests/loop.test.js).

B. One extension (about 1.5 hours) ​

Choose one. The kit's README lists them under "Lab extensions" (kit README).

B1. A smarter approval policy. Classify each command as read-only (runs without asking), workspace-writing (asks) or dangerous (refused without asking: sudo, rm -rf, network tools, a pipe into a shell). Test every branch, then try to defeat your classifier and add two bypasses as tests that document the limit. In EXTENSION.md, explain why classifying a shell string is a usability aid, not a security boundary: what the kit's SHELL_CONTROL rule in lib/approval.js does and doesn't catch, and why an allowlisted test command runs whatever the tests contain (approval policies).

B2. A context budget with compaction. Before each model call, measure the history (characters, or characters ÷ 4 as a rough token count). Over a budget, replace the oldest turns with a short summary (a deterministic digest, or a tool-less model call), keeping the system prompt, the task and the latest results. The trap: every tool message must follow the assistant message that requested it, so compact whole exchanges. Test that the system prompt and task survive, the history ends under budget, and no tool message is orphaned. Then measure one real task with a small budget and with none: turns, characters sent, and whether the agent forgot a constraint (compaction).

B3. A bash-only mode, like mini-swe-agent: a --bash-only flag that leaves only run_command. Test that the model sees one tool and that edit_file is reported as unknown. Run the Part 3 task in both modes and compare the traces (turns, approvals, how it edited files without an edit tool), and explain what the approval gate must now catch on its own.

EXTENSION.md (about 400–700 words): Specify · Delegate · Verify for parts A and B (what you decided, what an agent wrote, how you checked it); the failing-then-passing test output; for B, your measurement or bypasses; and the limits you know of. Locate every claim (file and line, command and output) and tag it observed or inferred.

C. Trace dissection of a real agent (about 1.5 hours) ​

  1. Choose an agent from the CLI row of the stack table: Gemini CLI (the primary), Copilot CLI or OpenCode. Prefer an open-source one (Gemini CLI or OpenCode): then you can read its system prompt and tool definitions in its source, which makes them observed rather than inferred.

  2. Set up safely. Run it in a codespace on your eswa-mini-agent repository: your own public course work, which the data rule allows on a free tier. The key comes from a Codespaces secret, never a file in the repository (for Gemini CLI, a secret named GEMINI_API_KEY for this repository, or export GEMINI_API_KEY="$LLM_API_KEY" if your kit key is a Gemini key). Keep the default approval mode, which asks before writes and commands; never a "yolo" or auto-approve mode (rule 2). Commit before you start (rule 7). If it asks to read .env or to run env or printenv, deny it.

  3. Give it a small real task with reads, at least one write and at least one command, for example:

    text
    Read lib/tools.js and tests/tools.test.js. Add one test to tests/tools.test.js showing that list_files skips node_modules and .git directories. Run npm test and report the result. Do not change any other file.

    Aim for at least 8 tool calls. Approve and deny as you would for real, and note each decision as you make it.

  4. Capture the evidence. You need the session (every tool call, its arguments and its result), the tool list and, where visible, the system prompt. Where to find them changes between versions, so check the agent's own documentation (--help, /help). The instructor posts the current commands on Canvas. At the time of writing:

    AgentSystem promptToolsSession
    Gemini CLI (Apache-2.0)In its source on GitHub; its documentation describes GEMINI_WRITE_SYSTEM_MD, which writes the built-in prompt to a file/tools desc lists tools with descriptions/chat save [tag] saves the conversation; /stats shows token use
    OpenCode (MIT)Prompt files in its source on GitHubIts documentation lists the built-in toolsopencode export writes a session as JSON
    Copilot CLINot published: describe what you can infer, and tag it inferredAsk it to list its tools (inferred); compare with GitHub's documentationIts session export or share command, if your version has one; otherwise a copy of the terminal

    Copy the raw session into evidence/. Before committing, check it doesn't contain your key: grep -rqF "$LLM_API_KEY" evidence/ && echo "KEY FOUND" || echo "no key". Repeat with the agent's own variable (for example GEMINI_API_KEY) if it has one.

  5. Write TRACE_DISSECTION.md (🔴 AI off: the reading and the tags are yours). Use these sections:

    markdown
    # Trace dissection — [agent] on [task]

## Setup
Agent and version · model · provider and allowance · date · repository and starting commit · approval mode · how you captured each piece of evidence

## The system prompt
Where you found it (file and commit, or exported file), or "not visible". Its size (characters, rough tokens).
Its sections in order, one line each. Three instructions in it that shaped what you saw, each linked to a step below.

## The tool schemas
| Tool | Parameters | Needs approval? | Evidence | Observed or inferred |

## The session, step by step
| # | What the agent did (tool and key arguments) | What came back (short) | Your decision | Why it did this | Observed or inferred |

## Three decisions that mattered
For each: what the agent chose, what else it could have done, what in its context led there (tag it)

## Compared with mini-agent
At least four differences (system prompt size, tools, edit format, approvals, context management, anything else), each located in both

## Claims I couldn't verify
At least three inferred claims, and for each, the check that would make it observed

    Minimums: every step of the session (at least 8 tool calls), at least four tools, at least one approval, denial, retry or error, and every row tagged. "Why it did this" is almost always inferred; say so.

AI log and commits ​

Add AI_LOG.md from the template, with one entry for each significant session: the extension work, the dissection session and any provider switch. Commit in small steps; AI-assisted commits end with a trailer:

text
Add search_files tool with path-escape test

Assisted-by: [tool and model]

How it's graded ​

20 points for the week: the Lab checkoff (5) and this assignment (15), on the labs and assignments rubric. This week, the rows mean:

Row (points)What it means this week
Deliverables work (5)The new tool and the extension work as specified; all the kit's original tests and yours pass offline; the dissection has every section and meets the minimums
Verification (4)Tests written first, with the failing run shown once; a misuse or escape test; for B1 branch and bypass tests, for B2 a before/after measurement, for B3 the trace comparison; in the dissection every claim tagged, and inferred claims paired with the check that would settle them
Process record (3)AI_LOG.md entries with Specify · Delegate · Verify and what your checks caught; small commits; Assisted-by: trailers
Write-up (3)EXTENSION.md and the dissection locate their claims (file and line, trace step, command and output), compare with mini-agent specifically, and state limitations

Due before next week's Seminar (default 11:59 pm the night before). The week 2 Seminar opens with a 7-minute, 🔴 AI-off quiz about this assignment (quizzes). Expect questions about your own tool, your extension, the mini-agent trace and your dissection.

IMPORTANT

Minimum to keep up. mini-agent runs in your codespace against at least one provider, with approvals on, and you can explain its loop, its approval gate and its trace. Week 2 compares a production harness with it, and week 4 attacks it. If you're short of time, submit part A with its tests and the dissection, and say in EXTENSION.md what part B would have needed. A documented gap earns more than a hidden one.

Troubleshooting ​

ProblemFix
The agent is not configured: LLM_API_KEY not setThe secret isn't in this codespace. Check its repository access, then reload or rebuild the codespace
401 or 403Wrong key, or a key for a different provider than LLM_BASE_URL (troubleshooting)
404LLM_BASE_URL or LLM_MODEL doesn't match Tool Handout: LLM APIs for the kits character for character (watch the trailing slash and /v1)
429 again and againThe kit retries with backoff. If it keeps failing you've hit a daily cap: switch provider by configuration and log it
The model writes prose or prints commands instead of calling toolsTry the next model in TOOLS.md (troubleshooting)
The run hit max_stepsRead the trace: is the model stuck repeating a failing edit? Rerun with a clearer task; don't just raise --max-steps
The agent edited something you didn't expectgit status and git diff; discard with git restore [file]. That's why you committed first
