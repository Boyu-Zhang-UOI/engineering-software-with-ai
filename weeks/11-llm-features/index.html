Week 11 — Building LLM Features ​

An LLM feature is a parser with a probabilistic front end: the model only proposes, and your schema, validation, retries and budget decide what the rest of the system accepts.

This week at a glance ​

WARNING

The data rule applies to every live call. Free tiers may train on what you send (Tool Handout: The data rule). Send only the kit's cases and requests you made up. Recordings store everything you sent and get committed, so never type personal data into npm run extract.

Learning objectives ​

By the end of this week you can:

  1. Distinguish asking for JSON, a provider's JSON mode and schema-constrained structured output, and explain why you validate in code in every case.
  2. Read a schema written as data and its validator, and say what validation catches (form) and misses (meaning).
  3. Design a retry with repair, and name the risk that a retry satisfies the validator by inventing data.
  4. Log and budget tokens, cost and latency per request, including what retries add.
  5. Measure one change against a baseline on the same cases and model, case by case, and write an error analysis with categories, counts and examples.

Lab ​

The lab uses the eval-harness kit: an extractor that turns "Book a room for 12 people next Tuesday 2–3pm with a projector" into a booking object for roomly, validated in code, with up to three attempts. You replay the 30 shipped cases (hand-written recordings: about 97% valid, about 63% fully correct), read the validator and the retry loop, then record a live baseline into your own folder, leaving the shipped recordings untouched.

Reading ​

Tam et al., "Let Me Speak Freely? A Study on the Impact of Format Restrictions on Performance of Large Language Models" (EMNLP 2024 Industry), read with .txt's reply, "Say What You Mean", the reading list's core pick. Tam et al. report that reasoning gets worse when the output format is restricted. .txt traces the effect to prompts that differed between conditions and to an LLM used as the answer parser; with matched prompts, structured output did as well or better (GSM8K 0.77 → 0.78, Last Letter 0.73 → 0.77). Compare the two methods sections.

Reading response prompt (150–250 words, 🔴 AI off, on Canvas): State each side's claim in one sentence. Name the one difference in method that you think explains most of the disagreement, and say whether it is a difference in the treatment or in the measurement. Then decide what it means for this week's extractor, which asks for plain JSON in the prompt and validates it in code: would you switch on a provider's structured-output mode, and what would you measure to know? End with one question for the debate.

Key ideas ​

  • The model proposes; code disposes. A reply is untrusted input: parse it, validate it, and let roomly still enforce its booking rules.
  • Valid is not correct. A schema checks types, enums and patterns. It can't tell that "next Tuesday" became the wrong week. Report validity and correctness separately.
  • Constrained decoding guarantees form, not meaning. Vendors report 100% schema adherence with it (OpenAI); whether it costs quality depends on how you measure, as the debate shows. Validate anyway.
  • A retry is a second, longer prompt. Feed back the exact errors, cap the attempts, decide what happens after the last one (fail closed, or ask), and watch for a model that passes the validator by inventing data.
  • Tool calling is structured output with a dispatcher. Tool-calling agents succeeded on under 50% of τ-bench tasks, and pass^8 was below 25% in retail: reliability (pass^k) is its own metric (Yao et al.).
  • Budgets are per request, and retries multiply them. Log every attempt, read p95 as well as the median, and take prices from TOOLS.md, never from code.
  • Retrieval has its own failure points, and RAG "can only be fully validated in operation" (Barnett et al., RAG). For bookings, the room catalog belongs in a query to roomly, not in the prompt.
  • A recording describes only the prompt that produced it. The kit keys recorded responses by a hash of the exact request: change the prompt and every replay fails until you record again.

Check your understanding ​

  1. The shipped run is about 97% valid but about 63% fully correct. Where does the other third go, and which of those failures could any schema catch?
  2. You add a cross-field rule to schema.js. Why might replay now fail on some cases but not others?
  3. Why does a retry cost more tokens than the first attempt, although it asks for the same object?
  4. Your change fixes 3 cases and breaks 1, out of 30, in one run. What can you claim?

If a tool is down ​

  • Rate-limited or down: switch provider in .env (Groq, OpenRouter or the lab machine; Tool Handout: LLM APIs for the kits), log it, and record into a new folder: a different model is a different baseline. Raise --delay-ms on a tight limit.
  • The lab machine's queue is long: record ten cases with --only for the checkoff and the rest later (troubleshooting).
  • No live model at all: Parts 1 and 2 replay offline. Analyze the shipped recordings, say they are hand-written, and record your baseline when a provider is back. API errors: troubleshooting.

Going further ​

  • Barnett et al., "Seven Failure Points When Engineering a RAG System", with Es et al., "Ragas", whose metrics are themselves LLM judges (next week's topic).
  • Hong, Troynikov & Huber, "Context Rot": a focused prompt of about 300 tokens beat the full 113K-token one.
  • CS [5xxx]: Tam et al. vs .txt is on the replicable list.
