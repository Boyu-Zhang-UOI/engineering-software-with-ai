Week 11 Lab and Assignment ​

Lab — A validated extractor: replay, read, run live (75 min) ​

The feature this week is small on purpose: one request in natural language, one booking object out. Everything around the model call is ordinary engineering you can read in an afternoon: a schema written as data, a validator, rules that span fields, a retry loop that feeds the validator's errors back to the model, and a log of tokens and latency for every attempt. Today you run it on the shipped recordings, read how it decides what to accept, see why a recording only describes the prompt that produced it, and then run it live against your own model, recording a baseline you'll measure your improvement against.

You'll use the eval-harness kit. It has no dependencies; only Part 3 needs a key.

Get the kit (once per student; you'll use the same repository next week):

  • Use the template: open the eswa-eval-harness template repository (link on Canvas), choose Use this template → Create a new repository, make it public (free CI next week), and open it in a Codespace.
  • Or copy its files: git clone --depth 1 https://github.com/Boyu-Zhang-UOI/eswa-eval-harness.git ~/eswa-eval-harness && rm -rf ~/eswa-eval-harness/.git, then git init and push it to a new repository of your own.

NOTE

🟢 AI use: code changes and small analysis scripts may be written with an agent, under the Safe Loop with approvals on, and logged. 🔴 AI off for Part 2: read the schema and the retry loop yourself. You'll be asked about your own changes to them in next week's quiz, and the error analysis depends on knowing exactly what the validator does.

Before the Lab (10 minutes, at home): create your repository and open it in a Codespace; put your free API key in .env as setup describes, or ask staff for the lab machine's address; run npm test. Don't run npm run calibrate or npm run eval:judge yet: next week you label titles before you see any judge's verdicts.

Setup check (5 min) — Core ​

bash
node --version   # 22.x (minimum 20.12)
npm test         # 38 tests pass, with no network and no key
npm run eval     # replays the 30 shipped cases from evals/recordings/

✅ Checkpoint: 38 tests pass, and npm run eval prints 30 case lines and a summary that names the model hand-written-example.

Part 1 — The shared baseline (10 min) — Core ​

The shipped recordings in evals/recordings/ were written by hand to look like a plausible model's output, mistakes included, so that the eval has something to find. They are everyone's starting point and the data the kit's tests replay. You will never edit or overwrite them.

Save their report where git will keep it (reports/ is not committed):

bash
npm run eval -- --out results/shipped

Read the per-case lines in the terminal and results/shipped/eval-report.md: the summary, the status confusion table (rows are what the case expected, columns what the feature said) and the table by tag. Write down, in a scratch file you'll turn into this week's error analysis:

  1. Valid after retries versus fully correct. They differ by about a third of the cases. Where does that third go?
  2. The worst field, and the worst tag.
  3. Which cases needed more than one attempt, and which one never became valid.

✅ Checkpoint: results/shipped/ holds eval-report.md, eval-report.json and calls.jsonl, and you can say in one sentence why "valid" is not "correct" here.

Part 2 — Read the schema and the retry loop (15 min) — Core, 🔴 AI off ​

Read src/schema.js (about 140 lines), then extractBooking() and the functions around it in src/extract.js. Answer each question with a file and a line, tagged observed:

  1. Form. Name three things the validator enforces that the prompt only asks for. Where does the list of allowed features come from, and why is it written once and used in two places?
  2. Rules across fields. Which rules need more than one field? Why does validateBookingRequest() run them only after the schema passes?
  3. Repair. When an attempt fails, what exactly does the model get back? Open the recording of a case that needed two attempts (the npm run eval output marks them) in evals/recordings/extract/[case].json, and read the second request's last two messages: the model's own bad reply, and the error list.
  4. Giving up. What does extractBooking() return after the last invalid attempt, and how does the eval score that case?
  5. Meaning. Find one case in your Part 1 notes whose output passes every rule and is still wrong. What would a rule that catches it have to know?

Now see why the kit keys recordings by a hash of the exact request. Change one character of SYSTEM_PROMPT in src/extract.js (a comma, say), then:

bash
npm run eval -- --only c02   # ReplayMissError: no recorded call matches this request
npm test                     # two tests now fail: they replay the shipped recordings
git restore src/extract.js   # put the prompt back
npm test                     # 38 pass again

Read requestKey() in src/recorder.js: the hash covers the messages, the temperature and the response format, but not the model. A recording says something only about the request that produced it, so a prompt change means recording again, and a different model means a different baseline even when every request is the same.

✅ Checkpoint: written, located answers to the five questions, and you have seen the replay miss and can explain it.

Part 3 — Run it live and record your baseline (20 min) — Core ​

1. Configure a provider. If you didn't before the Lab:

bash
cp .env.example .env    # then fill in LLM_BASE_URL, LLM_API_KEY and LLM_MODEL
npm run models          # list model IDs; copy one into LLM_MODEL

Use a free API key or the lab machine's Ollama; the base URLs and the suggested models are in Tool Handout: LLM APIs for the kits. .env is in .gitignore: never commit it, and never paste a key into a chat or an issue (safety contract rule 4).

2. One request, live.

bash
npm run extract -- "Need a room tomorrow 10-11am for 4, whiteboard please"

It prints the object, whether it's valid, and one line per attempt with tokens, latency and cost. Try one request of your own that should need clarification, and one that tries to change the rules. Only made-up requests: free tiers may train on them (the data rule).

3. Prices. Copy your model's input and output prices per million tokens from Tool Handout into prices.json, under a key that is exactly the model name the kit prints. On a free tier, write 0 for both: the money cost is zero, and the real budget is the rate limit, which you note in AI_LOG.md.

4. Record your baseline, with the prompt exactly as shipped, into your own folder:

bash
npm run eval:record -- --recordings evals/recordings-[model] --out results/[model]-baseline --delay-ms 2500

[model] is a short, folder-safe name for your provider and model (for example gemini or lab-ollama), the same in every command this week. The run makes about 30–40 extraction calls plus one judge call per valid title, so the folder is complete enough for the kit's tests and next week's CI gate to replay. Its report shows the judge's verdict on each of your titles: skip that column, because next week you may label these titles yourself, blind. --delay-ms pauses between cases; on a generous provider you can lower it.

WARNING

Always pass --recordings to eval:record. Without it, the command overwrites the shipped recordings in evals/recordings/, the shared baseline the tests depend on. If that happens, git restore evals/recordings puts them back.

5. Check it. Replay your folder, which needs no network:

bash
npm run eval -- --recordings evals/recordings-[model]
git status                       # your new folders; no .env; nothing changed in evals/recordings/

Open one recording: it holds the requests, the provider's responses and the latency, never the key.

6. Read the cost and latency log. results/[model]-baseline/calls.jsonl has one line per call: case, purpose (extract or judge), attempt, model, tokens, latency and cost. How much of your extraction budget did retries take?

bash
node -e '
const calls = require("fs").readFileSync(process.argv[1], "utf8").trim().split("\n").map(JSON.parse);
const tokens = (list) => list.reduce((sum, c) => sum + c.totalTokens, 0);
const extract = calls.filter((c) => c.purpose === "extract");
const retries = extract.filter((c) => c.attempt > 1);
console.log(`extract calls ${extract.length}, of which retries ${retries.length}`);
console.log(`tokens spent on retries: ${(100 * tokens(retries) / tokens(extract)).toFixed(1)}%`);
' results/[model]-baseline/calls.jsonl

A retry is a longer request than the first attempt: it carries the whole conversation so far. Write the totals, the cost per case, p50 and p95 latency, and the share spent on retries into an AI_LOG.md entry, with the provider and which allowance it used. Commit the recordings, results/ and prices.json, with an Assisted-by: trailer if an agent helped.

✅ Checkpoint (checkoff): a live recorded run of the 30 cases in evals/recordings-[model]/, a report that names your model, and its calls.jsonl, committed.

Part 4 — Choose your improvement (If time) ​

Compare your run with the shipped one, case by case:

bash
node -e '
const fs = require("fs");
const [before, after] = process.argv.slice(1).map((f) => JSON.parse(fs.readFileSync(f, "utf8")));
const was = new Map(before.results.map((r) => [r.id, r.pass]));
for (const r of after.results) if (was.get(r.id) !== r.pass) console.log(r.id, r.pass ? "fail -> pass" : "pass -> FAIL");
' results/shipped/eval-report.json results/[model]-baseline/eval-report.json

Then pick the kind of change you'll make in the assignment. How you can measure it depends on whether it changes what is sent to the model:

ChangeDoes it change the requests?How to measure it
The prompt or the retry message (SYSTEM_PROMPT, firstMessages(), retryMessage())AlwaysRecord live into a new folder and compare with your baseline: same model, same cases
The schema or validator (schema.js)Only for cases where a new rule rejects a reply that used to pass: that case now sends a retry nobody recordedReplay first: each replay miss names a case that needs a live call. Then record live into a new folder
A deterministic repair after a valid reply (code in extractBooking() that corrects or downgrades a valid answer, then validates it again)NeverReplay both the shipped recordings and your baseline: offline, free and repeatable

Write the Verify line now, before you change anything: which case IDs you expect to flip from fail to pass, what must not get worse, and the cost you'll accept.

Your noise floor (If time): record the unchanged baseline a second time into evals/recordings-[model]-rerun and compare the two runs with the command above. Temperature 0 is not a promise of identical output. Cases that flip between two identical runs are noise; an "improvement" no larger than that isn't one.

Checkoff ​

Staff confirm, at the end of the Lab:

  1. npm test passes, and the shipped recordings are unchanged (git status evals/recordings shows nothing).
  2. A live recorded run of the 30 cases in your own folder, whose report names your model. If the lab machine's queue made a full run impossible, ten cases recorded with --only count for the checkoff, with the rest due in the assignment.
  3. Its calls.jsonl, committed, and prices in prices.json (or 0 with the free tier named).
  4. You can answer one question about it, for example: "Show me a retry request in your recording: what did the model get back?" or "Why would your recording fail to replay after you change one word of the prompt?"

Troubleshooting ​

  • Missing settings: LLM_...: .env is missing or still has the placeholders from .env.example.
  • 401, 404 or 429: wrong key, wrong base URL or model ID (run npm run models), or a rate limit; raise --delay-ms and see troubleshooting. A run interrupted halfway keeps what it recorded; run it again.
  • Cost still shows unknown: the key in prices.json must match the model name in the report's model(s): line, which some providers write differently from your LLM_MODEL.
  • Every reply is prose, or the model ignores the format: a small local model may need a larger context (local models); some providers support --response-format json_object (JSON mode). Either is a change to the requests: record it into its own folder, and log it.
  • ReplayMissError you didn't expect: something that builds the request changed (the prompt, a case's input or now, the response format). git diff shows what.
  • The provider times out: the client waits 60 seconds per call. On the lab machine at a busy moment, record fewer cases at a time with --only.

Assignment — One measured improvement and an error analysis ​

You have a baseline from your own model. Now find out what goes wrong and why, change one thing, and show whether it helped, case by case, on the same cases and the same model. This is the method you'll use next week and in the team project whenever a contribution calls an LLM (EVAL_PLAN template).

Deliverables ​

In your eswa-eval-harness repository:

  1. ERROR_ANALYSIS.md on your live baseline (or sections 2 and 8 of EVAL_PLAN.md, if you prefer to start that file now):
    • Every failing case read in full: the input, the expected fields, each attempt's reply and errors (in the recording).
    • Categories you derived from the data, named for what went wrong ("resolves a relative weekday to the wrong week", not "date error"). Write a one-line note per failure first, then group; a case may fall in two categories. Some categories only appear once you look (criteria drift).
    • A table: category · count out of 30 · case IDs · one example (input, expected, got) · validity failure or correctness failure · could a schema rule or a deterministic check catch it, or does it need judgment?
    • What the validator did: which first attempts failed, whether the retry fixed them, and what the retry changed besides the error it was told about.
    • Cost and latency: tokens in and out, cost per case (or 0 and your free tier's limit as the real budget), p50 and p95 latency per case, the share of tokens spent on retries, and the slowest case with a reason.
    • The shipped run, briefly: which of your categories it shares, and why a hand-written run is evidence about the method, not about any model.
    • What you'd change next: a ranked list, each item with the cases you expect it to fix and what it costs.
  2. One improvement, as a pull request in your own repository:
    • One change of one kind (prompt, retry message, schema or validator, or deterministic repair), aimed at the category your analysis ranks first. Leave evals/cases.jsonl alone: editing an expected value to match the model's answer changes the test, not the feature.
    • Its recordings in their own folder, evals/recordings-[model]-[change], recorded with the same model; the shipped recordings and your baseline unchanged.
    • A before-and-after table in the PR description: validity, first-attempt validity, case accuracy, the field you targeted, tokens per case, p95 latency; then the list of cases that flipped in each direction.
    • If the change alters any request, the two tests in tests/eval.test.js that replay the shipped recordings (the end-to-end replay and the CI-gate test) fail on this branch, as you saw in Part 2. In the same PR, point the RECORDINGS constant at your new folder and pass it to the CI-gate test's command ('--recordings', RECORDINGS), and say why in the description: the tests now replay the recordings that match the current prompt. Never delete or skip a test.
    • Your decision: merge if the paired comparison supports it, otherwise close it, with your reason either way. The PR description is yours (🔴 AI off).
  3. AI_LOG.md entries for the Lab and the assignment, with Specify · Delegate · Verify, the provider and model of every run, and Assisted-by: trailers on AI-assisted commits.

Steps ​

  1. Finish the baseline if the Lab ended early, and commit it.

  2. Write the error analysis before you change anything: the analysis chooses the change, not the other way around.

  3. Pick the top-ranked category you can address with one change. Write the Verify line in AI_LOG.md: the case IDs you expect to flip, what must not get worse, the extra cost you'll accept.

  4. On a branch, make the change, then measure it in the way the table in Part 4 gives:

    bash
    git switch -c improve-[change]
# ...make the change...
npm run eval:record -- --recordings evals/recordings-[model]-[change] --out results/[model]-[change] --delay-ms 2500
# a deterministic repair needs no live calls:
npm run eval -- --recordings evals/recordings-[model] --out results/[model]-[change]

  5. Compare results/[model]-baseline/eval-report.json with results/[model]-[change]/eval-report.json using the Part 4 command, and fill in the table. With 30 cases, one flip is about 3 points: report the flips, not only the rates, and compare them with your noise floor if you measured one.

  6. Open the PR, review your own diff, decide, and update AI_LOG.md.

How it's graded ​

The 15-point assignment rubric (Rubrics: Assignment (15 points)), read for this week as:

  • Deliverables work (5): a live baseline with its recordings and calls.jsonl; an error analysis covering every failing case; the improvement PR with its own recordings and the shipped recordings untouched.
  • Verification (4): the Verify line written before the change; the change measured against your baseline on the same cases and model, with the per-case flips listed; cost and latency taken from the log; claims tagged observed or inferred. Exemplary work also measures the noise floor and says whether the improvement exceeds it.
  • Process record (3): AI_LOG.md with Specify · Delegate · Verify for the change and for any analysis script an agent wrote; provider and model logged for every run; small commits with Assisted-by: trailers.
  • Write-up (3): categories with counts, case IDs and examples; what the validator can and can't catch; a ranked "next" list; limitations stated (30 cases, one model, one run each, hand-written versus live).

Due before next week's Seminar (default 11:59 pm the night before). Next week's Seminar opens with a 7-minute quiz on this assignment.

NOTE

Minimum to keep up: your live baseline recorded into your own folder with its calls.jsonl; an error-analysis table that puts every failing case in a category with a count; and one change with a before-and-after list of flipped cases. Next week's eval report and CI gate build on exactly these files.
