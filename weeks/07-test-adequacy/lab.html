Week 7 — Lab and Assignment ​

In the Lab you run StrykerJS on roomly, measure three test suites on the same code, and triage the mutants none of them kill. In the assignment you raise one module's mutation score with tests whose every assertion you can justify, and compare an agent's batch with your own.

AI-use key: 🟢 AI on: any assistant or agent, under the Safe Loop · 🟡 AI limited: you write it; an AI may help, and you log that · 🔴 AI off: no assistant, no completions, no chat.

The oracle is still the Booking rules in roomly's README. A mutation score says how many plausible mistakes your tests would notice; only the rules say which behavior is right.

Before the Lab (15 min) ​

Work on your week 6 fixes branch in eswa-roomly (from week 6). StrykerJS first runs your tests without mutants and refuses to continue if any fail, so everything must be green:

bash
git switch fixes
node --version                          # must be 22.x; if not: nvm install 22 && nvm use 22 && npm install
npm test && FC_SEED=1 npm run test:properties
npx stryker --version
npm run mutate                          # the whole baseline, once: about a minute on a laptop, several on a 2-core Codespace

If a property still fails because you haven't fixed its bug, mark it test.skip with the issue number for now, and say so in your report. Then add a helper that lists the mutants no test killed, as rows for a triage table. Create scripts/survivors.mjs:

javascript
// Lists the mutants that no test killed, as rows for your triage table.
//   node scripts/survivors.mjs [report.json] > docs/triage.md
import fs from 'node:fs';

const report = JSON.parse(fs.readFileSync(process.argv[2] ?? 'reports/mutation/mutation.json', 'utf8'));
const code = (s) => '`` ' + String(s).trim().replace(/\s+/g, ' ').replace(/\|/g, '\\|').slice(0, 80) + ' ``';
console.log('| Where | Status | Mutator | Original line | Mutant | Decision | Reason |');
console.log('|---|---|---|---|---|---|---|');
for (const [file, { source, mutants }] of Object.entries(report.files)) {
  const lines = source.split('\n');
  for (const m of mutants.filter((m) => m.status === 'Survived' || m.status === 'NoCoverage')) {
    const { line, column } = m.location.start;
    console.log(`| ${file}:${line}:${column} | ${m.status} | ${m.mutatorName} | ${code(lines[line - 1])} | ${code(m.replacement)} | | |`);
  }
}

✅ Checkpoint: on fixes, Node 22, every test green, and a baseline report on disk.

Part 1 — Read a mutation report (10 min) ​

Core · 🔴 AI off for the reading

Mutation testing makes one small change to the code (a mutant), runs the tests, and repeats for every change it can think of. Run it on the smallest module with only its own shipped test file, so the report fits on a screen:

bash
npm run mutate -- --mutate src/time.js --testFiles tests/time.test.js --incrementalFile reports/inc-time.json

Read the table at the end. Then open the HTML report: python3 -m http.server 8080 -d reports/mutation, and open the forwarded port from the Ports tab (or download reports/mutation/mutation.html). Filter to Survived and click one: you see the diff, and which tests ran against it.

StatusMeansCounts toward the score as
KilledAt least one test failedDetected
TimeoutThe tests never finished (the mutant made a loop endless)Detected
SurvivedTests ran it, and all passedUndetected
NoCoverageNo test ran that code at allUndetected
RuntimeError, CompileErrorThe mutant broke the program before any test could judge itLeft out
IgnoredExcluded on purpose, for example by a // Stryker disable comment with a reasonLeft out

StrykerJS prints two scores: total = detected ÷ (detected + survived + no coverage), and covered = detected ÷ (detected + survived). Compute both by hand from your table and check them against the report.

The mutation operators you'll meet most often:

OperatorExample
ConditionalExpressionif (a < b) → if (true) or if (false)
EqualityOperator< → <=, === → !==
LogicalOperator|| → &&
ArithmeticOperator+ → -, * → /
BlockStatementa function or if body → {}
BooleanLiteraltrue → false, !x → x
StringLiteral'text' → ""

✅ Checkpoint: both scores computed by hand and matching the report, and one survivor whose diff you can explain in a sentence.

Part 2 — Three suites, one module (20 min) ​

Core · 🟢 AI on for the batch · 🔴 AI off for reading it

Use the rules section of src/bookingService.js, from limitsFor to the end of findConflicts, where Booking rules 1–8 are checked. If your week 6 properties were mostly about time.js, use src/time.js instead. Find your line numbers, since your fixes may have moved them:

bash
grep -n "^function limitsFor\|^function canManage" src/bookingService.js
RULES="src/bookingService.js:176-253"       # from limitsFor to the line before canManage
SHIPPED="tests/api.test.js,tests/bookingService.test.js,tests/roomService.test.js,tests/time.test.js"

1. Start the agent's batch first, so it works while you measure. In a fresh session, in plan mode:

text
Write unit tests with node:test for src/bookingService.js from limitsFor to the end of
findConflicts (checkRules, checkQuota, overlaps, findConflicts), in one new file,
tests/agent-rules.test.js. Use freshData() and user() from tests/helpers.js; never use
the real clock. StrykerJS will mutate exactly these lines: aim to kill its mutants.
Don't change any other file. Run node --test tests/agent-rules.test.js and show the result.

2. Measure the shipped tests and your properties on the same lines. Each run gets its own incremental file so earlier runs don't leak into its report, and FC_SEED makes the properties' kills repeatable:

bash
npm run mutate -- --mutate "$RULES" --testFiles "$SHIPPED" --incrementalFile reports/inc-shipped.json
cp reports/mutation/mutation.json reports/shipped.json
FC_SEED=1 npm run mutate -- --mutate "$RULES" --testFiles "tests/properties/*.test.js" --incrementalFile reports/inc-props.json
cp reports/mutation/mutation.json reports/props.json

3. Read the agent's file before you measure it. For each assertion, 🔴: what does it expect, and where did that expectation come from, a Booking rule or the code's current behavior? Count both. Then:

bash
npm run mutate -- --mutate "$RULES" --testFiles tests/agent-rules.test.js --incrementalFile reports/inc-agent.json
cp reports/mutation/mutation.json reports/agent.json
FC_SEED=1 npm run mutate -- --mutate "$RULES" --testFiles "$SHIPPED,tests/regression.test.js,tests/properties/*.test.js" --incrementalFile reports/inc-all.json
cp reports/mutation/mutation.json reports/all.json

4. Fill the comparison in docs/mutation.md, from what you observed:

SuiteKilledSurvivedNo coverageScore (total)Score (covered)Assertions from a rule / from the code
Shipped tests
Your week 6 properties
Agent batch
Shipped + regression + properties

✅ Checkpoint: the four rows filled from observed runs, and one sentence naming a mutant one suite killed that another didn't.

Part 3 — Triage the survivors (20 min) ​

Core · 🔴 AI off for every decision

bash
node scripts/survivors.mjs reports/all.json > docs/triage.md

A survivor is a question. Give each one you triage exactly one decision, with its evidence:

DecisionMeansEvidence
KillThe rules or the README's API section require a behavior that no test checksA new test, the rule it checks, and a rerun showing the mutant Killed
EquivalentNo input can tell the mutant from the originalAn argument: why every input gives the same observable result
Real bugThe mutant does what the rules require and the original doesn't: the mutant is the fixThe rule, quoted, and a bug report in the week 6 format
AcceptThe difference is observable but nothing promises it (the exact words of a message, say)Which contract is silent, and why a test for it would be testing the mutant

Questions that get you to a decision:

  1. What input would make the mutant behave differently from the original? If you can't find one, try to argue equivalence. Be careful with nearly equivalent mutants, which differ only on rare inputs: an exact boundary, a clock-change day, one role. Your week 6 generators exist for those.
  2. Can a client reach that input through the API, within the rules (opening hours, how far ahead)?
  3. If you wrote the test, what would it assert, and which rule says so?
  4. Does the mutant read more like the rule than the original does?
  5. For NoCoverage: which path never runs in any test? A whole branch with no coverage is often a missing test of an error case, or a route nobody calls.

Then kill one. Write a test in tests/adequacy-rules.test.js whose assertion you can justify from a rule, and rerun just that line:

bash
npm run mutate -- --mutate "src/bookingService.js:[line]-[line]" --testFiles "$SHIPPED,tests/adequacy-rules.test.js" --incrementalFile reports/inc-kill.json

✅ Checkpoint: three survivors in docs/triage.md with a decision and a reason each; at least one killed by your new test, shown in a rerun.

Part 4 — Mutation-guided generation (If time) ​

This is the reading's method in miniature. Give a fresh session one surviving mutant and its rule, and ask for a test that kills it:

text
This mutant of src/bookingService.js survives our tests:
[paste the original line and the mutant from docs/triage.md]
The Booking rule that governs this code: [quote it]
Write one node:test test, in tests/agent-mutant.test.js, that passes on the original code
and fails on the mutant, and say which words of the rule its assertion checks. If you
believe no such test exists, explain why instead of writing one.

Judge the result as you judged your own: does its assertion come from the rule, or does it test the mutant? Did it claim equivalence, and is the argument right?

Part 5 — Tests that agreed with bugs (If time) ​

Generate the same batch against the code as shipped, in a separate worktree, and see what it encodes:

bash
git worktree add ../roomly-shipped shipped
cd ../roomly-shipped && npm install

Run Part 2's agent prompt there and measure its score with Part 2's commands. Then copy its file into your fixes branch and run it with node --test. Every test that fails on your fixed code agreed with a bug on the shipped code, yet it raised the mutation score there. That's the ISSTA 2026 caveat, on your own code. Clean up with git worktree remove ../roomly-shipped.

Checkoff (15 min) ​

The checkoff is worth 5 points: complete, partial or missing (rubric). Show a staff member, on screen:

  1. A mutation report for your module from a run you made, with the command.
  2. Three survivors triaged in docs/triage.md, each with a decision and a reason; at least one killed by a new test, with the rerun showing it; any "real bug" with its rule quoted.
  3. The comparison table with at least the shipped tests and one other suite.

Staff then ask one question, such as "why is this one equivalent?", "what does this mutant do that the rule forbids?" or "which rule does your new assertion check?"

Next steps (5 min) ​

Commit docs/, scripts/survivors.mjs and your tests (not reports/, which git ignores). Choose your assignment module tonight, while the report is fresh.

Assignment — Raise a module's mutation score, honestly ​

Raise one module's mutation score with tests whose every assertion you can justify, account for every mutant that still survives, and compare an agent's batch with yours. About 3.5 hours.

Deliverables ​

On the fixes branch of eswa-roomly. Submit the repository URL and the tag week7 on Canvas (how to submit).

  1. One module: src/time.js, src/roomService.js, or one section of src/bookingService.js (the rules section from the Lab, or the operations from createBooking to the end of checkIn).
  2. Your tests, in tests/adequacy-[module].test.js (and properties in tests/properties/ if you like), each assertion with a comment naming the Booking rule or README API behavior it checks.
  3. An agent batch for the same module, tests/agent-[module].test.js, generated in a fresh session and committed exactly as generated (its own commit). You don't have to keep its failing tests in the suite: move them to a .skip and count them.
  4. docs/mutation.md:
    • Commands, exactly as run, with the seed; scores before (shipped tests plus your week 6 work) and after, both total and covered, with the counts.
    • Every mutant that still survives or has no coverage in your module, triaged with the Lab's four decisions (you may group mutants that share one reason). Equivalent ones argued. Any // Stryker disable next-line [mutator]: [reason] listed, with the score both with and without the ignores.
    • The comparison: the agent's batch and yours on the module, alone and combined; for each, how many assertions come from a rule, from the code's current behavior, or are wrong by the rules; what each killed that the other didn't; the time each cost you, including review.
    • The caveat, applied (🔴 AI off, one paragraph): does your higher score mean this module has fewer bugs? What evidence would show that?
  5. Real bugs found through survivors: reported and fixed as in week 6 (regression test, red, then the fix).
  6. AI_LOG.md: the agent batch session and your own sessions.

IMPORTANT

What doesn't count. Tests without assertions (they kill crashes, not wrong answers). Tests that assert a detail only because the mutant changes it, unless you argue that the detail is part of the API's contract. Changes to src/ to make mutants easier to kill (a real bug fix is a separate, reported commit). Narrowing mutate, deleting tests, or disabling mutants without a written reason. Graders rerun your commands.

Steps ​

  1. Run the before measurement for your module with every test you have, and save the report (cp reports/mutation/mutation.json reports/before.json).
  2. Generate the agent batch in a fresh session, as in Part 2 but for your module; commit it untouched; measure it alone.
  3. Triage the survivors from the before report (🔴 AI off). Work through them in order: NoCoverage first (whole untested paths), then survivors whose input is easy to reach.
  4. For each test you add: write the assertion from the rule, run it, see it pass on the code, and check that it kills what you meant it to kill by rerunning that line range. If a rule-based test fails on the code, you've found a bug: report it, and fix it test first.
  5. Run the after measurement with the same command and seed. Fill in docs/mutation.md.
  6. Commit, tag week7, push.

How it's graded ​

The 15-point assignment rubric (Rubrics: Assignment (15 points)), read for this week as:

  • Deliverables work (5): the module's score is raised by tests that run under npm test or npm run test:properties; the agent batch is committed and measured; docs/mutation.md is complete.
  • Verification (4): before and after scores from commands a grader can rerun with the same seed; every new assertion cites a rule; every remaining survivor triaged; equivalent mutants argued; nothing from the "doesn't count" list.
  • Process record (3): AI_LOG.md with the agent batch session and your own; small commits with Assisted-by: trailers.
  • Write-up (3): the comparison and the caveat paragraph, with every point located (mutants by file:line:column, tests by name).

Due before next week's Seminar (default 11:59 pm the night before). Next week's Seminar opens with a 7-minute quiz on this assignment.

NOTE

Minimum to keep up: one module; at least ten more mutants killed by justified tests; before and after scores with the command; every remaining survivor triaged in one line each; the agent batch's score next to yours. Next week's refactor of the god module uses your tests and this mutation score to show that behavior didn't change. Bring a green suite.

Troubleshooting ​

  • "Something went wrong in the initial test run": a test fails with no mutants at all. Run npm test and the properties; skip a known failure with its issue number.
  • The report lists files you didn't mutate: results from earlier runs carried over by incremental mode. Use a separate --incrementalFile per measurement, as above, and read only your module's row.
  • Scores change between identical runs: random properties. Set FC_SEED; raise numRuns on properties that only sometimes kill a mutant, or bias their generators.
  • It's slow: mutate a line range; skip the full project run after the baseline. Timeouts count as detected and usually come from server.js.
  • The HTML report won't open in a Codespace: serve it with python3 -m http.server 8080 -d reports/mutation, or download the file.
