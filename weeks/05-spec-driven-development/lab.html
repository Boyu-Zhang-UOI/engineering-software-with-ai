Week 5 — Lab and Assignment ​

In the Lab you turn a vague feature request into a specification a fresh agent session can't misread, then build its first task with an agent, test first, one approved step at a time. In the assignment you finish the feature, and halfway through, the request changes.

AI-use key: 🟢 AI on: any assistant or agent, under the Safe Loop · 🟡 AI limited: you write it; an AI may critique it, and you log that · 🔴 AI off: no assistant, no completions, no chat.

Rules for agents this week (safety contract): work in a Codespace; approvals stay on; no --yes or autopilot modes; commit before and after every agent task (rule 7). roomly is a course kit, so free tiers are fine for it (the data rule).

Before the Lab (15 min) ​

  1. Create your repository from the kit. Open the eswa-roomly template (link on Canvas) → Use this template → Create a new repository, public, in your own account, named eswa-roomly. Or copy its files into a new repository of your own:

    bash
    git clone --depth 1 https://github.com/Boyu-Zhang-UOI/eswa-roomly.git eswa-roomly
cd eswa-roomly && rm -rf .git && git init -b main && git add . && git commit -m "Start from the roomly kit"

    Then publish it to GitHub (VS Code's Publish to GitHub, or gh repo create). You'll use this repository in weeks 5–10 and 13.

  2. Tag the code as shipped, before you change anything. Weeks 6, 7 and 9 start from this tag:

    bash
    git tag shipped && git push origin shipped

  3. Create a codespace on the repository and check the kit:

    bash
    node --version   # 22.x (20.12 or later works this week)
npm test         # 29 tests pass; no packages needed

  4. Add the course templates to your repository:

    bash
    mkdir -p docs/recurring
base=https://boyu-zhang-uoi.github.io/engineering-software-with-ai/templates
for f in SPEC DESIGN TASKS; do curl -fsSL "$base/$f.md" -o "docs/recurring/$f.md"; done
curl -fsSL "$base/AI_LOG.md" -o AI_LOG.md
git add docs AI_LOG.md && git commit -m "Add spec, design, task and AI log templates"

  5. Read README.md: the API table, the Booking rules (the specification), and the code tour. Ten minutes, 🔴 AI off. You'll quote the rules today.

Setup check (5 min) ​

bash
git tag --list shipped        # prints: shipped
npm test                      # 29 pass
ls docs/recurring AI_LOG.md   # the three templates and the log

Open your CLI agent from Tool Handout: Tools by week (the week 5 row) in the codespace and confirm it starts in its plan or read-only mode. If it has none, you'll use the plan-first prompt in Part 5.

✅ Checkpoint: the shipped tag exists, 29 tests pass, and your agent starts with approvals on.

Part 1 — The request and the rules (5 min) ​

Core · 🔴 AI off

This is the request, beat 1 of the feature. Paste it into SPEC.md §1 as the source.

From: the Clearwater Hall facilities office · Subject: repeating bookings

Study groups, TAs and clubs book the same room at the same time every week, one booking at a time, and they often lose the slot to someone who books first. Please let Roomly take a repeating booking: one request that books the same room, at the same building-local start and end time, on the same weekday, for a number of weeks in a row. Every booking in a series must follow the same Booking rules as any single booking. People need to see which bookings belong to a series, and to cancel a whole series in one go. The lobby screen and room availability should show each occurrence like any other booking. Today a request with a recurrence field gets 501 Not Implemented; that should go away.

Then find out what's there now. Tag each finding observed (you ran or read it, with the file and line) or inferred (observed and inferred):

bash
grep -n "recurrence" -r src tests README.md

Answer three questions in SPEC.md §2 (Context): where does the 501 come from; which shipped test pins that behavior, and what shape of recurrence does it send; and which of the twelve Booking rules will a series interact with (read rules 3 and 8 twice).

✅ Checkpoint: §2 names the line that returns 501, the test that expects it, and at least three Booking rules a series must respect, each tagged observed.

Part 2 — Write SPEC.md v1 (15 min) ​

Core · 🟡 AI limited: you write the criteria; no AI drafts them.

Fill docs/recurring/SPEC.md from the template: the problem (§1), the context (§2), and above all the acceptance criteria (§3) in EARS form, each with a priority and a "Verified by" entry naming the test that will check it.

A criterion is testable when it names a trigger and a response you can observe through the API or a function's return value. Here is the move, on an existing rule rather than on your feature. Booking rule 10 says the organizer checks in "from 10 minutes before the start to 15 minutes after it":

VagueTestable
Check-in works around the start time.WHEN the organizer checks in to a booking in a room that requires check-in, at any time from 10 minutes before its start to 15 minutes after it, inclusive, THE SYSTEM SHALL record the check-in time and respond 200.
IF anyone other than the organizer checks in, THEN THE SYSTEM SHALL respond 403 and leave the booking unchanged.

Writing the testable version forced two decisions the rule left open: whether the window's ends are inclusive, and what happens to someone else. That's the point. For recurring bookings, decide and write down at least these:

  • The request. What does a client send (a count of weeks, an end date, or either), and what does it get back? Put one example request and response in §6 (Interfaces).
  • Partial failure. One occurrence breaks a rule or clashes with an existing booking. Is nothing booked, or everything else? What does the response say, and in which of the codebase's error shapes?
  • The rules, per occurrence. "Every booking in a series must follow the same Booking rules." Work out what rules 3 (how far ahead) and 8 (quota) then mean for a student's six-week series, and write the consequence as a criterion.
  • Time. "The same building-local start and end time" on every occurrence, on every date (rule 11). Give dates and times in the criterion.
  • Cancelling. What "cancel a whole series" does to occurrences that are in the past, in progress, or already checked in.
  • Limits. The smallest and largest series you accept.
  • What stays the same. Single bookings, their IDs and every existing route behave as before.

Add at least two properties in §4 (invariants for all series, such as "no two occurrences of one series overlap"); you'll test properties next week. Fill §5 (out of scope) with at least three things this feature won't do. Anything the request and the rules don't settle goes in §9 (open questions) as Assumed: [decision], because [reason]. Post real questions for the facilities office in the Canvas discussion Roomly: questions for facilities; staff answer there, and in the Lab, until the end of day 2 of the assignment.

✅ Checkpoint: at least eight criteria, every one in an EARS pattern with a "Verified by" entry; at least three of them edge cases; two properties; three out-of-scope items.

Part 3 — The Goldfish test and an approval (10 min) ​

Core · 🟢 AI on (the critique) · 🔴 AI off (your fixes)

  1. Commit the spec. Start a fresh agent session (no memory of your work) and run the Goldfish test: give it only SPEC.md.

    text
    You have only the document below, and no other context about this project.
1. In five sentences, say what you would build.
2. List every question you would need answered before starting.
3. List every assumption you would have to make to start without asking.
4. Name every acceptance criterion that a test could not check as written, and why.
Do not write any code.

[paste docs/recurring/SPEC.md]

  2. Every question and every wrong assumption is a defect in the document. Fix the document, not the session: add a criterion, an out-of-scope line or an Assumed: line. Don't answer the agent in the chat. Log the run in the Experiments table of AI_LOG.md (how many questions, how many you fixed).

  3. Approval. Swap specs with a neighbor. They check, 🔴 AI off: can they name a test for every criterion; are the three edge cases real; does anything in the spec describe how instead of what (that belongs in DESIGN.md)? When it passes, set Status to agreed and fill in Approved by in the header with their GitHub username and the date (a username, not a real name: the repository is public). Then commit.

✅ Checkpoint: a Goldfish run logged, its findings fixed in the document, and SPEC.md committed as agreed with a classmate's approval.

Part 4 — One decision and the first task (5 min) ​

Core · 🟡 AI limited

In DESIGN.md §3, record D1, the decision everything else depends on: how a series is stored (one booking per occurrence, linked by a series ID; a rule expanded when read; or both), with the options and your reason. Then write T1 in TASKS.md, the smallest task that moves the feature forward and can be tested on its own. A good T1 is a pure function in a new module, with no wiring yet: for example, expanding a series request into the list of occurrence start and end instants. Fill in every line of the template: criteria, Specify, Delegate (agent, mode, files in scope, commands allowed, step limit), Keep for myself, Verify, branch.

✅ Checkpoint: D1 with at least two options considered; T1 with a Specify · Delegate · Verify line and no more than three files in scope.

Part 5 — Build T1 in small verified steps (15 min) ​

Core · 🟢 AI on, under the Safe Loop

  1. Branch. git switch -c t1-[short-name].

  2. Check first. Write T1's test yourself, from its criteria and the function's signature only (check first): at least one ordinary case and one edge case from your spec. Run it and watch it fail (node --test tests/[your-file].test.js; failing because the module doesn't exist yet is fine). Commit it: the history now shows the test came first.

  3. Plan. In plan mode, or with this prompt:

    text
    Task T1 from docs/recurring/TASKS.md is below, with the acceptance criteria it covers.
Don't edit anything yet. Read what you need, then propose a plan: the files you will
create or change (only the ones the task lists), the steps in order, and how each step
will be checked. The test [tests/your-file.test.js] already exists and fails; do not
change it. Follow the code tour in README.md: new date code uses src/time.js.
List anything in the task you find ambiguous. Wait for my approval.

[paste the T1 entry and its criteria]

  4. Edit the plan. Delete any step that touches a file outside the task, refactors code "while it's there", or edits the test. If the agent found an ambiguity, fix SPEC.md or TASKS.md first.

  5. Step, test, read. Approve one step at a time. After each: run the test and npm test, read the whole diff, and keep only what you can explain. If the agent tries to change your test, refuse.

  6. Commit and merge. Commit with a message that says what changed and an Assisted-by: [tool and model] trailer (convention). Merge into main (git switch main && git merge --no-ff t1-[short-name], or a pull request in your repository) and push.

  7. Log it. One AI_LOG.md session entry: Specify, Delegated, Kept for myself, Verified and how (observed: the command and its output), What went wrong.

✅ Checkpoint: on main, T1's test passes, npm test passes, the test's commit comes before the code's, and the log entry exists.

Part 6 — The one-shot comparison (If time) ​

In another fresh session, give the agent only the facilities office's request, not your spec, and ask for a plan. Compare it with your spec: list three decisions it made silently (partial failure, time zones, cancelling) and whether each matches yours. Add the count to your Experiments table. This is the Seminar's demo, done on your own spec.

Checkoff (15 min) ​

The checkoff is worth 5 points: complete, partial or missing (rubric). Show a staff member, on screen:

  1. SPEC.md, approved: status agreed, with a classmate's GitHub username under Approved by; every criterion in EARS form with a "Verified by" entry a test could satisfy; at least three edge cases; an out-of-scope list; the Goldfish run logged and its findings fixed in the document.
  2. T1, merged with a test: on main, the test that you saw fail (its commit comes first) now passes, and so does npm test; an AI_LOG.md entry; the Assisted-by: trailer.

Staff then ask one question, such as "which criterion does your T1 test check, and what did the test do before the code existed?" or "which of your criteria did the Goldfish test change?"

Next steps (5 min) ​

Push everything. Read the assignment below and plan your days: beat 2 arrives on day 3. Your team's M0 proposal is due at the same time, and the three documents you wrote today are a rehearsal for course/SPEC.md, course/DESIGN.md and course/TASKS.md.

Assignment — Recurring bookings in two beats ​

Finish recurring bookings to your spec, then absorb a change to the spec without losing track of what changed. About 3.5 hours.

Deliverables ​

Everything goes in your eswa-roomly repository, on main. Submit the repository URL and the commit or tag to grade (week5) on Canvas (how to submit).

  1. The three documents, in two versions. docs/recurring/SPEC.md, DESIGN.md and TASKS.md as they stood when beat 1 was done, tagged beat-1, and updated for beat 2 on main. DESIGN.md records at least three decisions (D1 storage, plus at least partial failure and the API shape); TASKS.md lists every task you built, each with its Specify · Delegate · Verify line and status.
  2. The feature. Every MUST criterion of the beat-2 spec works and is verified by a test that npm test runs. The README's Booking rule 12 and API table describe the feature as built.
  3. docs/recurring/REPORT.md: a status table (each criterion: met, partial or not met, with the test that shows it), then the beat 2 note (🔴 AI off, 300–500 words): what changed; what it broke, located (test names, commits, design decisions, code that moved); what in v1 made the change easier or harder; one thing you'd specify differently next time.
  4. AI_LOG.md: a session entry per task, and your Goldfish runs in the Experiments table.

Steps ​

Beat 1 (days 1–2).

  1. Finish DESIGN.md before more code: the decisions, the seams where the feature plugs in (createBooking is the god module's main path; a new module is a seam), the risky areas you noticed (two sets of date helpers; three error styles), and the test strategy. Then split the rest into tasks in TASKS.md. Each task is one session and one diff you can review in one sitting (small tasks).
  2. Build each task as in Part 5: branch, test first and seen failing, plan, one step at a time, read the diff, commit with a trailer, merge, log.
  3. The shipped test recurring bookings are not supported yet pins the old 501 behavior and must change. That is a spec change, not a weakened test: replace it with a test of your new criterion, and say so in the commit message.
  4. Freeze the clock in every test (freshData() in tests/helpers.js sets it to Monday 5 October 2026, 08:00 in the building; setNow() moves it). A test that depends on today's date will fail next week.
  5. When beat 1 is done, or at the end of day 2, whichever comes first: git tag beat-1 && git push origin beat-1.

Beat 2 (day 3 onward). Read beat 2 when it's posted on Canvas (below), then work in this order: spec, design, tasks, tests, code.

  1. Spec. Add a dated row to SPEC.md §8 (Spec changes). Keep criterion IDs stable: change a criterion in place and note it, add new IDs, and mark a dropped criterion ✗ with the reason rather than deleting it. Set the status to changed in beat 2. Run the Goldfish test again on the changed spec.
  2. Design. Revisit each decision whose "Revisit if" the beat triggers, and record whether it held.
  3. Tasks. Add the new tasks; mark tasks that the change undid.
  4. Tests, then code. Update or add the tests first and run them: what fails now is your record of what the change broke. Save that output for the note (npm test 2>&1 | tee docs/recurring/beat2-red.txt). Then change the code until they pass.
  5. Write REPORT.md, update AI_LOG.md, tag week5, push, and submit.

git diff beat-1 -- docs tests shows exactly what beat 2 changed; graders read it, and so should you before writing the note.

Beat 2 ​

Beat 2 is a second message from the facilities office, posted on Canvas on day 3 of the assignment; it isn't on this page, so build beat 1 to the request you have. When it arrives, check that beat-1 is tagged and pushed, then work in the order above: spec, design, tasks, tests, code. Questions about it go to the same Canvas discussion.

How it's graded ​

The 15-point assignment rubric (Rubrics: Assignment (15 points)), read for this week as:

  • Deliverables work (5): the feature meets every MUST criterion of the beat-2 spec, shown by npm test; the README describes it; the three documents are complete and agree with the code.
  • Verification (4): every criterion's "Verified by" names a test that exists and passes; each task's test came before its code (visible in the history or the log); the time-zone and partial-failure criteria are tested; any changed shipped test is justified; claims tagged observed or inferred.
  • Process record (3): an AI_LOG.md entry per task with Specify · Delegate · Verify and what your checks caught; the Goldfish runs logged; small commits with Assisted-by: trailers; the beat-1 tag.
  • Write-up (3): the beat 2 note: a dated §8 row; what broke, located by test name, commit or decision; what you'd specify differently.

Due before next week's Seminar (default 11:59 pm the night before). Next week's Seminar opens with a 7-minute quiz on this assignment.

NOTE

Minimum to keep up: an approved SPEC.md tagged at beat-1; T1 and one more task merged with tests; beat 2 recorded in §8 with its changed criteria, and at least one of its changes implemented and tested; the beat 2 note. Week 6 starts from the shipped tag, not from this feature, so an unfinished feature won't block next week's lab. Your team's M0 is due at the same time.

Troubleshooting ​

  • A test passes on Monday and fails on Friday: it reads the real clock. Use freshData() or setNow(); set ROOMLY_NOW for manual runs with npm start.
  • A student's series is refused for being too far ahead: that may be your spec working (rule 3). For a series that crosses a daylight-saving change, test as a staff user (u-dana, 90 days ahead) or move the clock with setNow().
  • The agent wants to edit a test, the README, or a file outside the task: refuse, and add the boundary to the task's "Files in scope". Two failed attempts at the same step: stop, start a fresh session, rewrite the task (two strikes).
  • EADDRINUSE from npm start: another server is running; PORT=3001 npm start.
  • The agent is out of allowance mid-task: switch to a fallback in Tool Handout: Spreading the work across free allowances and note the switch in AI_LOG.md: a different model is a different result.
