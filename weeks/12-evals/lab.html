Week 12 Lab and Assignment ​

Lab — Calibrate the judge, then gate CI (75 min) ​

Field accuracy works for fields with one right answer. The booking title has no single right answer, so the kit grades it with a second model call: an LLM judge that answers pass or fail against a three-point rubric. A judge is a measuring instrument. Today you build the reference it is measured against (your own labels, made blind), measure it with percent agreement and Cohen's κ next to a "judge" that always says pass, and then turn the eval into a CI gate that runs on recorded responses with no key, no network and no cost.

Work in your eswa-eval-harness repository from week 11.

NOTE

🔴 AI off for your labels. They are the reference the judge is measured against; a model's opinion in them would measure the judge against itself. 🟢 AI on for scripts and the CI workflow, under the Safe Loop and logged.

Before the Lab: push your week 11 work and make sure npm test passes on main. Know which recordings match the prompt on main: the shipped ones in evals/recordings/ if you didn't merge a prompt change, your own folder if you did. Don't run npm run calibrate or npm run eval:judge before Part 1: they print the judge's verdicts, and your labels must not see them.

Setup check (5 min) — Core ​

bash
git switch main && git pull
npm test                               # passes
npm run eval                           # the 30 shipped cases replay (see the note below if they don't)

NOTE

If you merged a prompt change in week 11, the shipped titles no longer replay on main. Do Parts 1 and 2 in a worktree of your repository's first commit, which is the kit as shipped, and copy your labels back:

bash
git worktree add ../eh-shipped $(git rev-list --max-parents=0 HEAD)
cd ../eh-shipped        # label and calibrate here; then copy evals/labels-[you].jsonl back to your repository

✅ Checkpoint: tests pass, and you know which folder of recordings your main replays.

Part 1 — Label the titles, blind (15 min) — Core, 🔴 AI off ​

Read the rubric first: JUDGE_PROMPT in src/judge.js. A title passes when it is based only on what the request says, specific enough to recognize on a calendar (and at most 60 characters), and plain text. Then label all 29 shipped titles:

bash
npm run label -- --labels evals/labels-[you].jsonl

For each request and title, type p (pass), f (fail), s (skip) or q (quit and save; run it again to continue). Write a one-line note for every fail naming the criterion it breaks; notes are what make disagreements readable later. Apply the rubric as written, not your taste in titles. If a case makes you want to change the rubric, write that down separately: it's a finding for your report, not a reason to bend a label.

When you finish, count your own pass rate. You'll need it to interpret everything in Part 2.

✅ Checkpoint: evals/labels-[you].jsonl holds your labels, every fail has a note, and you have not seen the judge's verdicts.

Part 2 — Calibrate (15 min) — Core ​

Now compare the judge with your labels:

bash
npm run calibrate -- --labels evals/labels-[you].jsonl

Read every line: how many titles were compared; your pass rate and the judge's; the confusion matrix; percent agreement and κ for the judge, for an always-pass "judge" and for an always-fail one; how many of your fails the judge caught (fail recall) and how often its fails were right (fail precision); and the disagreements, with both reasons.

Check κ by hand once, from the confusion matrix: observed agreement p_o is the diagonal over n; chance agreement p_e = (judge's pass rate × your pass rate) + (judge's fail rate × your fail rate); κ = (p_o − p_e) / (1 − p_e). Your number should match the script's.

Two more comparisons. The judge against the course staff's labels, and you against the course staff (a human–human κ, roughly the ceiling any judge could reach on this rubric):

bash
npm run calibrate                 # the judge vs evals/human-labels.jsonl (course staff)
node --input-type=module -e '
import { readJsonl } from "./src/evaluate.js";
import { cohensKappa } from "./src/metrics.js";
const [mineFile, otherFile] = process.argv.slice(1);
const other = new Map(readJsonl(otherFile).map((l) => [l.id, l]));
const pairs = readJsonl(mineFile)
  .filter((l) => other.get(l.id)?.title === l.title)
  .map((l) => ({ a: l.label, b: other.get(l.id).label }));
const k = cohensKappa(pairs);
console.log(`n=${k.n}  agreement=${(k.agreement * 100).toFixed(1)}%  kappa=${k.kappa?.toFixed(3)}`);
' evals/labels-[you].jsonl evals/human-labels.jsonl

Read the disagreements. For each one, decide who is right by the rubric, you or the judge, and why. Then group them: is there a pattern in what the judge lets through, or flags wrongly? A pattern is something you can fix in a judge prompt; a scatter of one-offs probably isn't.

Write CALIBRATION.md in your repository:

ComparisonnAgreementκ
Judge vs your labels
Always pass vs your labels
Judge vs course staff
You vs course staff

Below the table: the confusion matrix against your labels; fail recall and fail precision; your pass rate and the judge's; the disagreement patterns, with case IDs; and two sentences on uncertainty (how many items, how many labelers, and what that does to a κ).

✅ Checkpoint (checkoff): CALIBRATION.md with percent agreement and κ for the judge and for the always-pass baseline, against your own labels, and you can say why the two numbers tell different stories.

Part 3 — A CI gate on recorded responses (20 min) — Core ​

The kit's docs/ci-example.yml runs the unit tests and npm run eval:check (replay, with the judge, then compare each metric with evals/thresholds.json) on every push and pull request. Read it first: no secrets, no key, no model calls.

1. Install it.

bash
mkdir -p .github/workflows
cp docs/ci-example.yml .github/workflows/evals.yml

If your main replays your own recordings, not the shipped ones, change the gate's step to npm run eval:check -- --recordings evals/recordings-[name].

2. Set the thresholds from a run you trust. The shipped evals/thresholds.json was set a little below the shipped recordings' values. Run npm run eval:check on the recordings CI will replay, and set each minimum from that run, with a margin you can defend. For each threshold, write one line in CALIBRATION.md (it moves into your eval report later): its value, the run it came from, and the answer to what change would make this number go up, and would that change make the feature better?

3. Push and watch it pass.

bash
git add .github/workflows/evals.yml evals/thresholds.json CALIBRATION.md evals/labels-[you].jsonl
git commit -m "Add an eval gate on recorded responses"
git push
gh run watch                     # or open the Actions tab

4. Prove it can fail. On a branch, make a plausible-looking change to code that runs after the model call, so it changes no request and replay still works. For example, in extractBooking(), default a missing attendee count to 1 before returning a valid answer. Then:

bash
npm test                         # does it still pass?
npm run eval:check               # and this?
git push -u origin [branch]      # open a PR and watch its check

Read the PR's check: the summary page shows which metric failed and by how much. Close the PR without merging. Then answer: why did the unit tests miss it? And what kind of red would a prompt change have produced instead? (You saw one in week 11: replay stops outright, and the log says why.)

✅ Checkpoint: the gate is green on main, red on your PR with a FAIL line, and you can name the metric that caught the change.

If time ​

  • An interval for κ. With 29 pairs, κ moves a lot if two labels change. Have an agent write scripts/kappa-interval.mjs, which resamples your (judge, you) pairs with replacement 2,000 times and prints a 95% interval for κ. Specify the check first: on pairs that all agree, every resample gives κ = 1 (or undefined when every label is the same).
  • Start the judge-only script from the assignment, and run its differential check.
  • Contamination: are any of the shipped or your planned cases copied from a public example a model may have seen? How would you know? (Case D4 has a probe you could adapt.)

Checkoff ​

Staff confirm, at the end of the Lab:

  1. Your labels, made before you saw any judge verdict (say how you kept them blind), with a note on every fail.
  2. CALIBRATION.md with n, the confusion matrix, and percent agreement and κ for the judge and for the always-pass baseline against your labels, plus the comparisons with the course staff's labels.
  3. A question, for example: "Why is κ so much lower than agreement for this judge?", or "What would an always-pass judge's agreement be if you had passed every title but one?"

The CI gate (Part 3) is part of the assignment; if it's done, staff look at it too.

Troubleshooting ​

  • npm run label shows nothing: every title already has your label (it resumes), or the replay failed: read the error, and see the setup note about prompt changes.
  • "Stale labels skipped": the title you labeled is no longer the one being judged (the recording changed). Relabel those cases.
  • κ prints undefined: both raters gave one label to everything, so chance agreement is 1. Not a bug; say so in the report.
  • The workflow doesn't run: check that the file is in .github/workflows/ on the branch you pushed, and that Actions is enabled in the repository's settings. Private repositories spend minutes; public ones don't (troubleshooting).
  • The PR stays green when you expected red: your change altered nothing CI replays, or a threshold is too low to fail. Both are findings about your gate.
  • ReplayMissError in CI: the prompt on that branch doesn't match the recordings CI replays. Record again, or point the step at the matching folder.

Assignment — An eval report ​

Write the eval report for the booking extractor in EVAL_PLAN.md (template), backed by an extended eval set, a judge you have measured, and the gate you built in the Lab. If your team's M2 contribution uses an LLM, this is the method your course/EVAL_PLAN.md follows.

Deliverables ​

In your eswa-eval-harness repository:

  1. EVAL_PLAN.md, every section filled in and located (files, case IDs, commands):

    • §1–2: what the feature must do, and its failure modes with their frequencies in your week 11 baseline.
    • §3 Dataset: the 30 shipped cases plus at least 10 new ones (deliverable 2); a dev set and a held-out set; who labeled what; a contamination check.
    • §4 Metrics: what you measure and why, each with a target and a reason; a 95% interval for case accuracy (bootstrap, below, or Miller's formula); the week 11 baseline and change compared case by case.
    • §5 Judge: your labels; agreement, κ, the always-pass baseline, n, fail recall and precision; the human–human κ; a decision rule ("the judge's verdict gates CI only if κ ≥ [value] on held-out labels"); and one judge change with its effect on κ on labels it wasn't tuned on (deliverable 3).
    • §6 Regression gate: which recordings CI replays; every threshold with its value, source run and margin; how recordings get refreshed (as their own reviewed PR); and what the gate catches and what it misses, at least two of each, with your failing PR as evidence for one "catches".
    • §7–8: the results table across versions, and what the eval does not measure.

  2. At least 10 new cases in evals/cases-extra.jsonl, same format as evals/cases.jsonl (leave that file alone: a test counts its 30 cases). Give each an ID that can't collide with c01–c30 (recordings are stored per case ID), a tag naming the failure mode or edge it probes, and a notes line justifying its expected values. Expected values are yours (🟡: an AI may suggest inputs, never answers). Spot-check: a classmate writes the expected values for three of your cases without seeing yours; report the disagreements and fix the cases they reveal as ambiguous. Record them with your model, into your own folder whose recordings match the prompt you're evaluating (never evals/recordings/):

    bash
    npm run eval:record -- --cases evals/cases-extra.jsonl --recordings evals/recordings-[name] --out results/[name]-extra --delay-ms 2500

  3. One judge change, measured. Change JUDGE_PROMPT to address a disagreement pattern from Part 2, tuning it on your dev labels only, then measure κ on your held-out labels. The simplest split is the shipped titles by case number (odd for dev, even for held-out); stronger is to use the shipped titles as dev and your own model's titles from evals/recordings-[model] as held-out, labeled blind. Do this on a branch: a new judge prompt changes every judge request, so the shipped judge recordings stop matching, and merging needs judge recordings made with the new prompt.

    Measuring it needs live judge calls on the same titles, so the extractions must replay while the judge runs live. Write scripts/judge-only.mjs (🟢 a good task to delegate, with this spec):

    • Specify: replay extraction calls from --extract (default evals/recordings); send judge calls to a recording client (--record) or a replay client on --judge-dir; run runEval with the judge; print calibrate() against --labels; accept --only; load .env only in record mode (loadEnv() in scripts/common.mjs). The core is one client that routes by purpose:

      js
      const client = {
  source: args.record ? 'record' : 'replay',
  complete: (request, meta) => (meta.purpose === 'judge' ? judgeClient : extractClient).complete(request, meta),
};

    • Verify before you trust it: with --judge-dir evals/recordings and no --record, it must print exactly what npm run calibrate -- --labels [the same file] prints. Write that check in AI_LOG.md before you run it.

    No live access this week? Propose the change from the disagreement pattern, predict its effect, and mark it unmeasured.

  4. The gate from the Lab: green on main, the failing PR linked, thresholds justified.

  5. AI_LOG.md entries with Specify · Delegate · Verify for the script and the judge change, and Assisted-by: trailers.

A 95% interval for case accuracy, by bootstrap over the cases of one report:

bash
node -e '
const results = JSON.parse(require("fs").readFileSync(process.argv[1], "utf8")).results;
const n = results.length, B = 2000, rates = [];
for (let b = 0; b < B; b++) {
  let pass = 0;
  for (let i = 0; i < n; i++) if (results[Math.floor(Math.random() * n)].pass) pass++;
  rates.push(pass / n);
}
rates.sort((x, y) => x - y);
const observed = results.filter((r) => r.pass).length / n;
console.log(`case accuracy ${observed.toFixed(3)} (n=${n}), 95% bootstrap interval ${rates[Math.floor(0.025 * B)].toFixed(3)} to ${rates[Math.floor(0.975 * B)].toFixed(3)}`);
' results/[model]-baseline/eval-report.json

Steps ​

  1. Draft §1–2 from your week 11 error analysis, then write the new cases aimed at its categories and at edges the 30 cases miss. Get the spot-check done early.
  2. Record the new cases; run npm run eval -- --cases evals/cases-extra.jsonl --recordings evals/recordings-[name] and add them to §3 and §7.
  3. Split your labels into dev and held-out, write the Verify line for the judge change (the κ you expect on held-out, and what must not get worse), build and check judge-only.mjs, then tune on dev and measure once on held-out.
  4. Compute the interval and fill in §4. Justify every threshold in §6 from a run.
  5. Write §6's "catches" and "misses" with evidence, and §8.

How it's graded ​

The 15-point assignment rubric (Rubrics: Assignment (15 points)), read for this week as:

  • Deliverables work (5): EVAL_PLAN.md complete; at least 10 new cases recorded; the gate green on main with a failing PR shown; the judge change measured (or, with no live access, proposed and marked unmeasured).
  • Verification (4): κ reported next to agreement, the always-pass baseline and n, on labels made blind; the judge change measured on held-out labels it wasn't tuned on; a 95% interval on the headline metric; the judge-only script checked against npm run calibrate; claims tagged observed or inferred.
  • Process record (3): AI_LOG.md with Specify · Delegate · Verify for the script, the cases and the judge change, Verify lines written first; small commits with Assisted-by: trailers.
  • Write-up (3): what you measure and why; thresholds justified from a run, with what would raise each; what the gate catches and misses, with evidence; honest limits (29 labels, one labeler, hand-written data, a gate that only sees recordings).

Due before next week's Seminar (default 11:59 pm the night before). Next week's Seminar opens with a 7-minute quiz on this assignment. M2 and peer evaluation 2 are due at the same time (milestones).

NOTE

Minimum to keep up: your blind labels; CALIBRATION.md with agreement and κ for the judge and the always-pass baseline; the CI gate green on main and one PR where it fails; and EVAL_PLAN.md §3–§6 filled in, with at least five new cases. Your team's M2 needs the same pieces if its contribution calls an LLM.
