Week 2 — Inside Real Agents ​

A production agent runs the same loop as yours inside a much larger harness, and the way to learn a large codebase, including that harness, is to let an agent map it and then verify every claim the map makes.

Learning objectives ​

By the end of this week you can:

  1. Name the parts of a production harness (system prompt assembly, tool schemas, context management, subagents, permission modes, sandboxing) and match each to its counterpart in mini-agent, if it has one.
  2. Explain why a sandbox needs both filesystem and network isolation, and which one a Codespace lacks.
  3. Build an unfamiliar codebase from its README and run its tests, recording every step that the README got wrong.
  4. Map a large codebase with an agent, then verify the map's claims by reading, running and deliberately breaking code.
  5. Find the risky areas of a codebase from evidence (history, tests, what the code enforces), not impressions.

Seminar ​

The 7-minute quiz on your week 1 work (quizzes); a production harness opened part by part beside mini-agent; a method for reading a codebase too big to hold in your head; a debate on whether approval prompts are a security boundary; a demo that catches an agent's map being wrong; and the new teams. Slides.

Lab ​

Build the codebase your team will work in from its README alone, run its tests, have an agent map it with a citation for every claim, and check the claims yourself. The assignment turns this into your onboarding report, the basis of your team's M0 proposal. Lab and assignment.

Reading ​

Anthropic Engineering, "Beyond permission prompts: making Claude Code more secure and autonomous" (October 2025), the reading list's core pick.

Reading response (150–250 words, 🔴 AI off, on Canvas, before the Seminar; rubric): state the post's main claim and the 84% figure. What exactly was measured, by whom, against what baseline? This is vendor evidence: what would you need to see to trust it? Your mini-agent has a workspace guard and an approval gate: which of the post's two kinds of isolation does it have, and for which tools? What will you change in how you run an agent on the class codebase this week? End with one question for the debate.

Key ideas ​

Same loop, bigger harness. A production CLI agent still sends the conversation and tool schemas, runs the tool calls and loops. Everything else in the harness is what makes it usable and safe, and it changes results: on SWE-bench Pro, scaffolds alone shift scores by tens of points (Deng et al., Tables 1 and 5).

Prompts and schemas are assembled. mini-agent has one fixed system prompt. Production harnesses typically build theirs at run time from parts: rules, tool guidance, the environment, project files such as AGENTS.md. Tool names, descriptions and parameters are all the model knows about a tool. Find out what the class codebase does by reading its code, not by asking it.

Context has to be managed. Harnesses truncate tool output, read files in ranges and compact old turns, because quality falls as input grows: all 18 models in Chroma's tests degraded (context rot). A subagent explores with a fresh context and returns a summary of code the parent never saw: treat it as inferred (agent patterns).

Approval prompts are not the boundary. Injected text has made an agent switch on its own auto-approve setting (case A4), and people stop reading prompts they see too often. The boundary is a sandbox with filesystem and network isolation; a Codespace gives you the first, not the second (sandboxes).

Read a large codebase outside in. Build it, run the tests, find the entry points, follow one request end to end, use tests as documentation and history for hotspots. Michigan's EECS 498, working in Aider's 20,000 lines, says "Learn, then design, then build" (Lab03). Agents miss project knowledge: of 567 PRs written with one CLI agent, 83.8% were merged, but 45.1% of those needed further changes, mostly bug fixes, docs and project conventions (Watanabe et al.).

Check your understanding ​

  1. Name three things a production harness adds around the loop that mini-agent doesn't have, and the problem each solves.
  2. An agent's subagent reports that "all permission checks go through checkPermission". What tag does that claim get, and what two checks would change it?
  3. Your codespace has your free-tier key as a secret. What can a prompt-injected agent inside it do with that key, and what can't it reach?
  4. Why does the onboarding Lab have you build from the README before you ask an agent anything?
Answers
  1. For example: compaction (the window fills), permission modes (fewer, better prompts), an OS-level sandbox (a path check can't confine a shell), subagents (exploring without flooding the parent). 2. Inferred. Read the function and its callers (git grep -n), and break one check on purpose to see which test fails. 3. Read it with env and send it out, since a Codespace doesn't restrict outbound traffic; it can't reach your laptop or other repositories. 4. You need a working build and test command to verify anything the agent claims, and the README's errors are observed findings.

Going further ​
