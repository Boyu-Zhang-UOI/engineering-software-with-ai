Week 2 — Lab and Assignment ​

Your first contact with the class codebase is comprehension, not change. Build it, test it, let an agent map it, and find out how much of the map is true.

AI-use key: 🟢 AI on: use an agent to explore, following the Safe Loop · 🔴 AI off: you open the files and run the checks yourself. A second agent confirming the first is still an inferred claim.

Rules for agents this week (safety contract): the class codebase is code you didn't write, so it runs only in a sandbox (rule 3). Its codespace gets one secret, your free-tier key, and nothing else (rule 4). That is acceptable only because this session reads the pinned class code and nothing else: no issues, no web pages, no other teams' code. Approvals stay on. The agent reads; it doesn't edit, except to save its own map if you approve that one write.

Before the Lab (20 min) ​

  1. Read the class codebase: the project, the class fork, the pinned commit, the language and the test command. Below, [install command] and [test command] mean the ones recorded there.
  2. Fork the class fork to your own account (Fork on the class fork's page). Your onboarding report goes in this fork; team work goes in your team fork later.
  3. Read the dev container config before you build it. On github.com, open .devcontainer/devcontainer.json in your fork, if there is one, and read any postCreateCommand, features or Dockerfile it names: they run when the codespace is created (sandboxes).
  4. Give the codespace your key, and only your key. github.com → Settings → Codespaces: add your fork to the repository access of the secret your agent reads (for Gemini CLI, a secret named GEMINI_API_KEY holding your free AI Studio key). Check that no other secret lists this fork.
  5. Create a codespace on your fork (2-core), let it finish building, then stop it until the Lab.

Setup check (5 min) ​

Start your codespace. In its terminal, check that you're on the pinned commit, and that your key arrived without printing it:

bash
git rev-parse --short HEAD
test -n "$GEMINI_API_KEY" && echo "key is set"

The hash must match the pinned commit in the class codebase. Create the report file now, from the outline in the assignment, and keep notes in it as you go:

bash
mkdir -p course && touch course/ONBOARDING.md course/AI_LOG.md

Part 1 — Build it from the README (15 min) ​

Core · 🟢 AI on (but follow the README, not an agent)

Follow the project's README (or CONTRIBUTING.md) development setup exactly as written, in order. Time each step:

bash
time [install command]

In course/ONBOARDING.md, under "Build", record each command, how long it took, and every place where the README was wrong, out of date or silent: a missing prerequisite, a renamed script, a step only CI performs. Each of those is an observed finding and goes in your report.

Don't let an agent "fix" the build by editing lockfiles, CI configuration or dependency versions (troubleshooting). If a step fails, record the exact error, check the class codebase for staff notes, and ask your neighbors.

✅ Checkpoint: the project builds (or you have the exact error and what you tried), and every command is in your notes.

Part 2 — Run the tests (10 min) ​

Core · 🟢 AI on

bash
time [test command]

Record the counts (passed, failed, skipped), the run time and the machine size. If anything fails on the pinned commit, say whether you think it's the environment or the code, and tag that inferred until you've checked.

Then find out how to run one test file and one test by name. You'll need that to verify claims in Part 4. For pytest it's pytest [path]::[test name] or -k [pattern]; JavaScript and TypeScript runners take a file path and usually a name filter (check the runner's --help). Run one and record the command.

✅ Checkpoint: the full-suite command, its counts and time, and a working single-test command, all in your notes.

Part 3 — Read the agent files, then map (15 min) ​

Core · 🟢 AI on

First, read what a stranger wrote for your agent. Project instruction files and agent configs are instructions to whatever agent opens the repository (sandboxes, step 4). List them and read each one before your agent does:

bash
git ls-files | grep -iE '(^|/)(agents|claude|gemini)\.md$|copilot-instructions|\.cursorrules|(^|/)\.(cursor|gemini|claude|vscode)/|(^|/)\.?mcp\.json$|(^|/)opencode\.jsonc?$'

Note anything that tells an agent to run a command, fetch a URL or change its settings, and any MCP server it would start. The list isn't complete (every harness has its own file names), so also skim the README for agent setup. The class codebase is itself an agent, so its source also contains prompts written for a model. Your agent will read them as files. Watch whether it treats them as data, or starts following them.

Then map it. Start your CLI agent in the repository root (Tool Handout: Tools by week: Gemini CLI, or the fallback), in its default approval mode. If its settings let you switch off web fetch and web search for this session, do; otherwise deny those calls. Give it this prompt:

text
I am onboarding to this repository. Read only: do not edit files, and do not run commands that change anything.
Produce an architecture map as a Markdown table with columns: # | Claim | Evidence (file:line, or the command you ran) | Confidence.
Cover:
1. The entry points a user runs.
2. The path from a user's request to the model call and back, as a numbered list of functions with file:line.
3. Where tools are defined, and how one tool is registered.
4. Where permission or approval checks happen, and what they check.
5. How model providers, base URLs and API keys are configured.
6. Where the system prompt is assembled, and what goes into it.
7. How the conversation is truncated or summarized when it grows.
8. How the tests are organized, and the command that runs one test file.
For every claim, cite the exact file and line you read. If you did not open the file, write "not opened" in the Evidence column. Aim for 20 to 30 claims.

Save the answer verbatim as course/architecture-map.agent.md. Copy it from the terminal, or approve one write to exactly that file. This file is the agent's work, unedited. Your corrections go in the report.

✅ Checkpoint: the agent's map is saved, and you've noted which instruction files exist and anything in them that surprised you.

Part 4 — Verify the map (10 min, continue at home) ​

Core · 🔴 AI off

A citation is a lead, not evidence, until you open it. In course/ONBOARDING.md, start a claims table:

markdown
| # | Claim (from the map, or your own) | Evidence: file:line at [commit], or command → output | How checked | Tag | Status |
|---|---|---|---|---|---|
| 4 | Approval checks happen in [function] | `[file]:[line]` at `a1b2c3d` | read; broke it | observed | confirmed |

Status is one of confirmed, wrong, partly right (say which part) or unsupported (the cited line doesn't show it). Check claims three ways, strongest last:

  1. Read it. Open the cited lines, and search for what they name:

    bash
    sed -n '[start],[end]p' [file]
git grep -n "[function or symbol]"

  2. Run it. Run the narrowest test that exercises the claim, with the single-test command from Part 2.

  3. Break it on purpose. Change one line in the code the claim is about (flip a condition, return early), run the test you think covers it, and see it fail. Then undo:

    bash
    git restore [file]
git status --short -- . ':!course'

    The status command (which ignores your course/ notes) must print nothing before you go on. If no test fails, you've found something else worth reporting: that code is untested.

✅ Checkpoint: at least five claims checked, each with located evidence, a tag and a status, and at least one checked by breaking it.

Part 5 — Find mini-agent's parts (If time) ​

If time · 🟢 AI on to search, 🔴 AI off to confirm

For each part of mini-agent you read in week 1, find its counterpart here, with file and line: the loop (runAgent), tool schemas (TOOL_DEFINITIONS), executing a tool call (executeToolCall), the approval gate (createApprovalGate), the system prompt (SYSTEM_PROMPT), the model client with retries (callModel), and the trace. Then list what this harness has that mini-agent doesn't: compaction, subagents, permission modes, a sandbox, session storage. This table goes into your report.

Part 6 — Hotspots from history (If time) ​

If time · 🟢 AI on

If the class fork kept upstream history, the files that change most often are where bugs and merge conflicts concentrate:

bash
git log --since="12 months ago" --format= --name-only | grep -v '^$' | sort | uniq -c | sort -rn | head -20
git log --oneline -- [file] | head -20

Compare the top of the list with the files the tests exercise. A file that changes often and has few tests is a candidate risky area for your report.

Checkoff (15 min) ​

Show a staff member, in your codespace, with your notes pushed to your fork:

  1. git rev-parse --short HEAD matching the pinned commit, and your build notes: the commands, their times and the README's gaps.
  2. The test run: the command, counts and time, plus a single-test command that works.
  3. course/architecture-map.agent.md, saved verbatim.
  4. At least five claims in course/ONBOARDING.md with evidence, a tag and a status, one of them checked by breaking code, with the source restored afterward.
  5. On request, one claim shown live: open the file at the line and explain it.

Scored with the Lab checkoff rubric. A build that fails for a reason you've recorded exactly still earns partial credit.

Next steps (5 min) ​

  • Push (git add course && git commit && git push) and stop the codespace.
  • Find your team (announced in the Seminar) and book a 45-minute charter meeting this week.
  • CS [5xxx]: check the presentation schedule when it's posted.

Assignment — The onboarding report ​

About 4 hours, individual. Everything goes in the course/ folder of your fork of the class fork. Submit the fork's URL and the commit to grade on Canvas (how to submit). Your team's M0 proposal in week 5 builds on the four reports, so write for a teammate who hasn't opened the code yet.

Deliverables ​

DeliverableAI use
course/ONBOARDING.md, the report (about 1,500 words plus tables)🟢 AI on to explore; 🔴 AI off for sections 5 and 6 and for every tag
course/architecture-map.agent.md, the agent's map, unedited🟢 AI on

The report ​

course/ONBOARDING.md has these sections:

  1. Summary. What the project does, in three sentences. The pinned commit, the agent and model you used, and the date.
  2. Build and test. The exact commands, their times and the machine size; every README gap you found; the test counts, any failures on the pinned commit, and the single-test command. Tag each claim.
  3. Architecture map. The main components with their paths (a table, or a Mermaid diagram). The request path traced end to end as a numbered list of functions with file:line: user input → loop → model call → tool call → permission check → tool runs → result back to the model → output. Then compared with mini-agent: for each part of mini-agent (Part 5's list), where it lives here and what this harness adds. Every line tagged.
  4. Three risky areas. For each: where it is; why it's risky, with evidence (it enforces permissions or handles keys; it changes often; few tests touch it; it's large or deeply nested); what could go wrong if an agent changed it; and what you'd require before merging a change there (characterization tests, a second reviewer, a security check).
  5. Five verified claims (🔴 AI off). Each with its evidence (file:line at the pinned commit, or a command and its output) and how you checked it. At least one checked by breaking code on purpose, showing the failing test's name and output.
  6. Two claims the agent got wrong (🔴 AI off). For each: what the map said (quote it), what is actually true (observed, with evidence), how you found out, and why you think it went wrong (tagged inferred: a stale file, a name that sounded right, a summary of a file it didn't open). If you check 20 claims and find fewer than two wrong, report that, with the count. That's a finding too.
  7. Open questions. Inferred claims you didn't check, and how you would check each.

Your AI log entry records the mapping session: the agent and model, the prompt (in a text block), what you delegated (the map), what you kept (the verification) and what the checks caught.

The team charter (team deliverable) ​

Meet as a team (45 minutes), fill in TEAM_CHARTER.md template as course/TEAM_CHARTER.md in your team fork, and have each member add their own sign-off line in their own commit. Include the "free allowances" plan, so the team doesn't run one pool dry in the same week (Tool Handout: Spreading the work across free allowances). The charter is due with this assignment and checked at M0, in the "Team setup" row of the M0 rubric. It isn't part of this week's 15 points.

How it's graded ​

20 points for the week: the Lab checkoff (5) and the report (15), on the labs and assignments rubric. This week, the rows mean:

Row (points)What it means this week
Deliverables work (5)A teammate could build and test the project from section 2 alone; the map covers the request path, tools, permissions, providers, the system prompt and context management; three risky areas, five verified claims and two wrong ones (or the documented count) are present
Verification (4)Every claim tagged; every verified claim located at the pinned commit; at least one checked by breaking code, with the failing test shown; each wrong claim set against what's actually true, with evidence
Process record (3)AI_LOG.md with the mapping session, the prompt, and what verification caught; the agent's map kept unedited; commits with Assisted-by: trailers where AI helped
Write-up (3)Risky areas argued from evidence, not impressions; the mini-agent comparison specific; open questions and limitations stated

Due before next week's Seminar (default 11:59 pm the night before). The week 3 Seminar opens with a 7-minute, 🔴 AI-off quiz on your report: expect "where does [part] live, and how do you know?"

IMPORTANT

Minimum to keep up. The class codebase builds in your codespace, you can run one test by name, and you can show from the code (observed) where its loop, its tools and its permission checks live. Week 3's AGENTS.md for this codebase and every team milestone depend on it. If the build is blocked, record the exact error and what you tried, and complete the map and verification by reading: a precise blocker earns partial credit.

Troubleshooting ​

ProblemFix
GitHub won't create your fork ("you already have a fork")GitHub allows one fork per repository network per account. Use your existing fork: git remote add class https://github.com/[course-org]/[project].git, git fetch class, then git switch -c onboarding [pinned commit], and submit that branch
The build runs out of memory or takes forever on 2 coresUse a 4-core machine for the build only, then switch back: it spends hours twice as fast (troubleshooting)
key is set doesn't printThe secret doesn't list this fork, or was added after the codespace was created: fix the access, then reload or rebuild
The agent hits rate limits or "request too large"It's reading too much at once. Ask one question of the prompt at a time, in fresh sessions (troubleshooting)
The map has no citations, or cites lines that don't existKeep it as saved: nonexistent citations are wrong claims for section 6. Then rerun the prompt on one area, insisting on "not opened"
The agent starts following instructions from a prompt file it readStop the session, record the step (it's an injection example for week 4) and start a fresh one
Code you broke on purpose stays brokengit restore [file], then git status --short -- . ':!course' and the test command again
