Week 6 — Lab and Assignment ​

In the Lab you write property-based tests for roomly with fast-check, learn to build generators that reach the inputs where rules bite, and hunt until a property fails on the shipped code. In the assignment you cover every Booking rule, report every real bug you find, and fix each one test first.

AI-use key: 🟢 AI on: any assistant or agent, under the Safe Loop · 🟡 AI limited: you write it; an AI may help, and you log that · 🔴 AI off: no assistant, no completions, no chat.

The oracle this week is the Booking rules section of roomly's README: "When the code and this list disagree, the code is wrong." The 29 shipped tests pass, and they miss several real bugs. Every bug you report must name the rule it breaks.

Before the Lab (10 min) ​

Work in your eswa-roomly repository from week 5, on a new branch made from the code as shipped, not from your recurring-bookings work:

bash
git switch -c properties shipped      # the kit exactly as shipped
git checkout main -- AI_LOG.md        # bring your log along
git commit -m "Start the property-testing branch from the shipped code"
node --version                        # 22.x recommended (20.12 works this week; next week needs 22)
npm install                           # installs fast-check and StrykerJS (dev dependencies only)
npm run test:properties               # 1 test passes

If you have no shipped tag, make it from your first commit: git tag shipped $(git rev-list --max-parents=0 HEAD). npm install reports moderate advisories in the testing tools' dependencies; leave them for week 10, where dev-only exposure is the topic.

NOTE

Why the shipped code and not your feature? The bugs you're hunting are in the original code, a clean baseline makes your results comparable with your classmates', and next week's mutation scores start from it. Your recurring bookings stay on main.

Part 1 — Anatomy of a property (10 min) ​

Core · 🔴 AI off for the reading, 🟢 for running

Open tests/properties/time.property.test.js. A property-based test has three parts: generators (fast-check calls them arbitraries) that produce inputs, a predicate that must hold for every input, and a runner, fc.assert, that tries 100 inputs by default and, when one fails, shrinks it to a small counterexample. The shipped property is a round trip: building time → UTC → building time gives back what you started with.

Look at what the date generator actually produces, and how often it lands on a day that Booking rule 11 calls out:

bash
node --input-type=module -e "
import fc from 'fast-check';
import { addDays } from './src/time.js';
const anyDate = fc.integer({ min: 0, max: 3 * 365 }).map((n) => addDays('2026-01-01', n));
const changes = ['2026-03-08', '2026-11-01', '2027-03-14', '2027-11-07', '2028-03-12', '2028-11-05'];
console.log(fc.sample(anyDate, 6));
fc.statistics(anyDate, (d) => (changes.includes(d) ? 'clock-change day' : 'other day'), { numRuns: 10000 });
"

Check those six dates against rule 11 (the second Sunday in March, the first Sunday in November) with a calendar. Then work it out: with 100 runs, how likely is the shipped property to try even one of them? (About 0.5% per draw; the chance of none in 100 runs is about 58%.) A property that passes has only been checked on the inputs it tried.

✅ Checkpoint: you can say, in numbers, how often the shipped generator reaches a clock-change day, and what that means for a passing run.

Part 2 — Generators that reach the interesting values (15 min) ​

Core · 🟢 AI on

1. Shared generators. Create tests/properties/generators.js. It isn't a test file (only *.test.js files run), so every property file can import it:

javascript
// Generators for roomly's property tests. Import what you need, for example:
//   import { date, hhmm, edgeTime, anyUser } from './generators.js';
import fc from 'fast-check';
import { addDays, weekdayOf } from '../../src/time.js';

// Show the assertion that failed, and make runs repeatable with FC_SEED=42.
fc.configureGlobal({
  includeErrorInReport: true,
  ...(process.env.FC_SEED ? { seed: Number(process.env.FC_SEED) } : {}),
});

// The nth Sunday of a month, as 'YYYY-MM-DD'.
export function nthSunday(year, month, n) {
  let d = `${year}-${String(month).padStart(2, '0')}-01`;
  while (weekdayOf(d) !== 'sun') d = addDays(d, 1);
  return addDays(d, 7 * (n - 1));
}

// Rule 11: the clocks change on the second Sunday in March and the first Sunday in November.
export const clockChanges = (year) => ({ spring: nthSunday(year, 3, 2), fall: nthSunday(year, 11, 1) });

// Any date from 2026 to 2028, uniformly.
export const anyDate = fc.integer({ min: 0, max: 3 * 365 }).map((n) => addDays('2026-01-01', n));

// A day the clocks change, or the day before or after it.
export const clockChangeDay = fc
  .record({ year: fc.integer({ min: 2026, max: 2028 }), spring: fc.boolean(), shift: fc.integer({ min: -1, max: 1 }) })
  .map(({ year, spring, shift }) => addDays(clockChanges(year)[spring ? 'spring' : 'fall'], shift));

// Mostly ordinary dates, but about one in four is next to a clock change.
export const date = fc.oneof({ arbitrary: anyDate, weight: 3 }, { arbitrary: clockChangeDay, weight: 1 });

// A wall-clock time 'HH:MM' with the hour from minHour to maxHour.
export const hhmm = (minHour, maxHour) =>
  fc
    .record({ hour: fc.integer({ min: minHour, max: maxHour }), minute: fc.integer({ min: 0, max: 59 }) })
    .map(({ hour, minute }) => `${String(hour).padStart(2, '0')}:${String(minute).padStart(2, '0')}`);

// Times where something changes: midnight, the clock-change hours, opening and closing, the last minute.
export const edgeTime = fc.constantFrom('00:00', '01:00', '01:30', '02:00', '02:30', '03:00', '07:00', '12:00', '22:00', '23:59');

// The seed users (data/seed/users.json): three students, a staff member and an admin.
export const anyUser = fc.constantFrom('u-alice', 'u-bao', 'u-carmen', 'u-dana', 'u-eli');

// Two different users: for example, a booking's owner and someone else.
export const twoUsers = fc.uniqueArray(anyUser, { minLength: 2, maxLength: 2 });

The clock-change days are computed from the rule's own words, not typed in. (Generators built from the code under test can share its bugs; weekdayOf is plain calendar arithmetic with its own test.)

2. Uniform versus biased. Create tests/properties/warmup.test.js, which claims more than the shipped example: the round trip holds at every time of day.

javascript
import { test } from 'node:test';
import assert from 'node:assert/strict';
import fc from 'fast-check';
import { buildingLocalToUtc, toBuildingLocal } from '../../src/time.js';
import { anyDate, date, edgeTime, hhmm } from './generators.js';

const anyTime = fc.oneof({ arbitrary: hhmm(0, 23), weight: 2 }, { arbitrary: edgeTime, weight: 1 });

test('warm-up: building time -> UTC -> building time, at any time of day', () => {
  fc.assert(
    fc.property(anyDate, anyTime, (d, t) => {
      const back = toBuildingLocal(buildingLocalToUtc(d, t));
      assert.equal(back.date, d);
      assert.equal(back.time, t);
    }),
    { numRuns: 1000 },
  );
});

Run it three times with node --test tests/properties/warmup.test.js. It almost always passes. Now change anyDate to date in the property and run it again. It fails. With FC_SEED=42 in front of the command you get exactly this (other seeds fail differently):

text
Property failed after 255 tests
{ seed: 42, path: "254:0:1:3", endOnFailure: true }
Counterexample: ["2026-03-08","02:00"]
Shrunk 3 time(s)
Got AssertionError [ERR_ASSERTION]: Expected values to be strictly equal:
'01:00' !== '02:00'

3. Read the counterexample. The counterexample is the smallest failing input fast-check could shrink to: it simplified the year, the season, the day and the time while the property kept failing. The seed and path replay exactly this failure: pass them to fc.assert(…, { seed: 42, path: "254:0:1:3" }), or rerun the whole file with FC_SEED=42. The last lines say what the predicate saw.

4. Is it the code or the property? Decide from the documentation, not intuition. Read the comment above buildingLocalToUtc in src/time.js, then 🔴 write one sentence in your notes: which one is wrong here? (Hint: what time is it in Moscow, Idaho, one minute after 01:59 on 8 March 2026?) Fix the warm-up so it claims only what's true: skip inputs that can't happen with fc.pre(…), and add a second property for the documented behavior on the skipped times. Run both with the biased generator until they pass.

5. Biasing, in general. The same moves work for every rule:

  • Boundaries: draw from small ranges so values collide. Two intervals on a 5-minute grid within one morning share endpoints often; two fc.date() values almost never do:

    javascript
    // [start, end) as 5-minute slot numbers within one morning
const slots = fc.tuple(fc.integer({ min: 0, max: 24 }), fc.integer({ min: 1, max: 12 })).map(([s, len]) => [s, s + len]);

  • Named values: mix ordinary and edge values with fc.oneof and weights, and fc.constantFrom for the edges a rule names: limits, opening and closing times from data/seed/rooms.json, the first and last allowed value, one past each.

  • Roles: draw users from every role, and pairs of different users, so "who may do this" is exercised for each.

  • Measure it. fc.statistics(generator, classify) prints how often each class appears. Paste the output into your report: a bias you didn't measure is a hope.

  • Keep shrinking readable. Build from integers with .map; prefer generating valid inputs to filtering with .filter or fc.pre, which waste runs (fast-check gives up after too many skips).

✅ Checkpoint: generators.js exists; the warm-up fails with the uniform-to-biased change, you replayed it with its seed, you can say from the documentation whether the code or the property was wrong, and the fixed warm-up passes.

Part 3 — An agent proposes, you judge (10 min) ​

Core · 🟢 AI on (the proposals) · 🔴 AI off (your verdicts)

Give a fresh agent session the oracle and the interfaces, but not the implementation:

bash
grep -n "^export function" src/*.js      # signatures only
text
I'm writing property-based tests (fast-check, node:test) for a room-booking service.
Below are its Booking rules, which are its specification, and the signatures of its
exported functions. Propose 8 properties. For each: the rule number it comes from,
the property in one sentence, the generator you'd use and which values it must reach,
and what kind of bug would make it fail. Work only from the rules; don't ask for or
guess the implementation. Don't write code.

[paste the "Booking rules" section of README.md]
[paste the grep output]

Judge every proposal in a table in docs/properties.md, with one verdict and a reason each:

VerdictMeans
KeepFollows from a rule you can quote
Fix the generatorThe right property, but the generator it describes wouldn't reach the case
Reject: restates the codeIts expected value is whatever the function returns (an oracle taken from the implementation)
Reject: not in the rulesIt invents a requirement. Ask about it, or log it as an open question
Reject: vacuousTrue for any implementation, or never reaches a case where it could fail

✅ Checkpoint: at least five verdicts with reasons in docs/properties.md, written by you, and at least one Keep you'll implement in Part 4.

Part 4 — Hunt (15 min) ​

Core · 🟢 AI on for the code, 🔴 AI off for deciding whether a failure is a bug

Pick a rule and write a property in a new file, tests/properties/[topic].test.js. Start each property with a comment: the rule number, the property in one sentence, and its pattern.

PatternIt comparesA place in roomly to try it
ModelA function with a few-line model written straight from a ruleThe exported helpers in bookingService.js against rules 1–7
DifferentialTwo implementations that should agreeThe code tour names two sets of date helpers that are "supposed to agree"
Round tripEncode, then decodeThe shipped example and your warm-up
MetamorphicTwo runs whose results must relate, with no model of the answerThe order in which two bookings are made; moving both by a week
Invariant / consistencySomething that must hold after any sequence of operations, or two features that must agree/availability says a slot is free; does a booking there succeed?

Practical notes:

  • Pure functions first. overlaps, findConflicts (pass { bookings: [...] }), localToUtc and parseWhen are exported for tests and need no data folder: a thousand runs take milliseconds. checkRules reads the rooms data and the clock but writes nothing, so one freshData() before the property is enough.
  • Service-level properties (createBooking, updateBooking, cancelBooking, checkIn) need freshData() from tests/helpers.js inside the property, so every run starts clean. It freezes the clock at Monday 5 October 2026, 08:00 in the building. Rule 3 then limits students to 14 days ahead, so move the clock with setNow() before a generated date, or use a staff user. Use fewer runs (50).
  • When a property fails: record the counterexample, seed and path; reread the rule; decide, 🔴 AI off, whether the code or the property is wrong. If it's the property, fix it and note why. If it's the code, don't fix it yet: that's the assignment.

✅ Checkpoint: a property that fails on the shipped code, a shrunk counterexample, its seed and path, and one sentence quoting the rule it shows the code breaking.

Part 5 — From counterexample to regression test (If time) ​

A shrunk counterexample is a ready-made example test. Make a branch for fixes and write it as a plain node:test case in tests/regression.test.js (no fast-check, so npm test runs it):

bash
git switch -c fixes

Run it and watch it fail. That red run is the first half of the assignment's fix for this bug: commit the test first, then the fix.

Part 6 — Every route, every role (If time) ​

Rule 9 says who may change or cancel a booking, "by any route". List every operation that changes a booking from the README's API table (each method and body shape is a separate operation), then write one property: for any operation and any pair of different users from twoUsers, a student who doesn't own the booking is refused with 403 and the booking is unchanged, while staff and admins succeed. Through the service functions it's synchronous; through HTTP, use createApp() from src/server.js, fetch, and fc.asyncProperty with await fc.assert(…).

Checkoff (15 min) ​

The checkoff is worth 5 points: complete, partial or missing (rubric). Show a staff member, on screen:

  1. A property that fails on the shipped code (the properties branch, src/ unchanged): the property's rule comment, the failing run with its shrunk counterexample, and a replay with its seed (or FC_SEED).
  2. The judgment: which Booking rule the counterexample breaks, quoted, and why the code, not the property, is wrong.
  3. generators.js in use, and at least five verdicts on the agent's proposals in docs/properties.md.

Staff then ask one question, such as "how often does your generator reach the value that broke the property?" or "what would this property have done with a uniform generator?"

Next steps (5 min) ​

Commit and push the properties branch. Plan the assignment: one rule at a time, a bug report per real bug, and fixes on a separate branch.

Assignment — A property suite, bug reports and fixes ​

Turn the Booking rules into a property suite, report every real bug it finds the way a maintainer would want, and fix each one test first. About 3.5 hours.

Deliverables ​

In your eswa-roomly repository. Submit the repository URL and the tag week6 (on the fixes branch) on Canvas (how to submit).

  1. A property suite in tests/properties/, on the properties branch, covering Booking rules 1–11: at least one property per rule, or a reason in your report why a property is the wrong tool for that rule and which example test covers it instead. Every property starts with its rule comment. Generators live in generators.js and are biased toward boundaries, clock changes and roles where a rule needs them.
  2. A bug report for every real bug the suite finds: one GitHub issue each in your repository (or one section each in BUGS.md if issues are off), from the bug report template, with the fields below.
  3. Fixes, test first, on the fixes branch (made from properties): for each bug, a commit adding an example-based regression test to tests/regression.test.js (red), then a commit with the fix (green) whose message says Fixes #[n]. At the end, npm test and npm run test:properties both pass, and the 29 shipped tests pass unchanged.
  4. docs/properties.md: a table of your properties (rule, pattern, generator bias with its fc.statistics share, result on the shipped code with the counterexample, result after the fixes); your verdicts on the agent's proposals from the Lab; the rules without a property, and why; what you would test next.
  5. AI_LOG.md: sessions for the agent's proposals and for each fix, with what your checks caught.

Bug report format ​

Start each report from the bug report template. This week its fields come from your property run, like this:

text
Title: [Rule N] [what goes wrong, in one line]

Rule violated: [quote the Booking rule]
Found by: [property name] · seed [s] · path [p] · shrunk counterexample: [value]

Reproduction (minimal, on the shipped tag):
  [a plain test, or curl commands with ROOMLY_NOW set, that anyone can run]

Expected: [what the rule requires]
Actual:   [what happens, observed: the command and its output]

Who is affected, and how badly: [for example: two groups hold the same room]
Suspected location: [file and function, tagged observed or inferred]

🟡 AI limited: the report is yours. An agent may help shrink a reproduction further; log it.

Steps ​

  1. One rule at a time. Write the property from the rule before you read the function body (check first). If you read the body first, ask yourself whether your expected value came from the rule or from the code.
  2. Make the generator reach the case, and prove it with fc.statistics. A property that never generates the boundary hasn't tested it.
  3. When a property fails: replay it, judge it against the rule, then either fix the property (and say why in docs/properties.md) or file the bug. One bug may make several properties fail; report it once and list them all.
  4. Fix on fixes, never on properties. For each bug: the regression test from the shrunk counterexample, run and seen failing, committed; then the fix under the Safe Loop, with the agent forbidden to touch the test; then npm test and the properties. One bug per commit pair. If a fix breaks a shipped test, stop and decide from the rules which one is wrong; never edit a shipped test to make a fix pass without saying why in the commit and the issue.
  5. Run it all reproducibly before you submit: FC_SEED=1 npm run test:properties, and once with numRuns raised to 1,000 on your main properties. Record the seeds in docs/properties.md.
  6. Tag and push: git tag week6 && git push origin properties fixes week6.

How it's graded ​

The 15-point assignment rubric (Rubrics: Assignment (15 points)), read for this week as:

  • Deliverables work (5): the suite covers rules 1–11 (or justifies each gap); a report for every real bug the suite finds; each fix on fixes with its regression test; everything runs with the documented commands.
  • Verification (4): every property cites its rule; the generators' bias is measured, not assumed; each regression test is shown red before its fix and green after (the commit pairs); counterexamples are shrunk and replayable; claims tagged observed or inferred.
  • Process record (3): AI_LOG.md covers the proposal session and each fix, with what your checks caught; one commit pair per bug, with Assisted-by: trailers.
  • Write-up (3): bug reports a grader can reproduce from the report alone; docs/properties.md with your verdicts, the gaps, and what you'd test next.

Due before next week's Seminar (default 11:59 pm the night before). Next week's Seminar opens with a 7-minute quiz on this assignment.

NOTE

Minimum to keep up: properties for at least five rules, including one that fails on the shipped code; its bug report; its fix with a regression test on fixes; the week6 tag. Next week's mutation testing runs on fixes, and StrykerJS needs every test there to pass: a property for a bug you haven't fixed yet can be marked test.skip with the issue number, and said so.

Troubleshooting ​

  • Not installed yet: fast-check: run npm install in the repository root.
  • A property is slow: freshData() in every run costs a temporary folder; use fewer runs, or test the pure function instead.
  • "Too many pre-condition failures": fc.pre or .filter rejects most inputs. Generate valid inputs directly.
  • The counterexample is huge or unreadable: the generator uses .chain or .filter, or very wide ranges. Build from small integers with .map.
  • It fails in one run and passes in the next: that's random generation finding a rare case. Use the printed seed, or FC_SEED, to make it repeatable, then bias the generator so it isn't rare.
  • A test depends on today's date: use freshData() or setNow(); never the real clock.
