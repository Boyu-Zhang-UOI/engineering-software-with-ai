Week 8 — Legacy Code ​

Before an agent changes code that nobody fully understands, pin down what it does now; then change it in steps small enough that each one can be shown to change nothing.

Learning objectives ​

By the end of this week you can:

  1. Find the seams in a legacy module, name the ones it lacks, and use one to get the code under test.
  2. Write characterization tests and an approval test that pin down what code does now, errors and side effects included, and show that they can fail.
  3. Say what "behavior unchanged" means for a given refactor: what is observed, through which boundary, and what may change.
  4. Delegate a refactor to an agent in small steps, and prove each one green with a test run at every commit and a mutation score over the same code before and after.
  5. Explain the strangler-fig pattern for migrations, and interpret the evidence on AI adoption and complexity.

Lab ​

In the Lab you work in your roomly repository from weeks 5–7. src/bookingService.js is the god module: validation, rules, conflicts, storage, the audit log, email, formatting, check-in and the lobby schedule in one file. You map it with an agent (and verify the map), pin its behavior with characterization and approval tests, then have the agent move one responsibility into its own module, one green commit at a time. The assignment finishes the extraction and proves it changed nothing.

Reading ​

He, Miller, Agarwal, Kästner & Vasilescu, "Does AI-Assisted Coding Deliver?" (MSR 2026; free on arXiv). 807 repositories that adopted Cursor, against 1,380 matched controls. Lines added rose 281% in the first month and the gain was gone after about two months, while static-analysis warnings (+29.7%) and complexity (+40.7% in a table, 25.1% in the text) stayed up. Doubling complexity went with 64.5% fewer lines added.

Reading response prompt (150–250 words, 🔴 AI off): State the main finding with two numbers. Pick one design choice (lines added as velocity, how controls were matched, what counts as complexity) and say how it could make the effect look larger or smaller. How would you cite the 40.7% versus 25.1% discrepancy? End with what persistent complexity means for how you'd use an agent on roomly this week, and one question for the Seminar.

More: reading list, week 8.

Key ideas ​

  • Legacy code is code without tests (Michael Feathers): you can't change it and know what you changed. Agents can produce it in weeks.
  • A characterization test records what the code does, not what it should do. In week 6 that was the flaw of LLM-written oracles, which "capture actual rather than expected behaviour" (Konstantinou et al.); for a refactor it's what you want. A pinned bug stays pinned; fixing it is a separate, tested commit.
  • An approval test (golden master) records every output and side effect for many inputs in one file and compares later runs against it. Scrub what changes every run; read the file before you approve it.
  • Seams. roomly has some (setNow, the data folder, findConflicts's bookings option, the exported outbox) and lacks others (ID generation, the audit file, email).
  • "Behavior unchanged" is a contract you choose. Name the boundary: HTTP responses, exports, files written, emails sent. Identical HTTP responses can still hide a change an in-process caller sees.
  • Small steps, every one green, and the agent never touches the characterization tests: git diff on tests/ is the check, not a sentence in the prompt.
  • Mutation score is a good refactoring gate: it helps in regression settings and misleads when code may already be buggy (Zhao, Zhou & Cohen). Compare the same code: the old file, then the old file plus the new one.
  • The strangler fig migrates by growing new code around the old: route one call at a time, run both and compare (a parallel run), and delete the old path last.
  • Two horizons. Cursor adopters' extra output faded while complexity stayed (He et al.); developers later evolving AI-assisted code showed no significant difference in time or quality (Borg et al.). The measure and its horizon decide the answer.

Check your understanding ​

  1. A characterization test pins a result that breaks a Booking rule. Why keep it, and what happens to it after the refactor?
  2. Name two seams roomly has and one it lacks. What would the missing one let a test do?
  3. After moving audit() out, the old file's mutation score rises and the new file's is low. Did your tests improve?
  4. A refactor keeps every HTTP response identical but makes getBooking() throw instead of returning null. Is behavior unchanged? For whom?
  5. Why is a strangler fig with a parallel run safer than swapping in a rewritten module, and what does it cost?

If a tool is down ​

  • No agent quota: move down the week 8 row of Tool Handout: Tools by week and log the switch, or move the code by hand: the characterization tests matter more than who moves it.
  • StrykerJS won't run (it needs Node 22): report the blocker and use the per-commit test run as evidence (troubleshooting).

Going further ​

  • Borg et al., "Echoes of AI": a preregistered two-phase study and a model of method; a graduate seminar paper, as is He et al.
  • Denisov-Blanch et al., "A Few Pages of Markdown": complexity rose 53% in agent-first repositories without a committed configuration file, 27% with one (observational).
  • CMU 17-313's refactoring assignment, and Feathers' Working Effectively with Legacy Code.
