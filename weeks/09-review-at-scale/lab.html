Week 9 Lab and Assignment ​

Lab — Review five PRs, then review the reviewer (75 min) ​

roomly ships with five pull requests in review-prs/, each a patch file plus a description written by its "author" (the folder's README). Some are fine and some aren't. Today you open them as real PRs, review them yourself with AI off, and later run an AI reviewer on the same PRs. After your reviews are frozen, the staff release a defect key, and you score both reviewers with precision and recall.

IMPORTANT

🔴 AI off for your reviews, from now until your freeze. No AI reviewer on this repository, and no AI chat about these PRs, not even to explain a line (the REVIEW template normally allows that; this week it doesn't, because the comparison needs your review to be yours). 🟢 AI on afterwards: running the AI reviewer, configuring CI, tabulating the scores.

Setup check (5 min) — Core: a fresh copy at the first commit ​

The patches apply only to roomly as it shipped. Your changes from weeks 5–8 touch some of the same lines, and the defect key's locations refer to the shipped code. So review in a fresh copy, made in one of three ways:

  • A new repository from the template (simplest): the eswa-roomly template (link on Canvas) → Use this template → Create a new repository, public, named eswa-roomly-review; or clone the template, delete its .git folder, and push the files to a new public repository. Its main is the shipped code, so BASE=main.

  • A new clone of your own repository, with a branch at its first commit:

    bash
    git clone https://github.com/[your-username]/eswa-roomly.git roomly-review
cd roomly-review
git switch -c review-base "$(git rev-list --max-parents=0 HEAD)"
git push -u origin review-base

  • A git worktree of the clone you already have: a second working folder that shares the same repository, with no second clone (worktrees):

    bash
    cd [your eswa-roomly clone]
git worktree add ../roomly-review "$(git rev-list --max-parents=0 HEAD)"
cd ../roomly-review
git switch -c review-base
git push -u origin review-base

With either of the last two, BASE=review-base. Then, in the fresh copy:

bash
BASE=review-base   # or main, for a new repository from the template
for p in review-prs/*.patch; do git apply --check "$p" && echo "ok: $p"; done   # five "ok" lines
npm test           # passes on the shipped code
gh auth status     # the GitHub CLI is signed in

The repository must be public for this week's free AI reviewer; it holds only kit code, which the data rule allows. Check that no AI reviewer is active on it yet (the repository's Settings → GitHub Apps, and any automatic Copilot code review you set up): your reviews come first.

✅ Checkpoint: five ok lines, npm test passes, and you know your BASE.

Part 1 — Turn the patches into pull requests (10 min) — Core ​

From the fresh copy's root:

bash
for name in 01-validate-attendees 02-faster-conflict-check 03-tidy-room-service 04-calendar-export 05-utilization-report; do
  title=$(head -n 1 "review-prs/$name.md" | sed 's/^# //')
  git switch -q "$BASE"
  git switch -q -c "review/$name"
  git apply "review-prs/$name.patch"
  git add -A
  git commit -q -m "$title"
  git push -q -u origin "review/$name"
  tail -n +3 "review-prs/$name.md" > "/tmp/pr-body-$name.md"
  gh pr create --base "$BASE" --head "review/$name" --title "$title" --body-file "/tmp/pr-body-$name.md"
done
git switch "$BASE"

If your repository was made from a template or a fork and gh opens the PRs in the wrong place, add --repo [your-username]/[repository]. Don't merge any of them: each one is reviewed against the original code.

Write your reviews in your main eswa-roomly repository (the one from weeks 5–8), so they don't disappear when you switch branches here. Start five files from the REVIEW template:

bash
cd [your eswa-roomly clone] && mkdir -p reviews
for n in 01 02 03 04 05; do
  curl -sL https://boyu-zhang-uoi.github.io/engineering-software-with-ai/templates/REVIEW.md -o "reviews/$n.md"
done

✅ Checkpoint: five open PRs against $BASE, and five blank review files.

Part 2 — Review them yourself, AI off (35 min) — Core ​

Aim for about ten minutes per PR: at least three in the Lab, all five by the freeze. For each one, work through the REVIEW template, and keep notes as you go:

  1. List the description's claims. "Tests pass", "no behavior change", a benchmark, "I tested it by hand": each is something the author says, not something you know yet.

  2. Size it up. git diff --shortstat "$BASE"...review/[name] and git diff --stat "$BASE"...review/[name]. Write the changed-line count in the review; you'll compare it with your time.

  3. Run it.

    bash
    git switch review/[name]
npm test

  4. Check that the new tests can fail. Put the old code back, keep the PR's tests, and run them; then restore:

    bash
    git checkout "$BASE" -- src/   # the shipped code, with the PR's tests still in place
npm test                       # the tests that check the change should fail now
git checkout HEAD -- src/      # restore the PR's code (git status: clean, apart from new files)

    If nothing fails, ask what the new tests actually test. (New files the PR added stay in place during this check; a PR with no new tests has nothing to check here.)

  5. Read the whole diff, not just the parts the description mentions: git diff "$BASE"...HEAD.

  6. Try one case the author didn't test. Start the server with a frozen clock, and use the README's demo tokens to act as different users:

    bash
    export ROOMLY_NOW=2026-11-09T16:00:00Z
npm run seed && npm start            # second terminal; Ctrl+C when done
curl -s -H 'Authorization: Bearer demo-alice' localhost:3000/bookings

  7. Write the review: the defect log (file and line, severity, type, observed or not, a suggestion), a decision, a summary for the author and your time. Commit and push it in your main repository after each PR (git -C [your eswa-roomly clone] add reviews, then commit -m "Review PR 0N" and push the same way): the commit times are your evidence that your review came first.

Don't post your comments on the PRs yet: the AI reviewer shouldn't see them, and you shouldn't see its.

Comments people act on are concise, located, and say what to do (Sun et al.). The shape, on an unrelated codebase:

text
lib/cache.js:88 · major · logic · observed
expire() compares Date.now() (milliseconds) with entry.ttl (seconds), so nothing expires
for 1,000 times longer than intended: a 60 s entry was still served after 5 minutes.
Suggest: store expiresAt = Date.now() + ttl * 1000, and add a test with a fake clock.

Mark each finding blocker, major, minor or nit (the template's severities). Put the most important one first. If you approve, say what you checked that convinced you. An invented problem costs points, here and in the PR round.

✅ Checkpoint (checkoff): at least three reviews committed and pushed, each with located findings (or a reasoned approval), a decision and the time you spent.

Checkoff ​

Staff check, on your screen:

  • ☐ At least three reviews/0N.md files, pushed, with commit times from this Lab.
  • ☐ Each has located findings (file and line) tagged observed or inferred, or an approval that says what was checked; a decision; the time spent.
  • ☐ No AI reviewer has commented on these PRs yet.
  • ☐ One question, for example: "What's the most important finding in one of your reviews, and how did you observe it?" or "For a PR you'd approve, what did you check first?"

Part 3 — Run an AI reviewer (If time; required before the freeze) ​

Only after all five of your reviews are pushed. Use the AI code review row of TOOLS.md:

  • CodeRabbit (primary, free on public repositories): install its GitHub App on this repository only. On PRs that already exist, comment @coderabbitai review to start a review.
  • PR-Agent (fallback): as a GitHub Action in this repository only, with your Gemini key as a repository secret, following PR-Agent's documentation; comment /review on each PR. Never put that key in your team fork (the CI section explains why).
  • Copilot code review (last resort): request Copilot as a reviewer at Lite effort only, within the budget TOOLS.md gives.

Note how long setup took and how long each review took to arrive. Then export what it said, from the fresh copy (the GitHub CLI fills in {owner} and {repo}):

bash
for n in $(gh pr list --state open --json number,headRefName --jq '.[] | select(.headRefName | startswith("review/")) | .number'); do
  echo "## PR #$n"
  gh api "repos/{owner}/{repo}/pulls/$n/comments" --jq '.[] | "- \(.path):\(.line // .original_line): \(.body | gsub("\n"; " "))"'
  gh pr view "$n" --comments
done > [path to your eswa-roomly clone]/reviews/ai-[tool].md

Part 4 — Start the CI gates on your team fork (If time) ​

With your team, split the gates (lint, CodeQL or Semgrep, the required-checks ruleset) and start on yours, following the assignment's CI section. Before anything else, check that the fork has no Actions secrets: other people's PRs will run its workflows from next week.

Next steps (5 min): the PR round opens ​

  • Find your target fork in the ring on Canvas. Claim an eswa-pr-round issue nobody has taken by commenting "I'm taking this", build the fork in a Codespace, and log Specify · Delegate · Verify before you start (PR round). Your PR is due before the week 10 Seminar.
  • Agents stay home: your agent works on your clone in your sandbox and never comments, pushes or opens anything in the other team's fork (rule 10).
  • Your team's reviewer rota: who reviews which incoming PR. First reviews are due by the end of the week 10 Lab.

Troubleshooting ​

  • git apply --check fails: you aren't at the first commit (git log --oneline -1), or your repository's first commit isn't the shipped kit. Use a new repository from the template.
  • The PR shows changes you didn't make: its base is wrong. Edit the PR's base branch to review-base on GitHub.
  • An AI review appeared before yours: say so in your comparison's limitations. It's a threat to validity, and naming it costs nothing.
  • CodeRabbit doesn't answer: is the repository public, and the app installed for it? Wait a few minutes after the trigger comment; then switch to the fallback and log the switch.

Assignment — Human versus AI review, and a CI gate ​

About 3.5 hours, plus your PR-round PR. Everything except the CI gate goes in your main eswa-roomly repository.

Deliverables ​

  1. Your five reviews, reviews/01.md … 05.md, each from the REVIEW template: a defect log with file and line, severity, type and observed or inferred; a decision; a summary for the author; your time.
  2. The AI reviewer's comments on the same five PRs, reviews/ai-[tool].md.
  3. The freeze. By the freeze deadline on Canvas (default: 11:59 pm two days after the Lab), submit the commit hash that contains 1 and 2. Staff release the defect key to you on Canvas once your freeze is in. Changes to 1 and 2 after the freeze are ignored.
  4. reviews/COMPARISON.md, written after you have the key:
    • The counting rule (below), copied in before any score.
    • For each reviewer: a confusion table (true positives, false positives, key items missed) with precision and recall.
    • A decision table: for each PR, the key's expected decision, yours and the AI's.
    • Overlap: key items found by both of you, only by you, only by the AI, by neither.
    • Cost: your minutes per PR and per 100 changed lines; the AI's setup time and waiting time.
    • Analysis (300–500 words): what each reviewer missed and why, located (PR, file and line); which AI comments you would have acted on; whether you'd make this AI reviewer a required check on your team fork, with one number from the week's evidence.
    • Limitations: five PRs, one human, one AI tool, and you've known roomly since week 5.
  5. A CI gate on your team fork (below). Submit the link to your gate PR and to a run where your gate failed on a deliberately bad change.
  6. AI_LOG.md entries for the AI reviewer and CI sessions, with Assisted-by: trailers on AI-assisted commits.

Also due before next week's Seminar, and graded as the PR round: your PR-round PR, opened on your target fork.

Steps ​

  1. Finish your five reviews, AI off, and push each one.
  2. Run the AI reviewer on the same five PRs, and export its comments.
  3. Freeze: submit the commit hash on Canvas, then read the key.
  4. Score both reviewers with the counting rule below, and write COMPARISON.md.
  5. With your team, add the CI gates; author your gate PR, get it reviewed, and show it failing once.
  6. Open your PR-round PR on your target fork.

The counting rule ​

Use the REVIEW template's definitions, with these rules fixed before you open the key:

  • A comment is one finding that claims a problem. Praise, questions and summaries aren't counted.
  • A true positive names a key item's location (file and function, or line) and its problem. Two comments on the same key item are two true positives but one item found.
  • A false positive claims a problem the key doesn't list. If you believe it's a real problem the key missed, mark it disputed, give your evidence (observed), and report precision with and without it; staff decide.
  • Comments about code the PR didn't change are out of scope: list them, don't count them. Key items marked optional count neither way.
  • Precision = true positives ÷ comments. Recall = key items found ÷ key items.
  • If the AI reviewer states no decision, write down the rule you'll use for it ("request changes if any comment is labeled critical or major") before you look at the key.

CI gates on your team fork ​

M1 left your fork running its tests on every PR. This week your team adds lint and static analysis, and makes the checks required. Split the work: each member authors at least one gate PR (lint, CodeQL or Semgrep, or the required-checks ruleset with its demonstration), reviewed by a teammate.

  1. Keep the course's gates in their own file, .github/workflows/course-gates.yml, apart from the project's workflows. Take the install, test and lint commands from the class codebase page and the project's contributing guide:

    yaml
    # .github/workflows/course-gates.yml - the course's gates, separate from the project's own CI.
name: Course gates

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read                # nothing more: other people's PRs run this workflow too

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7   # a Python fork: actions/setup-python@v7
        with:
          node-version: 22            # a Python fork: python-version: '3.12'
      - run: npm ci                   # the fork's install command
      - run: npm test                 # the fork's test command

  lint:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0              # the base branch is needed for the diff
      - uses: actions/setup-node@v7
        with:
          node-version: 22
      - run: npm ci
      - name: Lint only the files this PR changes
        env:
          BASE_REF: ${{ github.base_ref }}   # through env, never pasted into the script
        run: |
          files=$(git diff --name-only --diff-filter=ACMR "origin/$BASE_REF...HEAD" -- '*.js' '*.ts')
          if [ -z "$files" ]; then echo "No files to lint"; exit 0; fi
          npx --no-install eslint $files     # a Python fork: ruff check $files

    Linting only the changed files is a ratchet: old code with thousands of warnings doesn't block anyone, and no PR adds new ones. --no-install stops npx from downloading a package that isn't in the lockfile. If the project has no linter, adding one (with its config, as a pinned dev dependency) is its own PR.

  2. Static analysis. Team forks are public, so CodeQL is free: Settings → Code security → Code scanning → CodeQL analysis → Set up → Default (an admin may have to do it; ask staff). Or add a Semgrep Community Edition job, failing only on findings the PR introduces:

    yaml
      semgrep:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - uses: actions/setup-python@v7
        with:
          python-version: '3.12'
      - run: pip install semgrep      # pin the version TOOLS.md lists
      - env:
          BASE_REF: ${{ github.base_ref }}
        run: semgrep scan --config p/default --metrics=off --error --baseline-commit "$(git merge-base "origin/$BASE_REF" HEAD)"

    Semgrep's maintained rules have their own license (internal use; see Tool Handout: Free infrastructure).

  3. Make them required. Settings → Rules → Rulesets → New branch ruleset for main: require a pull request with one approval, require the status checks test, lint (and semgrep) to pass, and, with CodeQL, add Require code scanning results. Checks appear in the list after they've run once. Menus move; ask staff if yours differ.

  4. Show a gate failing. Open a throwaway PR with a deliberate lint error or a failing test. Link the red run, check that merging is blocked, then close the PR.

WARNING

Other people's pull requests run your workflows. In the PR round, classmates push branches to your fork, and a PR from a branch in the same repository runs its own version of your workflow files, with the repository's secrets. So: no LLM keys or tokens as Actions secrets in the team fork; permissions: contents: read; never pull_request_target together with a checkout of the PR's code; untrusted values (branch names, PR titles) reach scripts only through env:; third-party actions pinned to a full commit SHA. An AI reviewer on the team fork runs as a GitHub App (CodeRabbit), not as an Action holding your key.

How it's graded ​

The 15-point assignment rubric (Rubrics: Assignment (15 points)), read for this week as:

  • Deliverables work (5): five reviews and the AI's output for the same PRs, frozen before the key; COMPARISON.md complete; your gate merged into the team fork and required on main.
  • Verification (4): the counting rule stated before scoring; precision and recall correct for both reviewers, with the confusion tables; every claim in your reviews observed (a command and its output) or phrased as a question; your gate shown failing on a bad change.
  • Process record (3): commit times showing your reviews before the AI's; AI_LOG.md entries; small commits with trailers.
  • Write-up (3): the analysis located (PR, file and line), the cost numbers, and honest limitations.

Due before next week's Seminar (default 11:59 pm the night before), with the freeze earlier, as above. Next week's Seminar opens with a 7-minute quiz on this assignment.

NOTE

Minimum to keep up: your reviews of all five PRs and one AI reviewer's output, frozen before the key; precision and recall for both; one gate (lint or static analysis) required on your team fork; and your PR-round PR opened on your target fork.
