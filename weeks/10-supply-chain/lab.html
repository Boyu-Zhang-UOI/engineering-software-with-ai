Week 10 Lab and Assignment ​

Lab — Scan and fix (75 min) ​

About half of the functionally correct backends in BaxBench were exploitable. Today you look for the weaknesses in code you and your team actually ship: static analysis, the dependency tree, the names an agent suggests installing, and secrets anywhere in the git history. Every finding gets a decision backed by evidence, and one gets fixed with a regression test.

You work in two places: your own eswa-roomly repository (the one with your weeks 5–8 changes, public on GitHub, so CodeQL is free), and your team fork. If you don't have an eswa-roomly repository, use the template (the eswa-roomly template repository, link on Canvas, Use this template → Create a new repository, public) or copy the folder kits/roomly/ into a new repository of your own.

WARNING

Scan and attack only code you or your team own. Exploit tests run against a server on your own machine (127.0.0.1), never against another team's fork, a classmate's deployment or any real service. The PRs your team receives in the PR round are reviewed, not attacked. The secret in Part 4's drill is fake, and it stays on your machine: never push it.

NOTE

🟢 AI on: running scanners, asking an agent to explain a finding, the fix and its test. 🟡 AI limited: the threat model (an AI may brainstorm attacks; the analysis and decisions are yours). 🔴 AI off: your PR-round review comments and your team's decisions.

Setup check (5 min) — Core ​

  1. Start CodeQL first, because it takes several minutes: on GitHub, your eswa-roomly repository → Settings → Code security → Code scanning → CodeQL analysis → Set up → Default → Enable CodeQL. (Menus move; on a private repository this isn't free, so use Semgrep in Part 1.)

  2. In a Codespace on the same repository:

    bash
    git status && npm test           # a clean tree, tests green
git switch -c security/[short-name]

  3. Start a findings table in SECURITY_FINDINGS.md at the repository root:

    text
    | ID | Source | Location | Finding | Reachable from | Severity | Observed / inferred | Decision |
|---|---|---|---|---|---|---|---|

✅ Checkpoint: CodeQL is running, the tests pass, and the findings table exists.

Part 1 — Static analysis (12 min) — Core ​

While CodeQL runs, scan locally with Semgrep Community Edition (Tool Handout: Free infrastructure; Opengrep works the same way):

bash
pipx install semgrep || python3 -m pip install --user semgrep
semgrep scan --config p/javascript --metrics=off src/

When CodeQL finishes, read its results under Security → Code scanning. Then, on your team fork, open the code scanning alerts from last week's gate and keep the ones in code your team changed (git diff --stat [class-fork tag]..main lists those files; the tag is on the class codebase page).

Triage every finding into the table:

  • Is it real? Read the code at the location. Can you show it with an input, or explain why no input can trigger it?
  • Reachable from what? Trace from a source an attacker controls (a request body, a query string, a header, a file someone else wrote) to the sink the rule names. No path means low severity, whatever the label says.
  • Decision: fix, accept (with the reason and who accepts the risk), or false positive (with the evidence).

Scanners may report little on roomly. They match known dangerous shapes; an exploit tests behavior: who may do what, with which input. So add one manual pass: for each route in src/server.js's table, write down who the README's API table says may call it, and what the code actually checks. A difference is a finding.

✅ Checkpoint: every scanner finding and every manual-pass difference has a row with a decision.

Part 2 — Dependencies: what ships and what runs (12 min) — Core ​

bash
npm audit                       # everything in the lockfile, development dependencies included
npm audit --omit=dev            # only what ships with the app
npm explain [package]           # why a flagged package is in the tree, and whether it's "dev"
npm audit fix --dry-run --force # READ what --force would do; don't run it
grep -c '"hasInstallScript": true' package-lock.json   # packages that run code when installed
npm audit signatures            # registry signatures and provenance attestations of what's installed
npm sbom --sbom-format cyclonedx --omit=dev > /tmp/sbom-runtime.json
npm sbom --sbom-format cyclonedx > /tmp/sbom-all.json
grep -c '"bom-ref"' /tmp/sbom-runtime.json /tmp/sbom-all.json   # components in each

Answer, in your findings table or under it:

  1. Which packages carry the advisories, and through which path (npm explain)? Are any of them shipped to users?
  2. Who is exposed? Development dependencies don't ship, but they run on your laptop, your Codespace and your CI runner. Can an attacker's input reach the vulnerable function when you run your test tools on your own code? That decides the severity.
  3. What would --force have done? Read its proposal line by line. A "fix" that installs a much older major version of your mutation tester is a breaking change labeled as a security fix.
  4. How many packages run install scripts? Which commands would protect you if one were compromised (npm ci from a reviewed lockfile; npm install --ignore-scripts for a first look)?
  5. What do the signature and attestation counts prove, and what not? (A provenance attestation ties a release to a source repository and build; it says nothing about whether that code is benign.)
  6. How many components are in the runtime SBOM, and in the full one?

On your team fork, read Security → Dependabot alerts (free on public repositories) and, for a Node project, run the same npm audit pair. Record whether each advisory is in runtime or development code.

CAUTION

Never run npm audit fix --force without reading the dry run. It can replace a package with an older major version, and "audit fix" in a commit message makes the downgrade look like a security fix to a reviewer.

✅ Checkpoint: each advisory has a row saying runtime or development, and reachable or not.

Part 3 — Check names before anything installs them (8 min) — Core ​

Ask your agent for suggestions, names only:

text
I'm adding two features to roomly: a CSV export of a room's bookings that quotes fields
as RFC 4180 requires, and parsing of recurrence rules like "every Tuesday for six weeks".
Suggest npm packages for each, with one line on why. Don't install anything and don't
run any command.

Save this read-only checker outside the repository, as ~/tools/check-package.mjs. It fetches public registry metadata and installs nothing:

js
// check-package.mjs - look a package up on the npm registry before anyone installs it.
//   node ~/tools/check-package.mjs [name] [name] ...
const DAY = 24 * 60 * 60 * 1000;

async function check(name) {
  const res = await fetch(`https://registry.npmjs.org/${name.replace('/', '%2F')}`);
  if (res.status === 404) return { name, exists: false };
  if (!res.ok) throw new Error(`registry answered ${res.status}`);
  const meta = await res.json();
  const latest = meta['dist-tags']?.latest;
  const version = meta.versions?.[latest] ?? {};
  const dl = await fetch(`https://api.npmjs.org/downloads/point/last-week/${name}`);
  const created = meta.time?.created;
  return {
    name,
    exists: true,
    latest,
    ageDays: created ? Math.floor((Date.now() - Date.parse(created)) / DAY) : null,
    lastPublish: meta.time?.[latest]?.slice(0, 10) ?? null,
    weeklyDownloads: dl.ok ? (await dl.json()).downloads : null,
    maintainers: (meta.maintainers ?? []).length,
    repository: version.repository?.url ?? meta.repository?.url ?? null,
    installScripts: Boolean(version.scripts?.preinstall || version.scripts?.install || version.scripts?.postinstall),
    provenance: Boolean(version.dist?.attestations),
    deprecated: version.deprecated ?? null,
  };
}

for (const name of process.argv.slice(2)) {
  try {
    const r = await check(name);
    if (!r.exists) {
      console.log(`${name}: DOES NOT EXIST on npm. Do not install; anyone could register it.`);
      continue;
    }
    const flags = [];
    if (r.ageDays !== null && r.ageDays < 90) flags.push(`new (${r.ageDays} days old)`);
    if (r.weeklyDownloads !== null && r.weeklyDownloads < 1000) flags.push(`few downloads (${r.weeklyDownloads}/week)`);
    if (!r.repository) flags.push('no repository link');
    if (r.installScripts) flags.push('runs install scripts');
    if (r.deprecated) flags.push('deprecated');
    console.log(`${name}@${r.latest}: ${flags.length ? 'CHECK: ' + flags.join('; ') : 'no red flags'}`);
    console.log(`  age ${r.ageDays} days · last publish ${r.lastPublish} · ${r.weeklyDownloads} downloads/week · ${r.maintainers} maintainer(s) · provenance ${r.provenance ? 'yes' : 'no'}`);
    console.log(`  repository: ${r.repository ?? '(none)'}`);
  } catch (err) {
    console.log(`${name}: could not check (${err.message})`);
  }
}
bash
node ~/tools/check-package.mjs [each name the agent suggested]

For each name, record: exists? a red flag? Does the repository link point at a real project whose README names this package? Is the last publish recent enough for your needs? "No red flags" isn't approval: popular packages get compromised too (case B1). It means the name is what it claims to be.

Then make it a control, not an instruction. "Never install packages" in AGENTS.md is advice. The controls are: approvals on, so every npm install an agent proposes stops at your prompt; lockfile changes read in review (the REVIEW template's security section); npm ci in CI. Finally, check your team fork for dependency confusion: does it use a private registry or unscoped internal package names (cat .npmrc, the project's package manager config)? Usually it doesn't; record what you checked.

✅ Checkpoint: every suggested name checked and recorded, with at least one you would and one you wouldn't install, and why.

Part 4 — Secrets in the whole history (10 min) — Core ​

The drill: why a file scan isn't enough. On a throwaway branch, commit a fake key, delete it in the next commit, then scan both ways. Never push this branch.

bash
git switch -c secret-drill
printf 'LLM_API_KEY=FAKE-%s\n' "$(openssl rand -hex 16)" > config.local
git add config.local && git commit -qm "Add local config"
git rm -q config.local && git commit -qm "Remove local config"

grep -rn "FAKE-" . --exclude-dir=node_modules --exclude-dir=.git || echo "working tree: nothing found"
git log --all -p -G 'FAKE-[0-9a-f]{32}' --format='commit %h %s' | grep -E '^commit|FAKE-'

git switch - && git branch -D secret-drill

The file scan finds nothing; the history scan finds both commits. Had they been pushed, deleting the branch wouldn't recall the clones and forks: the key is burned, and the fix is to rotate it first, then clean up (troubleshooting).

The real scan, on roomly and on your team fork. The patterns match the key formats this course's tools use, private keys, and .env files ever added:

bash
PATTERNS='AIza[0-9A-Za-z_-]{35}|gsk_[0-9A-Za-z]{20,}|sk-or-[0-9A-Za-z-]{20,}|gh[pousr]_[0-9A-Za-z]{36}|github_pat_[0-9A-Za-z_]{22,}|-----BEGIN [A-Z ]*PRIVATE KEY-----'
git log --all -p -G "$PATTERNS" --format='commit %h %an %s' | grep -E "^commit|$PATTERNS"
git log --all --diff-filter=A --name-only --format= | grep -E '(^|/)\.env($|\.)' | sort -u

On the team fork, also read Security → Secret scanning (free on public repositories; GitHub scans the full history for known token formats) and check that push protection is on under Settings → Code security. Ask staff if you can't see those settings.

Two questions for your table:

  • Is a demo token a secret? data/seed/users.json holds demo-alice and friends. In this teaching app, anyone who knows a token is that user, by design. Would a scanner be right to flag it? What rule would you write, and where would it stop applying?
  • What can your agent reach? Every process in a Codespace sees its secrets as environment variables, including the agent and anything it runs; agent config folders and MCP config files hold keys too, and malware now looks for exactly those (case B4). List what's in reach in your setup.

✅ Checkpoint: the drill shows the difference; both repositories' history scans recorded (findings or "none", with the command).

Part 5 — Fix one finding with a regression test (8 min) — Core: start here, finish in the assignment ​

Choose one true-positive finding from Parts 1–4, in roomly or your team fork. Prefer a code finding. A dependency finding counts if you can argue it's reachable, have read the changelog of the version you move to, and add a CI check that would catch it returning.

Write the exploit test first: the attacker's request, the response the spec requires, and a check that nothing changed. In roomly, the shape is the same as tests/api.test.js. This example pins a control that works today:

js
// tests/exploit-[short-name].test.js: the request an attacker would send, and what the spec requires.
import { test, before, after } from 'node:test';
import assert from 'node:assert/strict';
import { freshData } from './helpers.js';
import { createApp } from '../src/server.js';

let server;
let base;
before(async () => {
  freshData();
  server = createApp({ log: false });
  await new Promise((resolve) => server.listen(0, '127.0.0.1', resolve));
  base = `http://127.0.0.1:${server.address().port}`;
});
after(() => server.close());

const as = (token) => ({ Authorization: `Bearer ${token}`, 'Content-Type': 'application/json' });
const roomCount = async () => (await (await fetch(`${base}/rooms`)).json()).rooms.length;

test('a student cannot add a room (POST /rooms is admin only)', async () => {
  const countBefore = await roomCount();
  const res = await fetch(`${base}/rooms`, {
    method: 'POST',
    headers: as('demo-alice'),
    body: JSON.stringify({ id: 'CLR-999', name: 'Not yours', capacity: 10 }),
  });
  assert.equal(res.status, 403); // the attacker is refused...
  assert.equal(await roomCount(), countBefore); // ...and nothing changed
});

For your finding, the test must fail on the current code. Commit it alone (that commit is your evidence), then fix, and commit again with the test green.

✅ Checkpoint: your finding's test exists and fails for the right reason.

Checkoff ​

Staff check one triaged finding, on your screen:

  • ☐ The evidence: scanner output, npm explain output, a history-scan hit, or your failing exploit test (observed).
  • ☐ The location, and what it's reachable from (or why nothing reaches it).
  • ☐ The severity, with a reason, and the decision: fix, accept or false positive.
  • ☐ One question, for example: "Who could exploit this, through which input?" or "Why isn't this development-only advisory a runtime risk, and when would it become one?"

If time ​

  • An exploit test per route and role: for every row of the README's API table, one request from each role that the table says must be refused, each asserting the status and that nothing changed.
  • A dedicated secret scanner (gitleaks or TruffleHog) on the same history, compared with your grep. It's a third-party binary: install it only from the project's official releases, after reading what it does (rule 8), and log it.
  • The SBOM on your team fork, and the answer to "are we affected?" for one current advisory.

Next steps (5 min): the PR round ​

  • Your team's first review of each received PR is due by the end of this Lab (PR round), with the REVIEW template, 🔴 AI off. Read any changes to CI files, AGENTS.md, prompts and dependencies as carefully as code (case B3); run check-package.mjs on any dependency a PR adds.
  • As an author, answer every review comment within 48 hours.
  • Decisions on every received PR before the week 11 Seminar. The round's clock is fixed.

Troubleshooting ​

  • CodeQL setup is missing: the repository is private (code scanning isn't free there) or you lack admin rights. Make your eswa-roomly public, or use Semgrep.
  • pipx and pip both fail: use Opengrep's release binary, or rely on CodeQL; note the blocker.
  • npm audit errors with no lockfile: the team fork may use another package manager; use its audit command, or Dependabot alerts.
  • You pushed the drill branch by mistake: delete it on GitHub, tell staff, and record it. The key is fake, but go through the rotation steps as if it weren't.

Assignment — A security review of your team's work ​

About 3.5 hours, plus the PR round's reviews and responses. Your team reviews everything it has contributed to the class codebase so far, and each member owns part of it.

Deliverables ​

  1. Your fix from Part 5: a PR (in roomly or the team fork) with the exploit or regression test committed first, failing, then the fix with it passing. Your own description (🔴 AI off).
  2. course/SECURITY_REVIEW.md in the team fork (one per team; each member adds their rows):
    • Scope: the commit range (git log --oneline [class-fork tag]..main) and the open PRs it covers.
    • Method: every scan, with its command or settings page, and who ran it.
    • A findings table with a Reviewer column, and the columns from the Lab: source, location, finding, reachable from, severity, observed or inferred, decision. A decision is fixed (link the PR and its test), accepted (the reason, and who accepts the risk) or false positive (the evidence).
    • Dependencies added by your team since the class fork's tag: each with why, the check-package.mjs summary, and whether it's pinned in the lockfile.
    • Secrets: the history-scan results, and the secret scanning and push protection status.
  3. course/THREAT_MODEL.md updated (🟡; version "week 10"), with rows for: dependencies and install scripts (T3); secrets an agent or a CI run can reach; incoming PR-round PRs, which run your workflows and may change AGENTS.md, prompts or CI; the permissions your AI reviewer app holds. Add an entry to section 7 for each change, with your name.
  4. AI_LOG.md entries for the scanning, triage and fix sessions; Assisted-by: trailers on AI-assisted commits.

Also due before next week's Seminar, and graded as the PR round: your team's reviews and decisions on every PR it received, and your answers to the review of your own PR-round PR.

Splitting the work. Use your team's reviewer rota so that every team PR is security-reviewed by someone other than its author. Your rows must cover at least your own M1 PR, one teammate's PR, and one team-wide scan (code scanning alerts, the dependency audit, or the history scan).

Steps ​

  1. Scope it: git log --oneline [class-fork tag]..main and git diff --stat [class-fork tag]..main.
  2. Run the scans on the team fork: code scanning alerts, the dependency audit (runtime versus development), the history scan, secret scanning.
  3. Make a manual pass over each PR in your scope with the REVIEW template's security section and the BaxBench lens: who may do what; input validation; injection; paths; secrets in logs; new dependencies; changes to CI, agent configuration or prompts.
  4. Triage and decide every finding. Fix what you can, each fix in its own PR with a test that fails first.
  5. Update the threat model and say what changed since M0, and why.

How it's graded ​

The 15-point assignment rubric (Rubrics: Assignment (15 points)), read for this week as:

  • Deliverables work (5): your fix merged or in review, with its test; your rows in SECURITY_REVIEW.md; your edits to THREAT_MODEL.md (visible in its history).
  • Verification (4): the regression test shown failing before the fix and passing after (a commit or a run); every finding backed by evidence (scanner output, an exploit test, an npm explain path, a history-scan line) with reachability argued; claims tagged observed or inferred.
  • Process record (3): AI_LOG.md entries with Specify · Delegate · Verify; small commits with trailers.
  • Write-up (3): findings located (file and line, or package and path) with a decision for each; threat-model changes justified; the residual risk your team accepts, stated.

Due before next week's Seminar (default 11:59 pm the night before). Next week's Seminar opens with a 7-minute quiz on this assignment. The PR round closes at the same time, and grace tokens don't apply to it.

NOTE

Minimum to keep up: one finding fixed with a regression test that failed first; your SECURITY_REVIEW.md rows covering your own M1 PR (scans plus a manual pass); the supply-chain and secrets rows of THREAT_MODEL.md; and your PR-round reviews and responses done before the round closes.
