Agent Patterns ​

Context-engineering patterns for the Delegate step: how to set an agent up so that what it does is small, checkable and yours. Each pattern says when to use it, how, the evidence, and how it fails.

The patterns are tool-agnostic: every current harness (Gemini CLI, Copilot, OpenCode, Claude Code, your own mini-agent) supports them in some form. Commands and menus differ; Tool Handout says which tool is current. Where the evidence for a pattern is practitioner consensus rather than a study, the pattern says so.

On this page: AGENTS.md structure · Plan first · Small tasks · Check first · Subagents · Worktrees · Approval policies · The Goldfish test · Measuring whether the agent follows it

AGENTS.md structure ​

What. A short file at the repository root that every session reads first. It tells the agent what it can't find out quickly by itself: the exact commands, where things live, the conventions it would otherwise get wrong, and the boundaries.

How. Use AGENTS.md template. The sections, in order:

SectionHoldsKeep it to
ProjectOne paragraph: what this is, which part your team owns3 lines
CommandsExact build, test, lint and single-test commands, as copied from a working terminal5–8 lines
MapEntry points and the directories that matter, with one phrase each5–10 lines
ConventionsOnly the non-obvious ones, especially those an agent got wrong before5–10 lines
WorkflowPlan first; tests first; one task per session; the evidence to show when done5 lines
ScopeDirectories it may edit; what it must ask about first5 lines
NeverDestructive commands, secrets, weakening tests, posting anything5–8 lines

Evidence. In 441 repositories, coding-agent adoption raised commits 28–38%; agent-first repositories without a committed configuration file saw code complexity rise 53%, against 27% for those with one. The study is observational, and 73.8% of configuration files were never edited after their first commit (Denisov-Blanch et al.). Agent PRs that get merged often need follow-up for project conventions (Watanabe et al.), which is what the Conventions section is for. Every line is read in every session, and context degrades with length (context rot).

Fails when. It becomes a copy of the README (long, generic, ignored); it is never updated (add a line the second time an agent makes the same mistake, and date the file); or you treat it as enforcement. In two famous incidents agents broke written rules they could recite afterwards (case C2). Rules go in AGENTS.md; guarantees go in permissions, tokens and the sandbox. And an AGENTS.md you didn't write is a stranger's instructions to your agent (case A9): read it before your agent does.

Plan first ​

What. The agent reads and proposes; it edits nothing until you approve a plan.

How. Use the harness's plan mode, or say so:

text
Don't edit anything yet. Read what you need, then propose a plan:
the files you will change, the steps in order, the test that will show each step works,
and anything you're unsure about. Wait for my approval.

Then edit the plan: delete steps that touch files outside the task, reorder so the test comes first, and ask about anything you don't understand. Approve one step at a time.

Evidence. Practitioner consensus and course experience rather than a controlled study. Michigan's EECS 498 requires "Learn, then design, then build", because "A one-shot prompt gives you the model's design, not yours" (Lab03).

Fails when. You approve a plan you skimmed. A plan is a design review in miniature: if you couldn't defend it to a teammate, don't approve it.

Small tasks ​

What. One task = one session = one diff a teammate can review in one sitting.

How. Split work in TASKS.md until each task names its files, its test and its "done when". Start a fresh session per task rather than continuing a long one. If a task needs a design decision, it isn't an agent task yet.

Evidence. Agents' reliability falls with task length: METR's time-horizon measure is the task length an agent completes with 50% reliability, and longer tasks fail more (Kwa et al.). Performance falls as context grows in every model Chroma tested, and a focused 300-token prompt beat a 113K-token one (Hong et al.). Compaction keeps long sessions going by summarizing, which loses detail.

Fails when. "Small" is measured in prompts rather than in the diff. A one-line prompt can produce a 900-line change.

Check first ​

What. The test that defines "done" exists, and fails, before the agent writes the code.

How. Write the test yourself, or have a separate session write it from the acceptance criterion and the function's signature only, never from the implementation. Run it and see it fail. Put "never weaken, skip or delete a test" in AGENTS.md's Never section, and check the diff for it anyway. For logic with a clear invariant, write a property test (week 6); measure the suite with mutation testing (week 7).

Evidence. Tests generated after faulty code caught 14% of its faults against 25% for independently generated tests (Konstantinou et al.); LLM-generated oracles capture actual rather than expected behavior (Konstantinou, Degiovanni & Papadakis); LLM-written tests rarely probe boundaries (null inputs 34.8%, empty 38.8%, against over 93% for booleans: Shi et al.).

Fails when. The agent sees the test and writes code that special-cases it. Review the implementation, not just the green check.

Subagents ​

What. A parent agent starts a child session with a fresh context for a sub-task (search the codebase, summarize a module, review a diff) and receives only the child's summary.

When. Exploration of a large codebase whose raw output would flood the parent's context; independent reads that can run in parallel; a review by a session that didn't write the code.

How. Give the subagent a narrow question and a required output shape ("list each file that calls createBooking, with the line number"). Treat what comes back as inferred until you check a sample of it.

Evidence. Thin. Subagents are taught as a harness technique (Michigan EECS 498's later lectures; ANU's COMP4020 "Subagents and real-time": Michigan, ANU), but no study found by the course measures their effect on quality.

Fails when. A subagent's confident summary becomes a fact in your onboarding report without anyone opening the files. And each subagent spends from the same allowance.

Worktrees ​

What. Separate working directories on separate branches of one repository, so several agents can work at once without touching each other's files.

How.

bash
git worktree add ../roomly-issue-3 -b issue-3
git worktree add ../roomly-issue-5 -b issue-5
git worktree list

Start one agent in each directory. Each worktree needs its own npm install and, if it runs a server, its own port. When a branch is merged:

bash
git worktree remove ../roomly-issue-3
git worktree prune

Before you start, write down each task's merge point: where the branches will meet, and who resolves conflicts there.

Evidence. Topics and demos only; no course has published outcome data. UT Austin teaches "Parallelize a task once you can name its merge point" (schedule); UMD's CMSC 389A lists "concurrent agents, git worktrees" as an outcome (syllabus). Week 13 asks you to measure your own review time, because review, not generation, is the likely bottleneck.

Fails when. Two tasks touch the same module (a conflict you scheduled), or three agents' output arrives faster than you can review it. Problems: troubleshooting.

Approval policies ​

What. The rules for which tool calls run without asking. The course default is ask for every command and every write (rule 2).

How. If you allowlist, allowlist read-only commands whose effect you can predict: git status, git diff, ls. Never allowlist anything that runs arbitrary code: a shell (bash -c), an interpreter (node, python), npx, or a package install. Note that npm test and node --test run whatever the tests contain, including code the agent just wrote, so allowlist them only in a sandbox with no secrets attached. Check how your harness matches. mini-agent's allowlist matches prefixes, so npm test && curl … passes a rule for npm test; week 1's "smarter approval policy" extension is about exactly that, and about the limits of parsing a shell string. An allowlist beats a deny-list, because a deny-list has to anticipate every dangerous spelling. Approve writes by reading the diff, not the agent's description of it. Treat any change to an agent's own config or permission files as a security change.

Evidence. Injected text has made an agent switch itself to auto-approve (case A4); in an autopilot mode, a web page exfiltrated secrets in about 28 seconds (case A7). Approval fatigue is real: Anthropic reports that sandboxing cut its internal permission prompts by 84% (Anthropic), the right way to reduce prompts.

Fails when. You approve by reflex. If you're approving more than you're reading, the task is too big or the sandbox is too loose.

The Goldfish test ​

What. Hand a fresh session (no memory of your work) only the document, and see what it does. A goldfish remembers nothing; if it can't work from the document alone, the document is leaning on context that lives in your head. From Michigan EECS 498's Elephant-Goldfish Model, which requires an "Elephant design document and Goldfish review ledger" before implementation (syllabus; EGM).

How, for a specification:

text
You have only the document below, and no other context about this project.
1. In five sentences, say what you would build.
2. List every question you would need answered before starting.
3. List every assumption you would have to make to start without asking.
Do not write any code.

[paste SPEC.md, or TASKS.md]

How, for AGENTS.md: start a new session in the repository, give it a small real task, and watch whether it runs the right commands, stays in scope and follows the workflow without your help.

Every question and wrong assumption is a defect in the document. Fix the document, not the session, and record the run in AI_LOG.md.

Fails when. You run it in the session where you wrote the document (it remembers), or you answer its questions in chat instead of in the document.

Measuring whether the agent follows it ​

Week 3 asks you to test your AGENTS.md, not just write it.

  1. Pick two real tasks and, for each, two or three rules you can check in the transcript or the diff ("ran the single-test command before finishing", "edited nothing outside src/").
  2. Run each task with and without the file (or with two versions of it), same model, same starting commit, in a fresh session each time. Models are nondeterministic: run each condition at least three times.
  3. Record what you observed per run: rule followed, partly, or not, with the evidence.
  4. Report counts, not adjectives, and scope the claim to the sample. Stanford CS146S's assignment puts it well: "Three repos is a small sample. Scope your claims to what it supports" (W5 spec).
