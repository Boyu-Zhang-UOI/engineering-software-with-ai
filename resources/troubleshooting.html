Troubleshooting ​

Something broke. Find it below, work through the steps in order, and stop when it's fixed. Limits and which tool is the fallback are in Tool Handout; this page says what to do.

Jump to: API errors · Request too large · Out of allowance · Local model ignores tools · Lab machine · Codespaces · Class codebase won't build · Worktrees · CI · MCP · Agent damage · Committed a secret · Still stuck

TIP

Before anything else: what did you expect, what happened instead (the exact error text), and what changed since it last worked? Write the three answers down. They solve many problems on their own, and they are the first thing staff will ask.

Running out of a free allowance is not a reason to be late. Switching to the fallback is part of the course, and so is logging the switch in AI_LOG.md.

My API call fails (401, 404, 429) ​

StatusUsually meansDo this
401 or 403Wrong, revoked or missing key; or the key is for a different provider than LLM_BASE_URLCheck the variable is set without printing it: test -n "$LLM_API_KEY" && echo set. Check .env and Codespaces secrets don't both set it. Make a new key if in doubt
404Wrong base URL (often a missing or doubled /v1 or trailing slash) or a model ID the provider doesn't serveCompare LLM_BASE_URL and LLM_MODEL with Tool Handout: LLM APIs for the kits character by character. List the models your key can use: curl -s "${LLM_BASE_URL%/}/models" -H "Authorization: Bearer $LLM_API_KEY"
400The request is malformed: often a tool schema the provider rejects, or a parameter it doesn't supportRead the error body; it usually names the field. Try the smoke test against the same provider
429Rate limit: requests or tokens per minute, or a daily capWait and retry with exponential backoff (mini-agent does this). If it persists, you've hit a daily cap: switch provider by configuration (api-keys)
5xxThe provider is having a bad dayRetry later, or switch provider

"Request too large", or the context is full ​

Some free tiers cap tokens per minute below the size of one agent turn (system prompt + tool schemas + file contents). The request is rejected however long you wait.

  1. Use that provider only for the kits, whose prompts are lean, not for an IDE or CLI agent (Tool Handout: Spreading the work across free allowances).
  2. In mini-agent: read file ranges instead of whole files, trim tool output before returning it, and compact or drop old turns (a week 2 extension).
  3. For a CLI agent: start a fresh session, give it fewer files, or move to a provider with a larger allowance.

I ran out of a free allowance ​

  1. Switch now, to the next tool in the stack table, and note it in AI_LOG.md. Don't add a payment method (rule 6).
  2. Copilot credits gone? Completions still work. Move agent work to your Gemini key, the lab machine or Zed Student until the 1st of the month.
  3. Codespaces hours gone? Use a dev container on your laptop (sandboxes), or pair with a teammate.
  4. Spend less per task next time: smaller tasks, fresh sessions, Ask mode for questions, and the lab machine for anything repetitive (eval runs, batch jobs).
  5. Tell staff if it happens before mid-month: it may mean a lab assumes more capacity than the free tiers give, and TOOLS.md needs fixing.

The local model ignores its tools ​

Symptoms: the model answers in prose, prints a shell command as text, or the agent loop ends after one turn with no tool call.

  1. The context is too small (the usual cause). Ollama truncates long prompts silently, cutting the tool definitions. Restart the server with OLLAMA_CONTEXT_LENGTH=64000 (local models) and run the smoke test with padding.
  2. The model can't do tool calls reliably. If the unpadded smoke test also fails, try the next model in TOOLS.md. Tool-calling skill depends on training more than size.
  3. The harness's system prompt is too big for the context you set. Full IDE and CLI agents send far more than mini-agent; use a free API for those.
  4. Everything is slow: the model plus its context doesn't fit in GPU memory, so it spilled to the CPU. Use a smaller model, not a smaller context.

The lab machine is slow or unreachable ​

  • connection refused or a timeout: are you on the campus network or VPN, or using the authenticated endpoint your instructor gave you? A Codespace is outside the campus network.
  • Very slow: it's one queue for the class. Check the class channel for a batch in progress, run your work later, or switch to a free API by configuration.
  • Errors under load: keep your step limit and timeout on; retry with backoff; never leave a loop running unattended.
  • It's down: that's the planned fallback drill. Switch provider and tell staff.

My Codespace won't start, or I'm out of hours ​

  1. Check githubstatus.com.
  2. Out of hours? Codespaces are blocked, not billed, without a payment method. Stop and delete codespaces you aren't using (github.com/codespaces), and use the smallest machine that works.
  3. Won't start: try a private browser window, or pause extensions that block github.dev and *.app.github.dev.
  4. Stuck building: open the creation log (View creation log) and read the last error. A failing postCreateCommand in devcontainer.json is the usual cause.
  5. Meanwhile, use a dev container on your laptop, or github.dev (press . on the repository page) for reading and small edits.

The class codebase won't build ​

  1. Follow The Class Codebase exactly, in a fresh codespace, before improvising.
  2. Check the runtime version it needs against node --version / python3 --version. The course standardizes on the versions in Tool Handout: Free infrastructure.
  3. Too slow or out of memory on 2 cores? Try 4 cores for the build only (it uses hours twice as fast), then go back.
  4. Ask your team: someone may already have hit it. Post the exact error in the team channel, then to staff.
  5. Don't let an agent "fix" the build by editing lockfiles, CI config or dependency versions without a plan you've approved.

Git worktrees ​

ProblemFix
fatal: '[branch]' is already checked out at …A branch can be checked out in only one worktree. Create a new branch: git worktree add ../dir -b new-branch
npm test fails in the new worktree but works in the main oneEach worktree has its own working files: run npm install there
Two servers fight over a portGive each worktree its own port (an environment variable or a command-line flag)
A deleted worktree directory still shows in git worktree listgit worktree prune
Removing a worktree with uncommitted workgit worktree remove refuses; commit or stash first, or check what you'd lose before adding --force
Agents in two worktrees edited the same fileA merge conflict you scheduled. Resolve it yourself, at the merge point you named (agent patterns)

Never let an agent run git worktree remove --force, git reset --hard or git clean -fdx without your approval.

CI minutes and failing workflows ​

  • Minutes running out? Standard runners are free on public repositories; your team fork is public, so check that the workflow runs there and not on a private copy. Larger runners are billed even on public repositories: use the standard ones.
  • Cut waste: add concurrency with cancel-in-progress: true so a new push cancels the old run; use paths filters so docs-only changes skip the test job; cache dependencies.
  • A workflow from a fork has no secrets: that's intended. Never "fix" it by using pull_request_target with a checkout of the fork's code.
  • CodeQL or Semgrep fails the build: read the finding before you suppress it. A suppression needs a comment saying why, and a reviewer.
  • Self-hosted runner on a lab machine: trusted repositories only, never pull requests from forks.
  • An agentic workflow or AI reviewer ran up usage: check its per-run cap first (rule 6), then disable it until it's lowered.

MCP: the server won't connect ​

  1. Run the server by hand from the exact command and working directory the client uses. Does it start? Does it exit with an error?
  2. Nothing may go to stdout but protocol messages. Over stdio, each line on stdout must be one JSON-RPC message. A stray console.log or a startup banner breaks the connection; log to stderr instead.
  3. Paths. Clients often launch servers from a different working directory. Use absolute paths in the client's config, or resolve paths relative to the server file.
  4. Exercise it with MCP Inspector (npx @modelcontextprotocol/inspector [command]) or the kit's own client script, to separate server bugs from client bugs.
  5. Protocol versions. The specification changes, and newer clients may skip the initialize handshake that older servers expect, or send the version differently (Tool Handout: Free infrastructure). Check which version the client speaks; make the server answer tools/list sensibly either way.
  6. Old tutorials. Many 2025 tutorials import the legacy SDK. Code that mixes the legacy and current SDKs fails in confusing ways.
  7. A server you didn't write won't start? Read its startup command before you run it: launching a server is running its code (rule 8).

The agent broke or deleted things ​

  1. Stop the agent. Deny the next approval, or interrupt it.
  2. git status and git diff to see what changed. git stash or git restore . to discard uncommitted changes, or git switch back to your last good branch.
  3. If it committed: git log --oneline -5, then git revert [commit] (safe on shared branches) or reset your own unpushed branch.
  4. Pushed to the team fork? Your pushed history is the backup. main should be protected; if it isn't, tell your team today.
  5. Write down what it did and why your approvals let it through. That's a threat-model finding (THREAT_MODEL.md template).

I committed a secret ​

  1. Revoke the key at the provider first. Deleting the commit doesn't un-leak it.
  2. Make a new key; put it only in .env or a Codespaces secret (api-keys).
  3. If the commit was never pushed: amend or rebase it out, and check git log -p for any other copy.
  4. If it was pushed: tell your team and staff. On a public fork, assume it's been seen. Cleaning history (with a tool such as git filter-repo) and force-pushing is a team decision, and forks keep the old history anyway: the revocation is what protects you.
  5. Run the history-aware secret scan your kit or fork uses, to make sure there's no other copy.

Still stuck ​

  1. Ask your team, then the class channel, with your three answers (expected, actual, what changed) and the exact error.
  2. Ask staff in the Lab or office hours. A tool problem that blocks more than one student is a TOOLS.md problem: open a tool change issue.
  3. If an AI tool helped you debug, say so in AI_LOG.md, and tag what it told you as inferred until you've confirmed it.
