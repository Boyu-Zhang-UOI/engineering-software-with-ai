API Keys, Tokens and Spending Caps ​

How to keep keys out of repositories and away from agents, how to scope tokens, and how to switch the kits between providers or the lab machine by configuration alone.

Read this before week 1's Lab. It applies safety contract rules 4, 5 and 6.

Why it matters more with agents. A coding agent reads files and runs commands. Anything it can read, a prompt injection can ask it to send somewhere (case studies), and any credential it can find, it may use: in one 2026 incident an agent deleted a production volume with a token it found in an unrelated file (PocketOS). Stolen AI keys are now a malware target in their own right (supply chain). So the course's keys are built to be worth nothing if stolen: free tier, no payment method, one purpose each.

The four rules ​

  1. A key never enters a repository, a chat, an issue, a PR, a log or a screenshot. Not even in a commit you plan to delete: history keeps it.
  2. Every key is free-tier with no payment method, so its spending cap is zero. Where a service needs a card, set the lowest hard cap it offers and turn off automatic top-ups. A budget alert is not a cap.
  3. Every token is scoped to one job, one repository and the fewest permissions, with an expiry date.
  4. An agent session that reads untrusted text has no real secret in reach. The one exception is unavoidable: the agent's own model key has to be in its environment for it to work at all. That's why that key must be free-tier with no payment method, worth nothing to steal. Everything else (GitHub tokens with write access, other providers' keys, .env files from other projects) stays out of any session that reads issues, web pages, the class codebase or another team's code.

Keys in .env ​

The kits read three environment variables and speak the OpenAI chat-completions format:

VariableWhat it holdsSecret?
LLM_BASE_URLThe provider's OpenAI-compatible base URLNo
LLM_API_KEYYour key (for Ollama, any non-empty string)Yes
LLM_MODELThe model IDNo

In a kit's folder, create a .env file (most kits ship a .env.example to copy; the kit's README lists its variables):

bash
cp .env.example .env
git check-ignore -v .env

The second command must print the .gitignore line that ignores .env. If it prints nothing, stop and fix .gitignore before you put a key in the file. Then fill in .env with the values for your provider from Tool Handout: LLM APIs for the kits:

text
LLM_BASE_URL=[base URL from TOOLS.md]
LLM_API_KEY=[your key]
LLM_MODEL=[model ID from TOOLS.md]

Better still, use a Codespaces secret for LLM_API_KEY: github.com → Settings → Codespaces → New secret, scoped to the one repository that needs it. The key then never exists as a file in the project, so neither git add . nor an agent's cat .env can expose it. Keep LLM_BASE_URL and LLM_MODEL in .env. Put each variable in one place only. Check it arrived without printing it:

bash
test -n "$LLM_API_KEY" && echo "LLM_API_KEY is set"

WARNING

A Codespaces secret is still visible to an agent that runs env or printenv in that codespace. The protection is against committing the key, not against an agent. That is why the injection lab (week 4) uses a worthless canary instead of a real key, and why a codespace in which an agent reads untrusted text gets no secrets attached (sandboxes).

Switching provider, or using the lab machine ​

Because every kit reads the same three variables, switching provider is a configuration change: edit .env (or the Codespaces secret), restart the kit, and nothing in the code changes. You'll do this on purpose in week 1, and for real whenever a free tier runs dry.

To useLLM_BASE_URLLLM_API_KEYLLM_MODEL
The primary free APIfrom Tool Handout: LLM APIs for the kitsyour primary keythe suggested model in TOOLS.md
The fallback free APIfrom TOOLS.mdyour fallback keyits suggested model
The lab machinehttp://[lab-machine-host]:11434/v1 (your instructor gives the host)ollama, or the class token if the instructor set onethe lab model in TOOLS.md
Ollama on your laptophttp://localhost:11434/v1ollamathe laptop model in TOOLS.md

Keep one file per provider (.env.gemini, .env.groq, .env.lab) and copy the one you want over .env. The kits' .gitignore files ignore .env and .env.* (except .env.example); in any other repository, add both patterns before you create the files, and check with git check-ignore -v .env.groq. Log every switch in your AI_LOG.md: a result produced by a different model is a different result.

NOTE

Model output differs by provider. A prompt that works against the primary may fail against a small local model, and a test that passes on recorded responses may fail live. When you switch, re-run the kit's tests and one real task before you trust the switch.

Scoped tokens ​

An agent needs a GitHub token when it works with issues or pull requests, and a CI workflow needs one to post results. Give each the least it needs.

Fine-grained personal access tokens (github.com → Settings → Developer settings → Personal access tokens → Fine-grained tokens):

  • Repository access: Only select repositories: one repository, your team fork.
  • Permissions: start with Contents: Read and Metadata: Read. Add Pull requests: Write or Issues: Write only when a task needs it, and only for the token used by that task.
  • Expiration: the end of the lab or the milestone, never "no expiration".
  • Name it for its job (week13-jules-roomly-fork), so you can tell what to revoke.

In GitHub Actions, set the workflow's permissions: block to the minimum (contents: read by default) and grant write permissions per job. Workflows triggered by pull requests from forks must never get secrets.

For MCP servers that reach GitHub, use a read-only token where the task allows it. A public issue once led an agent with a broad token to copy private-repository data into a public PR (case study); a read-only token removes the way out.

Never give an agent a classic personal access token, your SSH key, a token with admin or delete_repo scope, or a cloud console credential.

Spending caps at zero ​

On every metered service, the cap is zero or the lowest value the service allows:

  • No payment method on any account used in the course. GitHub Codespaces and Actions, for example, are blocked rather than billed when the free quota runs out, if there's no card.
  • Copilot: don't set a paid budget. When the allowance runs out, switch tools.
  • Agentic workflows and cloud agents: never run one whose per-run cap could exceed a free allowance. GitHub Agentic Workflows' default per-run cap is far larger than a student's monthly allowance; lower it before the first run (Tool Handout: Free infrastructure; contract rule 6).
  • Department-funded credits (if your instructor provides them): a hard limit set by the department, per student, with no automatic top-up.

Never in a repository ​

Before your first commit in any repository:

bash
git check-ignore -v .env
git status --short

Before every push from week 4 on, run the secret scan your kit or team fork provides (week 10 adds a history-aware scan), and keep GitHub's push protection on in your public forks (Settings → Code security). Push protection is free on public repositories and blocks pushes that contain known key formats, but it recognizes only formats it knows, so it is a backstop, not a plan.

Things that leak keys in practice: a debug console.log(process.env), a trace file committed with request headers in it (mini-agent's trace must never record the key), a screenshot of a terminal, a pasted error message that includes the request, and a .env.local that .gitignore didn't match.

If a key leaks ​

Pasted into a chat, committed (even to a branch), shown on a shared screen or in a screenshot:

  1. Revoke it now, at the provider, before anything else. Deleting the commit doesn't help: forks and clones keep history.
  2. Make a new key and put it only in .env or a Codespaces secret.
  3. Check usage on the provider's dashboard for anything you didn't do.
  4. Tell your instructor. Reporting quickly is always the right call, and on a free-tier key with no card the damage is usually nil.
  5. If it reached a public repository, follow troubleshooting: I committed a secret to clean the history, after revoking.
