Sandboxes: Codespaces and Dev Containers ​

Where to run an agent on code you didn't write, and exactly what that protects you from.

Read this before week 2, when you first point an agent at the class codebase. It applies safety contract rules 3 and 4.

Where you run an agent decides the worst case. An agent reads files and runs commands with your permissions. On your laptop, the worst case is your laptop: your home folder, SSH keys, browser sessions, every other repository. In a sandbox, the worst case is the sandbox. The course treats three things as untrusted code: the class codebase and any other repository you didn't write, other teams' forks (the PR round), and the injection-lab kit, which is hostile on purpose.

The options ​

SandboxWhat it isUse it forCost
GitHub Codespaces (default)A cloud VM running VS Code, created from a repositoryEvery lab; anything untrustedFree monthly hours (Tool Handout: Free infrastructure)
Dev container on your laptopA Docker container described by the repository's .devcontainer/devcontainer.json, opened with VS Code's Dev Containers extensionWhen Codespaces hours run out; when you need the lab machine on the campus networkDocker Desktop is free for educational use
Docker Sandboxes (sbx)Each agent in its own microVM, on your laptopRunning a CLI agent with stronger isolation than a containerFree locally
The agent's own sandbox modeFor example Copilot's local sandboxing, switched on with /sandbox enableAn extra layer inside one of the above, never instead of itFree; off by default

The same .devcontainer/devcontainer.json drives both Codespaces and a local dev container, so a repository that works in one works in the other.

Running an agent on untrusted code, step by step ​

  1. Get the code from its URL, never from a folder someone sent you. A received folder (zip, shared drive, USB stick) can carry a .git/config that makes git run an attacker's program the first time any tool runs git status, before an agent's approval prompt appears (case study A6). If you must open a received folder, read .git/config and list .git/hooks/ first, with the agent closed.
  2. Create the codespace with no secrets attached. In Settings → Codespaces, your secrets list which repositories may use them; a repository with untrusted content gets none except the agent's own free-tier model key (no payment method, so worth nothing to steal). No GitHub token with write access, no other provider's key.
  3. Read the dev container config before you build it. devcontainer.json can run commands (postCreateCommand, features, a Dockerfile) when the container is created. Someone else's config is someone else's code (contract rule 8).
  4. Read the agent instructions before the agent does. AGENTS.md, CLAUDE.md, .cursor/rules, .github/copilot-instructions.md, skills folders and MCP configs in the repository are instructions to your agent, written by a stranger. An agent can be told to start an MCP server declared in an untrusted repository's config (Tool Handout: Not verified lists the advisory, unverified). Read them; disable what you didn't write.
  5. Keep approvals on for every command and every write (rule 2).
  6. Commit or stash before the agent starts, on a branch, so you can see and undo everything it did (rule 7).
  7. Stop the codespace when you finish, and delete it when the task is merged.

What a sandbox does and doesn't protect ​

A sandbox moves the blast radius; it doesn't remove it. Anthropic's engineering team puts it this way: both filesystem isolation and network isolation are needed, because without either one a compromised agent can escape or exfiltrate (Anthropic). A Codespace gives you the first, not the second.

AssetProtected in a Codespace or dev container?Why
Your laptop's files, SSH keys, browser sessionsYesThey aren't in the sandbox (unless you mount them into a dev container: don't)
Your other repositories' filesYesOnly this repository is cloned
Secrets attached to the sandbox (Codespaces secrets, .env)NoThe agent can read them with env or cat. Attach none where untrusted content is read
The repository itselfPartlyThe codespace holds a token that can push to its repository. Branch protection on main and your pushed history limit the damage
Data sent out over the networkNoCodespaces have open outbound internet. A filter in the harness (week 4 builds one) is a speed bump; only network isolation enforced outside the agent stops exfiltration
Your free API allowanceNoA runaway loop spends it from inside the sandbox. mini-agent has a step limit for this reason
Your GitHub accountPartlyOnly as far as the tokens inside the sandbox reach. Scope them (API Keys, Tokens and Spending Caps: Scoped tokens)
Correctness of what gets mergedNoThat's verification and review, weeks 6–9

Network isolation, in practice. When a step needs no network (running a received repository's tests after dependencies are installed, for example), run it in a container with networking off:

bash
docker run --rm --network none -v "$PWD":/work -w /work node:22 npm test

An agent needs the network to reach its model, so it can't simply run offline. The course's layers, from weakest to strongest: an egress filter in the harness that inspects commands (week 4; the injection-lab kit documents how encodings, variables and other tools get past a string filter), removing the tools that can send data out from any agent that reads untrusted text, and no secrets in reach. If there's nothing worth stealing and no tool to send it with, prompt injection has much less to work with.

Dev containers on your laptop ​

When Codespaces hours run out, or when you need to reach the lab machine on the campus network:

  1. Install Docker Desktop (free for education) and VS Code's Dev Containers extension.
  2. Clone the repository from its URL.
  3. Read .devcontainer/devcontainer.json (step 3 above).
  4. Command Palette → Dev Containers: Reopen in Container.
  5. Don't add mounts of your home folder, ~/.ssh or ~/.config to devcontainer.json. If the config already has them, remove them.

A container shares your laptop's kernel, so it is weaker isolation than a VM. For a hostile repository (injection-lab, a stranger's fork), prefer a Codespace or Docker Sandboxes.

Never on the lab machine ​

Students use the lab machine's model API, not its shell. Never run an agent, a received repository or a test suite on the lab machine itself: one compromised session there affects the whole class's queue.
