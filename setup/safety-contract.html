Agent Safety Contract ​

Read it in week 0. Sign it on Canvas in week 1. It is personal, so don't commit it to a repository.

This contract is adapted from the sibling course's nine-rule safety contract (Building Apps with AI), rewritten for agents that run on large codebases you didn't write, with MCP servers, CI and other people's repositories in reach. Each rule has a short version, the week the course teaches it, and the incident or study behind it. The incidents are in Case Studies.

Why a contract, not just advice. An AGENTS.md line that says "never delete the database" is advice the agent may ignore; in two well-known incidents agents deleted production data despite explicit instructions (Replit; PocketOS). What holds is the setup around the agent: approvals, sandboxes, scoped tokens, empty wallets. These rules are about that setup, and they are yours to keep, because the agent can't.

How the course backs you up. Labs run in Codespaces; the kits are built with an approval gate, a workspace guard and a step limit; the injection lab uses a worthless canary instead of a real key; graded work stays in a class fork, not in maintainers' repositories. If you break a rule by accident, say by committing a key, tell your instructor the same day. Reporting quickly is always the right call, and the fix is usually small.

The eleven rules ​

1. The data rule ​

Short version: free tiers may train on your prompts, so they see only public open-source code and course kits. Week 0 and week 1.

I send free-tier AI services only public open-source code, the course kits and my own course work. Never personal data, grades, secrets, unreleased research code, an employer's code, or code I don't have the right to share. I turn off training wherever a setting exists (accounts).

Why: the Gemini API's free tier is "used to improve our products" with human review and no opt-out, and Copilot's individual plans train on interaction data unless you opt out (Tool Handout: The data rule).

2. Approvals stay on ​

Short version: the agent asks before every command and every write, unless I allowlisted that exact command. Week 1 (you read the kit's approval gate, and may extend its approval policy).

I never use autopilot, "yolo", auto-approve or skip-permissions modes, except where a lab explicitly says to, inside a throwaway sandbox with no secrets attached. Allowlists contain only read-only commands I named (ls, git status, git diff), never a shell, an interpreter or a package manager's install command; I remember that a test command runs whatever the tests contain. An agent may not edit its own permission settings: I review any change to an agent's config files as carefully as a change to its code.

Why: injected text made Copilot set its own auto-approve flag, switching off the very prompts meant to stop it (CVE-2025-53773). In autopilot mode, a web page sent a project's secrets to an attacker in about 28 seconds, and the vendor said the user had chosen full autonomy (case A7). Anthropic reports that sandboxing cut permission prompts by 84%, which is how to fight approval fatigue: fewer, better prompts, not none (Anthropic).

3. Untrusted code runs in a sandbox ​

Short version: a repository I didn't write is opened only in a Codespace or a dev container, cloned from its URL. Week 2 (the class codebase) and week 4.

The class codebase, other teams' forks, upstream projects and the injection lab run only in a sandbox (sandboxes). I clone from the URL; I never open a received folder with an agent. I read a repository's agent instructions, MCP configs and dev container config before an agent or a build uses them.

Why: a received folder can carry git settings that run an attacker's program before any approval prompt appears (case A6). Planted instructions in project files made agentic editors run malicious commands up to 84% of the time (Liu et al.).

4. No real secrets near an agent ​

Short version: an agent session that reads untrusted text has nothing worth stealing in reach. Week 1 (keys) and week 4 (the canary).

My keys are free-tier, with no payment method, kept in .env or a Codespaces secret, never in a repository (api-keys). A sandbox in which an agent reads issues, web pages, PRs, the class codebase or another team's code has no secrets attached beyond the agent's own free-tier model key, which is worth nothing to steal. No agent ever sees a production credential, my SSH key, a cloud console login, or a classic personal access token.

Why: an agent holding a database service key read instructions in a support ticket and copied secrets into a reply the attacker could see; Willison's "lethal trifecta" (private data, untrusted content, a way out) explains why (case A1). Malware now hunts specifically for AI keys and agent configs (case B4).

5. Scoped tokens only ​

Short version: every token does one job, in one repository, with the fewest permissions, and expires. Week 4; again in week 13 (cloud agents).

I use fine-grained tokens limited to one repository, read-only unless a task needs a write, with an expiry date, named for their job (how). CI workflows get contents: read unless a job needs more. MCP servers that reach GitHub get a read-only token where the task allows.

Why: a malicious public issue led an agent with a broad GitHub token to copy private-repository data into a public pull request (case A2). An agent deleted production data with a token it found in an unrelated file, made for a different job (case C2).

6. Spending caps at zero ​

Short version: nothing in the course can spend money; anything metered has its cap at zero or the lowest value allowed. Week 0; week 9 (CI) and week 13 (agentic workflows).

No payment method on any course account. No paid budget on Copilot. I never run an agentic workflow or cloud agent whose per-run cap could exceed a free allowance: I lower the cap before the first run. Department-funded credits, if any, have a hard limit and no automatic top-up.

Why: GitHub Agentic Workflows' default per-run cap is several times a student's monthly Copilot allowance (Tool Handout: Free infrastructure). Stolen AI keys have run up charges of more than $1,000 (case B4). An empty wallet is the only cap that can't be misconfigured.

7. Save points before and after ​

Short version: commit before an agent starts and after it finishes, on a branch or worktree; backups live where the agent can't reach them. Week 1; worktrees in week 13.

Every agent task starts from a clean commit on its own branch (or git worktree) and ends with a commit I've read. Agents never run git push --force, git reset --hard or history rewrites without my approval. main in the team fork is protected; my pushed history is my backup.

Why: an agent's undo is not a backup. In the PocketOS incident the backups sat on the same volume the agent deleted (case C2).

8. Read before you adopt ​

Short version: an MCP server, skill, rules file, AGENTS.md, GitHub Action, dev container or package is someone else's code until I've read it. Week 3 (MCP and AGENTS.md) and week 10 (supply chain).

I install only what my plan named. I check that a package exists, is the one I meant and is maintained, and I pin its version. I read every MCP server's tool descriptions, every skill and every rules file before an agent loads it, and I pin Actions to a version I've read.

Why: MCP tool descriptions can carry hidden instructions the user never sees, and a server can change its descriptions after approval (case A3). Models invent package names that attackers then register (case B5), and real, popular packages get hijacked too (case B1).

9. Verify, and say how ​

Short version: every claim about code, an agent or a tool is tagged observed (I ran or read it) or inferred (I or the AI concluded it), and only observed claims count as verified. Week 1 (trace dissection); tests in weeks 6–7.

I run the tests myself and read the output. I check that an agent didn't weaken, skip or delete a test to make it pass. I don't merge what I can't explain.

Why: tests written after the code tend to agree with its bugs (Konstantinou et al.); LLM-generated oracles capture what code does, not what it should do (Konstantinou, Degiovanni & Papadakis); and about half of functionally correct backends generated by the best model in one benchmark were exploitable (BaxBench).

10. No unattended agents in other people's spaces ​

Short version: no agent posts, comments, opens or reviews anything in a repository I don't own without me reading it first; I write my own PR descriptions. Week 9 (the PR round); weeks 12–15 (optional upstream PRs).

No agent publishes anything (a repository, gist, release, issue, comment or PR) without my approval. In other teams' forks and upstream projects, every word posted under my name is one I wrote or read and approved; PR descriptions and review comments I sign are my own writing (🔴 AI off). Upstream, I follow the project's own AI policy when it is stricter than the course's, keep one open PR per project, and can explain every line.

Why: agents asked for screenshots created public repositories and published more than 13,000 internal images, with no attacker involved (case A8). LLVM bans agents that act "without human approval" and asks for self-written PR descriptions (case E3); maintainers have closed their bug bounty and throttled PRs because of AI-generated noise (cases E6–E7).

11. Disclose AI help ​

Short version: AI_LOG.md in every repository, an Assisted-by: trailer on AI-assisted commits, and the PR template's AI section filled in honestly. Week 1.

My AI_LOG.md records each significant session: tool and model, what I delegated, what I verified and how (template). AI-assisted commits end with Assisted-by: [tool and model]. I never let an agent add a sign-off or attribution on my behalf.

Why: detectors that try to spot agent-written commits reach a precision of only 0.332 at realistic prevalence, so "detection cannot replace recorded attribution" (Horikawa et al.). The Linux kernel's rule is blunt: "AI agents MUST NOT add Signed-off-by tags" (case E4).

And three project rules ​

  • No real personal data. Test data is made up. The class codebase and kits contain none.
  • No human-subjects research without IRB approval. Graduate studies use public datasets or your own artifacts, never classmates or maintainers as subjects (case E8; template).
  • Nothing you'd miss if an agent deleted it. Real documents stay out of agent workspaces.

Signature ​

On Canvas, in week 1: open the safety contract assignment and type the statement below with your name and the date.

I have read the agent safety contract and will follow it in this course, from the week each rule is taught. If I'm unsure whether something is safe, I will ask before I do it. If I break a rule by accident, I will tell my instructor the same day.
