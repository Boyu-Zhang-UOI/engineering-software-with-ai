Upper-Division, Graduate, and Semester-Length AI-Assisted SE Courses: Research for the Course A / Course B Split ​

Research notes compiled 2026-11-02 for the split of "Building Software with AI" (since renamed Building Apps with AI) into Course A (CS 2xxx, campus-wide, one prior programming course) and Course B ("Engineering Software with AI", CS 4xxx/5xxx joint-listed, prereq CS 3383).

Scope and method.

  • These notes are a delta on research/notes/university-courses.md (2026-09-25), research/notes/2026-10/university-courses-fall-2026.md (2026-10-21), and research/landscape-report-2026-09.md. Courses already covered there are revisited only where new week-by-week or assignment detail is now public.
  • Primary sources were read directly where possible: course sites fetched with curl, GitHub repos read through the GitHub API, PDFs converted with pdftotext.
  • Claims that rest only on a search-engine summary are marked "(search summary)". Anything I infer is marked Inference.
  • One CMU 15-113 source is a draft paper linked from the public course site but marked "In submission. Do not distribute." I paraphrase it briefly and do not quote it at length.

UT Austin CS 378 "Agentic Software Engineering" (Fall 2026, Emmett Witchel) ​

The most fully published new course, and the closest to Course B in level, though it leans toward systems rather than SE.

Framing and grading

  • It treats "use of AI coding agents as a form of technical writing that should be practiced and can be improved": students learn to split a problem into "what you specify, what you delegate, and what you verify." Prereq: C S 439 plus Python and git; "No prior AI/ML experience required." Topic mix: agent tools and architecture 30%, systems 25%, SE 20%, how models work 10%, tooling 15%. — CS 378 home
  • Weights: end-of-class quizzes 12%, homeworks 58%, final project 30%. Each class ends with a 5-minute, 3-question quiz (four lowest dropped), and each homework due date opens with a 7-minute individual quiz on that homework. All quizzes are AI-free, with "only a single browser tab open." — CS 378 home

Homework design

  • Homeworks arrive "in beats": "you build v1 against a spec, then the spec changes under you — new drops arrive mid-homework, the way real software changes." — CS 378 home
  • HW0 dotfiles (completion); HW1 email-index (search engine, then "resilience: mutation, crashes & concurrent search"); HW2 tm-compute (rank Turing machines "under a tight compute budget", then a "PR round in a peer's repo"); HW3 concurrent-index (race a baseline, compare two design variants, "synthesize a design based on evidence"); HW4 pdf2md (auditable tables from PDFs, then arXiv transfer). Pairs are allowed but "you must work with a different partner each time." Each writeup includes self-contained insight slides, some shown in class. — CS 378 home

Final project, tools, and process evidence

  • Solo or pair; 2-point proposal, 23-point repository plus live defense, 5-point slide writeup (six slides, "including two design or evaluation decisions and a debugging story"). "Feature count, repository size, token spend, prompt volume, and visual polish do not substitute for demonstrated behavior, reproducible checks, controlled engineering decisions, or honest limitations." — CS 378 home
  • Codex and Claude Code are provided through ChatGPT Edu and UT's Claude access, with "no personal subscription cost". Students manage their own credits ("It is not acceptable to turn in a homework with a note that, 'I would have done X, but I ran out of credit…'"), and the course concedes that "students who add more generous personal subscriptions have an advantage." "Commit history is part of the evaluation", and forum hints stay "deliberately vague" because "AI agents often need only a hint." — CS 378 home

Week-by-week (condensed) — CS 378 schedule

  • W1 setup, coding-agent fundamentals · W2 token efficiency, workflow skills, "Models should verify each other"; SQLite · W3 prompt injection and the lethal trifecta; permissions and sandboxing; crash consistency; maintaining agent guidance · W4 WAL; "Parallelize a task once you can name its merge point" · W5 how assumptions become architecture; git data model; pull requests · W6 quiz, guests · W7–8 concurrency, linearizability, performance; PR round; mid-semester feedback; proposal due · W9 protecting secrets; using secrets safely with agents · W10 virtualization, containers, GPUs, serving · W11–12 what a language model is, transformers, pre/post-training · W13 "Rewards and benchmarks: A test suite rewards and grades until its answers leak" · W15 demos and defense.
  • Extra decks include "Sandbox mechanics: namespaces, cgroups & seccomp" and "Claude Code Unpacked: the agent loop, mapped from source".

Michigan EECS 498-016 AASE: what changed since the baseline ​

Schedule now published through Week 10. L01–L04 cover the landscape, how LLMs code, context/model/prompt, and spec-driven development; L05–L11 agentic CLIs, orchestration, the raw call, Hackathon 1, stop conditions and approval, skills and the Elephant-Goldfish Model, guardrails; L12 is a course feedback session; L13–L18 browser extensions, subagents, compaction and caching, memory, knowledge bases, "Many Models, One Harness". Weeks 11–15 are TBD. — AASE syllabus

The Analyze phase was rebuilt

  • P2 is now "Aider as an agent". It has four parts (a skills loader, a model-driven tool loop, a shell tool behind approval rules, and a stdio MCP client), graded 50% design and 50% working behavior. An "Elephant design document and Goldfish review ledger" must be committed before implementation. — AASE syllabus
  • The former agent-v0 eval suite and teardown report "are no longer required." — AASE syllabus
  • From Lab 03 everyone uses Codex with a Luna model "on course-provided credit". The expected cost stays "$0". — AASE syllabus

Why it changed (Lab03 slides)

  • The lab "replaces the 'Build the agent' lab." — Lab03 slides
  • 49 students answered "If you had Codex for the rest of the course, what would you want to learn?" About 23 wanted to learn to use the tools well, 8 design and specs, 7 orchestration and skills, and 5 context and tokens. "Almost nobody asked what to build with it." — Lab03 slides
  • The new work is in "the real Aider… About 20,000 lines of Python with 12,000 lines of tests". The required order is "Learn, then design, then build", because "A one-shot prompt gives you the model's design, not yours." — Lab03 slides

Takeaway for Course B ​

The two strongest templates are UT Austin CS 378 (individual craft, systems depth, evidence-graded final defense) and Michigan AASE after its pivot (work inside a real 20K-line agent codebase).

Practices worth copying from them:

  • Homework "beats" where the spec changes mid-assignment.
  • A short no-AI quiz at the start of each homework due date.
  • A peer PR round in classmates' repos.
  • Rotating partners.
  • A final defense graded on "demonstrated behavior, reproducible checks… honest limitations" rather than feature count.
  • University-provided agents. Course B's $0 rule needs an equivalent: Michigan's course credit, UT's university accounts, or local models.

Inference: Michigan dropped two plans. One was building an agent from scratch on a small model; the other was a stand-alone eval-suite project. Course B's "build a ~200-line agent" therefore works best as a short early lab, not a multi-week project. It should then be followed by extending a real open-source harness, which also serves the "large existing codebase" goal.

Q2. Team projects on existing open-source codebases ​

How courses run them ​

CMU 17-313 Foundations of SE (Fall 2026): a class fork of a real agent codebase

  • "This semester, we will be building upon opencode, the open source AI coding agent." Students fork "a class-specific fork of opencode" (CMU-313/opencode). "We will ONLY be working with the course specific repo in this class." — 17-313 P1
  • P1B onboarding (95 pts) asks students to remove one or more Qlty-reported code smells by refactoring and to validate the change, plus TypeScript self-study. — P1B
  • In P2 sprints, each student owns one backlog issue on a named branch with a PR to the team repo that has "at least some teammate review". "The PR does not need to be merged yet." Grading uses "a snapshot of your repository (including open branches and PRs)" at the deadline. "You should not submit your changes to the parent opencode repository." — P2B
  • Checkpoint slides must include a video demo or, "if you were not able to make a working build", screenshots that explain "what factors impeded your progress." — P2B

Michigan AASE (Fall 2026) moved its projects into Aider's real codebase (above). Whether students send PRs upstream is not stated. — Lab03 slides

Stanford CS146S (Fall 2026) grades "Open Source Contributions" at 30% and names 15 "Open Source Partners" (OpenHands, marimo, CrewAI, Semgrep, Milvus, Unsloth, cmux, pi.dev, Arize Phoenix, Browserbase, CopilotKit, HeyGen, Vercel, Warp, Anyscale), but no contribution rubric is public. Weeks 3–5 all work on unfamiliar OSS repos: a skill, an AGENTS.md for "a repo you did not write", and a three-repo readiness comparison. — CS146S site; W4 spec; W5 spec. Inference: the partner list plus three onboarding assignments look like a deliberate on-ramp to upstream PRs with maintainers who agreed in advance.

UT Austin CS 378 PR round (peer repos instead of upstream)

  • "every student or pair opens one real pull request against a classmate's tm-compute repository and reviews the pull request that lands on their own", on "a fixed one-week clock". — CS 378 home
  • Repos that fail staff checks are left out of the ring and scored 50/100. A declared opt-out also gets 50. Not showing up scores 0. — CS 378 home

Pre-AI upstream-contribution courses (data on merge rates and grading)

  • Michigan EECS 481, 2018–2022 (Fang, Endres, Weimer et al., FSE 2023):
    • Scale: 1,361 students; 984 reports; 443 projects.
    • Process: students picked a GitHub project, found an open issue, built it locally, and submitted a PR, with a project plan and a final reflection. "Extra credit points were awarded for contributions merged… before the end of the semester."
    • Acceptance: 44% of student PRs were accepted. Solo 47% (266/561) vs pairs 39% (166/428). OSS-for-social-good projects 53% vs 40%.
    • Experience: 42% found it more stressful than expected; 1.6% called it terrible.
    • The authors' advice: "avoid mandatory grading of whether pull requests are accepted."
    • — Fang et al. FSE 2023 PDF
  • Other merge-rate data. Seneca OSD600, Fall 2021: 54 students, 392 PRs, 277 merged (70%, up from 63% in 2019), with 7–10 upstream PRs of growing complexity alongside labs where students maintain each other's tool; lesson: students "should make smaller PRs". — humphd blog. Toronto ECE444's "Open Source Excursion" listed 46 merged PRs across 40 projects in Fall 2024 (my count), running since 2020. — ECE444 showcase. UIUC CS 491TC (Fall 2018) graded 25% on FOSS work at "+2½% per contributive effort" and "+12½% per accepted pull request." — CS 491TC
  • Cassee et al. (ICSE-SEET 2026) studied a master's SE course in Europe:
    • New barriers: "Conflicting Mentor Guidance" and "Communication Channel Ambiguity".
    • Per the abstract (paraphrased), commit frequency predicted contribution success better than project size or age, and students who chose projects by personal interest succeeded more often.
    • Recommendation (paraphrased): educators should use project-vitality metrics and prepare students for common barriers.
    • — TU/e record; ICSE 2026 listing

Maintainer AI policies and the 2026 environment ​

Policy landscape

  • Hora and Robbes analyzed 1,000 popular repos and found 118 contributor AI policies. Of these, 78% allow AI-assisted contributions, 22% discourage AI use, 51% require disclosure, and 74% require a human in the loop. — arXiv 2605.16706

Three primary-source examples spanning the range

  • QEMU (ban): "Current QEMU project policy is to DECLINE any contributions which are believed to include or derive from AI generated content". The stated reason is DCO and copyright uncertainty. Using AI for "researching APIs… static analysis, or debugging" is allowed if the output is not included. — QEMU code-provenance.rst
  • Ghostty (strict disclosure):
    • "All AI usage in any form must be disclosed". "If you can't explain what your changes do… do not contribute".
    • "Bad AI drivers will be denounced" on a public list that "will block all future contributions."
    • "if you're interested in [learning]… don't use AI, and we'll help you."
    • — Ghostty AI_POLICY.md
  • LLVM (human in the loop):
    • "Contributors must read and review all LLM-generated code"; new contributors should "start with small contributions"; "Passing maintainer feedback to an LLM doesn't help anyone grow".
    • Disclosure uses a trailer such as Assisted-by:. PR descriptions should be written by the contributor.
    • Agents acting "without human approval, such as the GitHub @claude agent" are banned.
    • — LLVM AIToolPolicy.md

Platform and community responses to low-quality PRs

  • GitHub added settings in February 2026 to disable PRs or restrict them to collaborators, and in June 2026 an open-PR cap for non-collaborators that counts agent-opened PRs (cap details from a search summary). — GitHub discussion #187038; Visual Studio Magazine
  • Godot maintainers called AI PRs "draining and demoralizing" (search summary). — The Register, 2026-02-18
  • Hacktoberfest 2026 dropped the PR challenge after "a massive flood of activity and burnout from the rise of low-effort PRs", becoming one-day "Fests" about "building with open source AI". — hacktoberfest.com/llms.txt
  • In the AIDev dataset (456K agent PRs), acceptance was Codex 64%, Devin 49%, Copilot 35%, vs about 77% for humans (search summary of the paper). — arXiv 2507.15003
  • Cautionary case: in 2021 the Linux kernel banned contributions from the University of Minnesota after a research group submitted "hypocrite commits"; how IRB review was handled is disputed in the coverage. — The Register, 2021-04-21; LWN. Inference: one student's behavior can get a whole institution blocked, and Ghostty-style public denouncement lists make that easier in 2026.

Takeaway for Course B ​

Run the semester project in three tiers.

  1. Graded core work in a class fork of a real, active OSS codebase (the CMU 17-313 opencode model).
    • Grade issues, branches, PRs, and team review from a deadline snapshot, so that nothing depends on maintainers.
  2. A peer PR round across teams' forks (the UT Austin model) to practice review at scale and CI gates.
  3. Optional upstream PRs to a short, pre-vetted list of projects. The list should meet five criteria:
    • (a) a written AI policy that allows disclosed assistance (LLVM-style, not QEMU)
    • (b) high recent commit frequency and responsive maintainers (the Cassee et al. vitality metric)
    • (c) labeled good-first issues
    • (d) a maintainer contact made before the term
    • (e) no history of capping or closing outside PRs

Grading. Follow Michigan's advice and grade process evidence, not merge status:

  • issue discussion, a reproduction, tests, and a self-written PR description with an Assisted-by trailer
  • a responsive revision after review
  • a reflection

Merges count as a bonus. Expect roughly 40–70% of PRs to merge based on pre-AI course data. Inference: expect lower rates in 2026, given maintainer pushback.

Rules for students.

  • One open upstream PR per student per project.
  • No agent posting unattended in a maintainer's space.
  • Students must be able to explain every line before asking for review.
  • Staff screen PRs before submission for the first upstream round.

Q3. Undergraduate/graduate differentiation in joint-listed courses ​

UIdaho's own convention ​

  • UIdaho CS catalog entries for joint-listed courses state the graduate difference in one sentence.
  • The common wording is "Additional projects/assignments required for graduate credit". Examples include CS 4200/5200, 4211/5211, 4380/5380, 4441/5441, 4502/5502, and 4602/5602. — UIdaho CS courses
  • Other wordings:
    • "Extra term paper required for graduate credit" (CS 4701/5701 AI)
    • "Additional class presentation and/or paper required for graduate credit" (CS 4615/5615)
    • "Graduate-level research and possible paper or presentation required for graduate credit" (CS 4731/5731)
    • — UIdaho CS courses
  • Registration rule B-11: a student "may only earn credit at the level the student initially completes the course." — UIdaho catalog B-Registration
  • Inference: the Course B catalog entry should name the graduate extra concretely, e.g., "Additional paper presentations and an empirical study required for graduate credit." This matches local precedent and tells students what to expect.

Published rubrics and templates for graduate extras ​

CU Boulder CSCI 7000-05 (Danny Dig)

  • Paper critique (one page, due before class) has six headings:

    1. What I liked
    2. What I disliked
    3. Future directions
    4. Open questions
    5. Most important for class discussion
    6. Summary

    — Paper Critiques

  • "Tool Experience Report" alternative: read the paper, download the tool, and "use it for your own usecase". The report covers experience, strengths, weaknesses, potential for practical impact, and reflection, including "one improvement" for the tool's creators. — Paper Critiques

  • Presentation rubric (two per student):

    • 30 points: presentation of the content
    • 30 points: "Value added to the content" (hands-on activity, own analysis of the tool)
    • 20 points: effectiveness of the materials
    • 20 points: moderating discussion using classmates' critique questions

    — Paper Presentation

  • Project: "research-oriented or… novel-industrial", teams of 3–4, a proposal, four milestones, and a final. — Research Project

  • Weights: participation 10, critiques 20, presentation 20, project 50. — Syllabus

Cornell CS 6158 (Saikat Dutta). Each class has Presenter 1, Presenter 2, and a Discussant. Presenters give a 15–20 minute talk and lead 10–15 minutes of discussion from "at least 5 questions" drawn from classmates' Perusall comments; discussants submit written answers to all Perusall questions; everyone else posts at least 2 questions per paper and rates presenters. Project milestones: 2-page proposal (W4), 5-minute pitch (W6), 2–3 page midterm report (W9), 5-page final report and 15-minute talk. Reviews may use AI "to understand concepts" but not to generate "entire reviews". — CS 6158 home

NC State GAI4SE gives a "What is a good presentation?" checklist:

  • "Highlight the biggest take-aways"
  • explain why the paper is important
  • explain the characteristics of the data
  • attend to technical details and present results properly
  • "(Bonus) What can be done in the future?"

— GAI4SE README

Takeaway for Course B ​

UIdaho precedent and peer courses support graduate extras worth about 15–25% of the 5xxx grade.

Option A: graduate extras replace undergraduate work (the CMU 17-745 model)

  1. Two paper presentations, using the CU Boulder rubric, drawn from a reading list built from Cornell's and CU Boulder's schedules: SWE-agent, Agentless, SpecBench reward hacking, IFC for agents, AIDev agentic PRs, and METR/RCT productivity studies.
  2. Weekly one-page critiques, with the Tool Experience Report as an alternative.
  3. A small empirical study that replaces one or two undergraduate labs.

Option B: graduate extras added on top (the ANU model)

  • A 1,000-word critical research note attached to the semester project.

Empirical studies should use the team's own data, such as:

  • the team's own PR and review data
  • a mutation-score comparison of agent-written vs human-written tests
  • a replication of an AIDev-style acceptance analysis on public data

IRB caution. Studies must not intervene on maintainers or other students without IRB review. The 2021 UMN case shows the cost of getting this wrong.

Inference: the presentation role structure (presenter, discussant, Perusall questions) lets undergraduates attend graduate presentations as a graded audience at low cost.

Q4. Semester-length (14–16 week) AI-assisted courses for students with one programming course (Course A) ​

CMU 15-113 "Effective Coding with AI", Spring 2026: the full-semester version ​

Logistics and grading

  • Prereq: 15-112. 6 hrs/week (3 in class plus 3 outside). Two 80-minute meetings a week. — 15-113 S26 archive
  • Grading: homework (about 10) 20%, "based on evidence of effort"; participation 20%; three big projects 40%; "infrequent quizzes + 2 exams" 20%, which "will mostly ask you to reflect on tools and strategies". — 15-113 S26 archive

Three-phase, 14-week schedule — 15-113 S26 archive

  • Phase 1, Tools and Exploration (W1–4): first build and HTML crash course; Copilot; Project 1 portfolio due W2; "Tetris 3 ways" (naive prompting, Plan-Adjust-Execute, detailed prompts) and HW2 Crossy Road; APIs, "Build a chatbot in Python", HW3 Explore an API.
  • Phase 2, Strategic Mastery (W5–9): backend basics and HW4 Frontend + Backend; AI, labor, and learning with HW5 readings; Project 2 due W7; spring break; databases and SQLite (guest: "Why AI+SQL is Hard"), HW6; case studies, Project 2 showcase, HW7 Code Handoff.
  • Phase 3, Capstones and Best Practices (W10–14): multi-agent workflows and HW8 "The Agentic Build"; phone apps with Expo (HW9); RAG; "The Agentic Frontier" and Project 3 checkpoint; "How does GenAI work?", best practices, Project 3 due.

How the extra weeks are used

  • The Fall 2026 7-week mini (15-113) covers essentially Spring's weeks 1–7. The rest moved to the second mini, 15-114: databases, case studies, the cutting edge, phone apps, RAG, final topics, and Project 3. — 15-113 F26 site; compare S26 archive

  • Inference: going from the 7-week to the full semester version adds four things:

    • (a) a data/persistence unit
    • (b) a code-handoff exercise that tests documentation
    • (c) spec-driven agentic work from a hand-written SPEC.md
    • (d) a third, more ambitious capstone plus reflection weeks

    Agents arrive only in week 10.

Bridging Python to the web

  • Project 1 assumes "Most students have never built a website before". It asks students to "use AI as a learning tool to master new domains (HTML, CSS, JavaScript)", with a reflection written without AI. — 15-113 S26 archive
  • Python stays in use for the API chatbot, the SQLite CLI, and the Render backend. — 15-113 S26 archive
  • In Fall 2026, Crossy Road moved from a one-hour Python build to "a playable JavaScript game" published on the portfolio. — F26 report

Instructor's draft paper (marked "in submission"; linked from the course site; paraphrased here) — draft PDF

  • Audience: designed for first-year students who have taken one rigorous programming course (AP CS A level or above). About 50 enrolled. 95% named Python as their most comfortable language.
  • HW4 (deployed secure backend) and HW9 (phone apps) were the two hardest. Unsuccessful students on HW4 most often got stuck "in a prompting loop for hours" and did not seek help.
  • After spec-driven development was introduced, students who had the AI write their SPEC.md found the agent's output constrained in ways they did not want. Peer experience changed behavior more than instructor warnings did.
  • In HW7 (code handoff), most students had documented with AI. Most found inherited code documented in enough detail.
  • Students struggled to top their Project 2 idea in Project 3. The instructor suggests saving the best idea for the end.

Agentic Studio (Spring 2026)

  • Taught by Kathi Fisler, Shriram Krishnamurthi, and Michael Littman. Required "at least one prior computer science course". About 20 students were admitted from about 80 applicants. — Brown news, 2026-06-11
  • Projects (teams, Claude Code, journals throughout): an upside-down Tetris, a graduation-requirements checker, and a Signal-like messaging app. — Brown news, 2026-06-11

Other semester-length models ​

ANU COMP4020 (12 weeks) makes the bridge explicit: client-side static apps on GitHub Pages until week 7, then a server and database on Fly.io, with a weekly in-person crit on small, varied briefs ("Forgotten web", "An instrument", "A game", "The ANU system you wish existed"). — ANU course site; ANU lectures

UMD CMSC 389A goes from Python FastAPI to MySQL to React/TypeScript in weeks 2–3, but its prereq is two sophomore courses. — 389A schedule

"Programming with GenAI" (course 11102, Fall 2025) shows the opposite assessment design: "80% of the course grade comes from GenAI-free proctored assessments". — 11102 GenAI page

Takeaway for Course A ​

How to use the extra weeks (inference from CMU's 7- vs 14-week versions, Brown, and ANU):

  • Keep the 8-week course's first half nearly intact, and spread it out. That means portfolio, timed game sprint, API, and frontend plus backend, with more reflection and debrief time.
  • Spend the added weeks on the topics that were thin or failed in short versions:
    • a persistence/database unit, where CMU's understanding scores peaked
    • a code-handoff week as the first "existing code" experience
    • spec-driven agent work only after week 9–10, with a hand-written spec
    • a security/deploy week for secrets and row-level security
    • a third project that is the real capstone
  • Introduce agents late. CMU did so at week 10 of 14 and Brown in the last month. Pair the agent weeks with code review and defense of decisions, which Brown found essential.
  • Bridge from Python to JavaScript the way CMU and ANU do:
    • First project: an AI-built static HTML/CSS/JS site on GitHub Pages.
    • Small Python scripts (API calls, SQLite) stay in parallel.
    • Then a Python backend (FastAPI/Flask) behind a JavaScript frontend.
    • Avoid mobile apps. CMU found them the hardest and the least understood.

Takeaway for Course A ​

What evidence supports

  • Labs on existing code work when they start with comprehension. In the 17-316 Hextris activity, students explain AI-generated docs to a neighbor before changing anything.
  • CMU's code-handoff week is a cheap, proven option.
  • Avoid mobile apps and multi-agent teams, which were the hardest and least understood.

Where security fits

  • Security is better taught through the student's own deployed app (secrets, keys) than through an abstract injection lab.
  • Inference: a short "your agent read a malicious README" demo in the agent weeks is enough at this level.

Takeaway for Course B ​

Sequencing the labs

  • Keep the 200-line agent as a one-week lab, with a mini-swe-agent-style bash-only design and a trace dissection.
  • Then move straight into extending a real harness or codebase. This is how both Michigan and CMU 17-313 converged on "large existing codebase" learning.
  • Teach prompt injection with UT Austin's framing (lethal trifecta, then permissions and sandboxing, then secrets for agents) in weeks 3–4, before students give agents broad access in the team project.

Mutation testing and AI review

  • Mutation testing of AI-written tests is an open niche: no course has published results. It suits a graduate empirical study and a Course B lab graded on mutation score rather than coverage.
  • For AI vs human review, the Oliveira et al. capstone data say tooling reliability and instructions matter more than the model. Pilot the review bot before students depend on it.
