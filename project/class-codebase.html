The Class Codebase ​

Every team works in the same real open-source project all semester. It's large enough that nobody can hold it in their head, real enough that its maintainers' standards apply, and, by default, a coding agent itself, so the codebase also teaches the course's subject.

Why a coding agent's codebase ​

Two of the strongest comparable courses converged on the same idea in 2026. Michigan's EECS 498 dropped its "build the agent" lab and moved its projects into "the real Aider… About 20,000 lines of Python with 12,000 lines of tests", with the rule "Learn, then design, then build" (Lab03 slides). CMU's 17-313 says "we will be building upon opencode, the open source AI coding agent", and its students fork "a class-specific fork of opencode" (17-313 P1).

An agent's codebase does double duty. Onboarding to it teaches you how a real harness manages context, tools, permissions and model providers, which is what weeks 1–4 are about. Changing it is the "large existing codebase" work of weeks 5–13. And your team's contribution is something you'll use: a feature, a fix or a test suite for a tool in your own workflow.

How the codebase is chosen ​

The instructor picks one project before the term, against these criteria. Each criterion is checked and recorded in the instructor's selection notes.

  1. A permissive license (MIT, Apache-2.0, BSD), so a fork, a class fork and student changes raise no licensing questions.
  2. Active. Recent commits and releases, and maintainers who respond to issues. In a study of a master's course, how often a project was committed to predicted student success better than its size or age (Cassee et al.).
  3. A real test suite and CI that pass on the pinned commit, so "CI green" means something from week 2.
  4. Builds in a Codespace from its own README, on the default machine, in minutes, so nobody's laptop decides their grade.
  5. Approachable issues: enough labeled or easily scoped issues for every team to find a feature area, plus room for each team's own proposals.
  6. An AI-contribution policy that permits disclosed AI assistance, or no policy that forbids it. A project that declines AI-assisted work (as QEMU's policy does at the time of writing) is unsuitable even for Tier 1, because Tier 3 must stay possible.
  7. Manageable size: large enough to need agents and real comprehension, small enough that a team can find its way around in two weeks. Michigan's 20,000 lines is a good reference point.
  8. For Tier 3: no history of capping or closing outside PRs, and a maintainer contact made before the term (contribution rules).

If no candidate meets criteria 1–6, the course uses the strongest candidate as a class fork for Tiers 1 and 2 and drops Tier 3 for the term, rather than send students to a project that doesn't want their work.

What you do first (week 2) ​

Your first contact with the class codebase is comprehension, not change. That's where brownfield labs work best: CMU 17-316's activity has students use an agent to understand an unfamiliar game, generate documentation, and explain it to a neighbor ("Is it good? Correct?") before changing anything (17-316 activity).

In the week 2 Lab you:

  1. Build it in a Codespace from the class fork, following the build steps above and the project's own README. Note every step the README got wrong or left out (observed).
  2. Run its tests and record the command, the time it takes, and any failures on the pinned commit.
  3. Map its architecture with an agent: the entry points, how a user request flows to a model call and back, where tools are defined, where permissions are enforced, how providers are configured, how the tests are organized.
  4. Verify every claim in the map: tag each one observed (you opened the file or ran the code) or inferred (the agent said so, or you concluded it), and check the inferred claims that matter. Agents summarize code they haven't fully read; this is where you learn how often.

The week 2 assignment turns this into an individual onboarding report, which becomes the basis for your team's M0 proposal. Then:

  • Week 2: teams are announced; each team forks the class fork into the course organization and writes course/TEAM_CHARTER.md.
  • Week 3: you write an AGENTS.md for the class codebase and test whether an agent follows it.
  • Week 4: your team writes course/THREAT_MODEL.md for its own agent setup, before anyone gives an agent broad access to the fork.
  • Week 5: M0, your team's proposal.

How the class fork is managed ​

  • Pinned. The class fork starts at one upstream commit, so every team builds on the same base and the course's labs and answer keys stay valid.
  • Syncs are announced. Staff may merge newer upstream work into the class fork once or twice a term, with a week's notice and a known-good commit. Teams then merge from the class fork when they're ready. Never pull from upstream yourselves: an unannounced upstream change can break every team's CI at once.
  • If upstream changes its license or AI policy during the term, the instructor tells the class what changes for Tier 3. Tiers 1 and 2 continue on the class fork.
  • Team forks are public, in the course's GitHub organization, so free CI and code scanning work and the PR round can happen. They contain only public open-source code and course documents, never grades or personal writing.

Rules ​

  • Nothing goes upstream except through Tier 3 and its rules (contribution rules). CMU's course says the same: "You should not submit your changes to the parent opencode repository" (17-313 P2B).
  • Follow the project's code of conduct and license in your team fork as you would upstream. Keep the license file and copyright headers as they are.
  • Credit what you use. Code copied from elsewhere needs a compatible license and a note in the PR.
